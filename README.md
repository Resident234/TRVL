# TRVL

Версия проекта: **0.2.0** (см. [CHANGELOG.md](CHANGELOG.md)).

## Архитектурное решение

### Основа решения

Для проекта TRVL принимается **слоистая архитектура**. Подход основан на описании технологической платформы и Yii-приложения в статье «Слоистая архитектура на основе фреймворка yii» [1], а структура прикладных компонентов дополнительно сопоставляется с официальной моделью Yii 2 [2] [3].

> Слоистая архитектура — это такая архитектура системы, при которой система состоит из упорядоченной совокупности программных подсистем, называемых слоями, такой, что:
>
> 1. на каждом слое ничего не известно о свойствах и даже существовании последующих, более высоких слоёв;
> 2. каждый слой взаимодействует с непосредственно предшествующим, более низким слоем через заранее определённый интерфейс, не зная внутреннего устройства нижележащих слоёв;
> 3. каждый слой располагает ресурсами, которые он либо скрывает от других слоёв, либо предоставляет непосредственно следующему слою через абстракции.
>
> Практическое следствие для TRVL: зависимости направлены сверху вниз, а детали реализации скрыты за контрактами и публичными API модулей.

В классической схеме статьи технологическая платформа разделяется на **Core layer**, **Shared layer** и **Application layer**. Для TRVL сохраняется эта модель. Docker, nginx, PHP-FPM и PostgreSQL рассматриваются как среда исполнения и инфраструктурная граница, а не как повод нарушать логические границы прикладных слоёв.

### Слои TRVL

| Слой | Назначение | Что находится в слое | Что слой не должен знать |
|---|---|---|---|
| **Core** | Низкоуровневые, стабильные и переиспользуемые технические абстракции | Yii 2, Composer-зависимости, базовые контракты, DTO/результаты, технические исключения, общие утилиты и абстракции доступа к инфраструктуре | Конкретные сценарии приложения, канал TRVL, конкретные источники и пользовательские процессы |
| **Shared** | Переиспользуемая бизнес-функциональность и интеграционные модули | Модули сущностей, профилей, источников, публикаций, стилей, медиа, тегов, актуальности и Telegram; публичные сервисы, репозитории и адаптеры модулей | Конкретные контроллеры и представления приложения, конкретную конфигурацию одного приложения и детали других Shared-модулей |
| **Application** | Сценарии конкретного продукта и его пользовательские интерфейсы | Тонкие web-контроллеры, console-команды, конфигурация, сборка use-case сценариев, приложение TRVL, dashboard и специфические представления | Внутреннее устройство Shared-модулей, SQL, HTTP-клиенты, Telegram API и конкретные способы хранения данных |

Направление зависимостей для бизнес-кода: **Application → Shared → Core**. Core не зависит от Shared и Application. Shared не импортирует классы Application. Application обращается к Shared только через его публичные контракты, сервисы, команды, DTO и результаты. Прямой обход слоя, например вызов SQL из контроллера или обращение Application к внутреннему классу Shared-модуля, запрещён.

Инфраструктурные детали подключаются на границе системы. PostgreSQL, HTTP-источники, Telegram, файловое хранилище, нейронные сервисы и средства обработки изображений должны быть скрыты за интерфейсами и адаптерами. Конкретные реализации связываются с интерфейсами конфигурацией Yii и контейнером приложения. Поэтому замена PostgreSQL, API-адаптера или реализации генерации текста не должна требовать изменения use-case кода.

### Правила слоёв

Каждый слой обязан предоставлять следующему слою только необходимую абстракцию. Внутренние модели, SQL-запросы, структуру таблиц, HTTP-ответы, токены, файловые пути и SDK-объекты не должны утекать через публичный API модуля.

Связь между слоями выполняется через параметры, команды, DTO, типизированные результаты и исключения. Использование общих глобальных массивов, глобальных переменных и неявного состояния для обмена данными между слоями запрещено. Сервисы должны получать зависимости явно через конструктор или через конфигурацию композиционного корня.

`Yii::$app` и другие service locator-механизмы допускаются в entry points, конфигурации и composition root, где собираются зависимости приложения. В бизнес-коде предпочтительны явные зависимости и интерфейсы; бизнес-сервис не должен самостоятельно искать глобальный компонент, открывать соединение с БД или создавать внешний SDK-клиент.

### Application layer: тонкие контроллеры и команды

Web-контроллеры и console-команды являются точками входа. Они принимают и минимально валидируют входные данные, преобразуют их в команду или DTO, вызывают use-case сервис и формируют HTTP-, console- или JSON-ответ.

Контроллеры и команды не должны содержать правила парсинга, планирования публикаций, выбора стиля, преобразования изображений, работы с Telegram, SQL-запросов или сложных ветвлений предметной области. Такая логика располагается в Shared-модулях и вызывается через их публичное API.

Application layer отвечает за композицию конкретного продукта. Например, сценарий «поставить текст в очередь, обработать стиль и отправить на публикацию» может быть собран в Application-сервисе из публичных операций модулей очереди, стиля и публикации, но внутреннее устройство этих модулей ему неизвестно.

### Shared layer: функциональные модули

Функциональность, которая может быть использована более чем одним сценарием или приложением, оформляется как модуль с чёткой границей. На первом этапе модуль может находиться внутри Application, но при появлении второго потребителя его необходимо выделить в Shared без изменения публичного API.

В перспективе в TRVL должны быть выделены следующие функциональные области:

| Модуль | Ответственность |
|---|---|
| **Source/Entity** | Источники, сущности, посты, идентификация элементов и фиксация изменений |
| **Profile** | Профили, описания и слоганы |
| **Parsing** | Получение и нормализация данных из источников; повторный проход и обнаружение обновлений |
| **Publication** | Посты, порядок публикации, отложенная публикация и очереди |
| **Style** | Хранение образцов текста, структуры и выбранных стилей |
| **Media** | Изображения, преобразования и будущий логотип-вотермарк |
| **Tagging/Actuality** | Теги и примечания с датой актуальности информации |
| **Telegram** | Интеграция с каналом TRVL и будущим Telegram-ботом |
| **Settings** | Подстраиваемые величины страницы публикаций, их описание в одной схеме и хранение в `publications_setting` (`app/shared/Settings`, выделен из Publication) |
| **Dashboard** | Только если интерфейс нельзя оставить в Application; бизнес-операции остаются в Shared |

Каждый модуль должен скрывать свои модели хранения и инфраструктурные детали. Другие модули обращаются к нему через сервисы, интерфейсы, команды и DTO. Например, модуль Publication не должен требовать от вызывающего кода знания таблиц PostgreSQL, а модуль Style не должен заставлять контроллер работать с конкретной реализацией AI-провайдера.

В Yii 2 модуль является самодостаточной единицей, которая может включать `Module.php`, модели, контроллеры, представления, конфигурацию и консольные команды [3]. Для TRVL это используется как организационный механизм, но границы слоёв важнее одной только структуры каталогов: наличие каталога `models` не делает любой код внутри него бизнес-логикой автоматически.

### Предлагаемая организация каталогов

Текущий Yii Basic Application остаётся рабочей точкой входа. По мере развития проекта структура должна эволюционировать в сторону явного разделения приложения и переиспользуемых модулей:

```text
TRVL/
├── app/                         # Application layer и Yii entry points
│   ├── commands/                # тонкие console-команды
│   ├── controllers/             # тонкие web-контроллеры
│   ├── modules/                 # специфичные для приложения модули
│   ├── views/                   # представления приложения
│   ├── config/                  # конфигурация и composition root
│   ├── web/                     # публичный document root
│   ├── tests/                   # тесты приложения и сценариев
│   └── yii                      # console entry script
├── shared/                      # Shared layer, добавляется при выделении модулей
│   ├── modules/
│   ├── contracts/
│   └── config/
├── core/                        # Core layer проекта, если собственных абстракций станет достаточно
│   ├── contracts/
│   ├── dto/
│   ├── exceptions/
│   └── support/
├── docker/                      # среда исполнения, вне бизнес-слоёв
├── config/                      # конфигурационные шаблоны проекта
├── docker-compose.yml
└── README.md
```

Пока отдельные `core/` и `shared/` ещё не выделены в коде, это не является основанием для размещения бизнес-логики в контроллерах. Новая функциональность должна сразу проектироваться как кандидат на отдельный модуль с публичным API и возможностью последующего перемещения из `app/modules` в `shared/modules`.

### Конфигурация и подмена реализаций

Конфигурация Yii используется как слой связывания зависимостей и как средство уменьшения связанности. Компонент получает стабильный идентификатор или интерфейс, а конкретный класс выбирается в configuration/composition root. Замена локального адаптера на REST-клиент, одного хранилища на другое или одного AI-провайдера на другой не должна требовать изменений в контроллерах и use-case сценариях.

Конфигурация окружения, секреты и параметры подключения не должны зашиваться в исходный код. Локальные значения передаются через `.env` и Compose, а код получает их через конфигурационный слой. Секреты не коммитятся и не выводятся в логи.

### Модель данных и PostgreSQL

PostgreSQL является инфраструктурой хранения. Таблицы, индексы, SQL и ORM/ActiveRecord-модели относятся к нижнему уровню модуля и не должны становиться контрактом для Application layer. Use-case сервисы работают с репозиториями или доменными API, а не с прямыми SQL-запросами.

Схема данных должна поддерживать идентификацию источника и внешнего элемента, дату последнего наблюдения, версию или хэш содержимого, состояние обработки и дату актуальности. Это позволит реализовать повторный полный проход диапазона без дублирования, обнаружение изменений и добавление новых элементов. Конкретные таблицы и поля будут проектироваться отдельным этапом, когда начнётся реализация парсинга.

### Тестируемость и развитие

Каждый Shared-модуль должен иметь тесты публичного API и основных бизнес-правил. Инфраструктурные адаптеры тестируются отдельно от use-case сценариев. Application-тесты проверяют сборку сценариев и точки входа, но не должны дублировать внутренние тесты Shared-модулей.

В дальнейшем система сборки, миграций, CI, Selenium, очереди и фоновые процессы добавляются как инфраструктура вокруг слоёв, не разрушая их границы. Новая технология не должна становиться причиной прямой зависимости контроллеров от внешнего SDK или хранилища.

### Архитектурные критерии при code review

Перед добавлением функциональности необходимо ответить, к какому слою и модулю она относится, какой публичный контракт предоставляет и какой нижний слой использует. Следует проверить, не знает ли нижний слой о верхнем, не протекают ли наружу детали хранения или SDK, не появилась ли бизнес-логика в контроллере и можно ли заменить инфраструктурную реализацию через конфигурацию.

Функциональный блок считается корректно выделенным, если его можно вызвать из другого Application-сценария через публичный API, протестировать без реального внешнего сервиса и при необходимости перенести между приложениями без переписывания внутренней логики. Это поддерживает ключевые цели подхода из статьи: повторное использование, расширяемость, единый деплой и возможность менять детали реализации без изменения верхних слоёв [1].

### Модель данных

Публикации канала TRVL хранятся в четырёх таблицах PostgreSQL, а подстраиваемые величины страницы публикаций — в пятой:

| Таблица | Назначение |
|---|---|
| `publications_post` | Посты канала: запланированные (`published_at` в будущем, `telegram_id` пуст) и уже опубликованные (`telegram_id` заполнен) |
| `publications_draft` | Черновики — записи до отправки в Telegram |
| `publications_edited` | Архив редактирования опубликованных постов (те же поля, что у поста, плюс `edited_at`); пустой `edited_at` означает, что сообщение в канале ещё не заменено новым текстом |
| `publications_deleted` | Архив удалённых постов — soft-delete (те же поля, что у поста, плюс `deleted_at`); пустой `deleted_at` означает, что сообщение ещё не удалено из канала |
| `publications_setting` | Настройки публикации: строка на каждую подстраиваемую величину (`code` → `value` + `updated_at`), сид берётся из схемы `PublicationSettingsService` |

Данные форума (см. [PARSER.md](PARSER.md)): `topic` — топики, `post` — посты топиков, `member` — профили участников (авторы топиков и постов), `parser_config` — диапазоны сущностей и поведение запросов парсеров (см. «Настройки парсера»).

Четыре таблицы публикаций держат один и тот же набор полей, и у них есть общее — `formatting jsonb NOT NULL DEFAULT '[]'` (миграция `m260926_000001_add_formatting_to_publications`): `text` остаётся обычным текстом, а разметка этой строки лежит отдельным списком сущностей сообщения рядом (см. «Форматирование текста»). Пустой список — обычный текст, то есть ровно то, что записано в любой строке, созданной до появления колонки. Тем же порядком рядом лежит и кнопка-ссылка строки — `button jsonb NOT NULL DEFAULT '{}'` (миграция `m260927_000001_add_button_to_publications`, см. «Кнопки-ссылки»): список пар `{text, url}` той же записи, по одной на каждую кнопку сообщения; пустой список или пустой объект — сообщение без кнопок, а одиночный объект — то, что записала строка, созданная до появления списка. Рядом стоит и заголовок строки — `title text NOT NULL DEFAULT ''` (миграция `m260928_000001_add_title_to_publications`, см. «Заголовок части»): жирная первая строка, которая в `text` не входит и добавляется к сообщению при отправке; пустая строка — сообщение без заголовка, то есть ровно то, что записано в любой строке, созданной до появления колонки.

### Открытие на редактирование

При нажатии на кнопку-иконку редактирования (или двойном клике по элементу списка) публикация любого типа — черновик, запланированная, опубликованная или удалённая — открывается на редактирование в форме «Новая публикация»: текст подставляется в поле ввода, заголовок — в поле над ним (атрибут `data-title` строки, пустой заголовок остаётся пустым полем), дата публикации (для постов и удалённых записей с непустым `published_at`) — в поле даты, а тип и id исходной записи передаются скрытыми полями `publicationSource` / `publicationSourceId`.

Время публикации в списках и в атрибуте `data-published-at-utc` хранится в UTC, а поле даты формы работает с местным временем пользователя, поэтому при подстановке значение переводится в часовой пояс пользователя (`utcToPickerValue()`) и в обратной форме возвращается на сервер, где `normalizeDate()` приводит его обратно к UTC. У записи без `published_at` (черновик) поле даты остаётся таким, каким было в форме.

Поле «Дата и время публикации» берёт ближайший слот от часов браузера, когда форма возвращается в пустое состояние: после отправки, которую сервер принял («Опубликовать» или «Сохранить» — обе кнопки одной формы, и успешный ответ проходит через `clearEditingState()`), и после «Очистить». Ответ, который запись не принял, форму не трогает: время, выбранное редактором, остаётся, пока он правит текст под замечанием. Прочие запросы страницы — прогрузка списков и постов топика, сортировка, порядок текста, переключатели заголовка и ссылок, сохранение фильтра — поле не двигают, иначе дата уехала бы с каждым кликом по списку. Две стороны одного момента пишет `applyPublicationSlot()`: значение поля, календарь рядом (`setStartDate`/`setEndDate` на `__HORIZON_HOURS` вперёд) и бейдж времени в предпросмотре; до этого тот же текст был набран дважды — в `setEditing()` и в `clearEditingState()`, — и вторая копия не проверяла, читается ли значение.
Запись, открытая на редактирование, своего времени не теряет: `setEditing()` ставит в поле её дату (из `data-published-at-utc`, переведённую в пояс редактора), и держится она до тех пор, пока форма стоит открытой, — а `published_at` при сохранении берётся прямо из поля.

У каждой части разбитой публикации — свой альбом. Блок части несёт поле `publicationPartImages[]` со своей подписью («Изображения этой части»), своим пикером файлов, своей плашкой замечаний и своим превью; альбомом первой части служит общее поле «Изображения публикации» (`publicationImages`) под списком, поэтому у первого блока собственное поле скрыто и выключено (`d-none` + `disabled`) — невыгружаемое поле не уходит на сервер и не сдвигает части списка. Порядок при этом один и тот же: `publicationText[]` и `publicationPartImages[]` читаются позиционно (`SiteController::imageGroupsFromRequest`), так что N-е поле текста соответствует N-му полю альбома. И общее поле, и блок части стоят в рамке `publication-field-frame` — той же, что обводит набор кнопок (см. «Кнопки-ссылки»), — а не в отдельном отступе: рамка говорит, где кончается один набор полей и начинается другой. Её класс добавлен к `publication-part-album`, по которому коробка альбома находится и клонируется, поэтому JS от обводка не переехал.

Вместе с текстом в поле альбома подставляется список `image_urls` — из редактируемой записи или из элемента форума (атрибут `data-image-urls`), и в форму он попадает не как есть. Форум хранит ссылки, которые он прочитал когда-то, а файл за ссылкой к этому времени мог исчезнуть; заметить это до отправки альбома в канал можно только одним способом — запросив каждую ссылку, чем и занимается JS страницы (`writeImages`, `probeImage` через `new Image()`). В поле остаются ссылки, ответившие загрузкой; та, что не ответила вовсе, мёртвой не считается — по истечении `__IMAGE_PROBE_TIMEOUT` (настройка «Ожидание проверки картинки», 6 с по умолчанию) она остаётся в поле. Альбом записывается в поле целиком сразу, а не по мере ответов, чтобы форма, отправлённая посреди проверки, не потеряла живую картинку; список сужается, когда ответили все. Проверка и сужение живут отдельно у каждого альбома: счётчик `albumWrites[index]` растёт от любой записи в это поле — и от заполнения, и от руки, — поэтому опоздавший ответ не трогает поле, которого к его приходу уже нет.

Отброшенные ссылки в форму не подгружаются и перечисляются под тем полем, из которого их убрали: у общего поля это `#publicationImagesNotice`, у поля части — `.publication-images-notice` её же блока (`Мёртвые ссылки в изображения не добавлены (N): …`), и то и другое скрыто (`d-none`), когда терять нечего. Очистка формы после сохранения идёт через ту же `writeImages`, поэтому замечание убирается вместе со ссылками. Замечание общего поля отступлено на `mt-1`, а не на `m-3 mb-1`: верхний отступ ему даёт рамка, внутри которой оно стоит.

### Сценарии сохранения

Дальнейшее поведение зависит от типа редактируемой записи и нажатой кнопки — «Опубликовать» или «Сохранить». Восемь сценариев (логика в `PublicationsService::saveFromForm`, `app/shared/Publications/Service/PublicationsService.php`):

| Редактируемая запись | Кнопка | Что происходит |
|---|---|---|
| Запланированная публикация | **Опубликовать** | Штатное обновление в таблице публикаций: `published_at` обновляется текущим значением соответствующего поля формы, `updated_at` — временем изменения, `created_at` сохраняется в неизменном виде |
| Запланированная публикация | **Сохранить** | Запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `updated_at` — текущее время, то есть момент перемещения в черновик; `created_at` сохраняется в неизменном виде |
| Опубликованная публикация | **Опубликовать** | Запись удаляется из таблицы публикаций и добавляется в `publications_edited`: копируются значения всех полей, `updated_at` — текущее время, `edited_at` остаётся пустым |
| Опубликованная публикация | **Сохранить** | Запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `updated_at` — текущее время, то есть момент перемещения в черновик; `created_at` сохраняется в неизменном виде |
| Черновик | **Опубликовать** | Запись удаляется из таблицы черновиков и добавляется в таблицу публикаций; `updated_at` — текущее время, `created_at` сохраняется в неизменном виде |
| Черновик | **Сохранить** | Штатное обновление в таблице черновиков; `updated_at` — время изменения, `created_at` сохраняется в неизменном виде |
| Удалённая запись | **Опубликовать** | Запись удаляется из `publications_deleted` и добавляется в таблицу публикаций с датой из поля формы; `created_at` сохраняется, `updated_at` — текущее время, `telegram_id` сбрасывается; ожидающееся удаление из канала отменяется |
| Удалённая запись | **Сохранить** | Запись удаляется из `publications_deleted` и добавляется в таблицу черновиков; `created_at` сохраняется, `updated_at` — текущее время (момент перемещения), `telegram_id` сбрасывается; ожидающееся удаление из канала отменяется |

Отдельно от формы работают кнопки-иконки на элементах списков:

- **«Опубликовать» на черновике** — запись удаляется из таблицы черновиков и добавляется в таблицу публикаций; `created_at` без изменений, `updated_at` и `published_at` — текущее время (пост сразу готов к отправке в канал периодической задачей)
- **«Опубликовать» на запланированной публикации** — запись перестаёт быть запланированной: `published_at` и `updated_at` становятся равными текущему времени, `created_at` не меняется
- **«Переместить в черновик» на публикации** (пост любого типа — запланированный или опубликованный) — запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `created_at` не меняется, `updated_at` — текущая дата и время
- **«Удалить» на публикации или черновике** — запись перемещается в `publications_deleted`: `created_at` и `published_at` сохраняют свои значения (у черновика `published_at` остаётся пустым), `updated_at` заполняется текущим временем, `deleted_at` не заполняется. Периодическая задача `telegram/delete-due` затем удаляет сообщение из канала по `telegram_id` (у записей без `telegram_id` — черновиков и запланированных постов — сообщения в канале не было, им `deleted_at` проставляется сразу) и записывает в `deleted_at` время удаления. Если канал сообщения уже не содержит (`message to delete not found`), это и есть нужный результат: запись получает `deleted_at` как при обычном удалении и из очереди уходит, а не повторяется каждые пять минут.

Общие правила всех сценариев:

- `created_at` исходной записи всегда сохраняется неизменным;
- `updated_at` всегда устанавливается в текущее время — момент обновления или перемещения между таблицами;
- отправка в Telegram из формы не выполняется: записи уходят в канал только периодической задачей `publishDue()` по наступлении `published_at`.

Для новой записи (форма открыта без редактирования) кнопка «Опубликовать» создаёт запланированный пост, кнопка «Сохранить» — новый черновик.

Кнопка **«Очистить»** (третья в том же ряду, `#publicationClearBtn`) форму не отправляет: она возвращает её в то же пустое состояние, в каком страница открывается, — тем же сбросом, который отрабатывает после сохранённой записи (`clearEditingState()`). С полями уходит и перехваченная под правку запись: `publicationSource` встаёт в `new`, `publicationSourceId`, `forumEntityType` и `forumEntityId` — в пусто, гаснет её бейдж, а дата получает ближайший слот; осталась она на своём id — следующий «Опубликовать» перезаписал бы её вместо новой. Разбитая публикация сворачивается в одну часть, её заголовки, альбомы ссылок, выбранные файлы, кнопки и переключатели «Нумерация частей», «Равномерно распределить изображения» и «Кнопки-ссылки в каждой части» очищаются вместе с ней; два переключателя, живущих в сессии («Первая строка — в заголовок», «Ссылки из текста в кнопки-ссылки»), остаются как их оставили.

### Форматирование текста

Текст части набирается в редакторе Quill (версия 2.0.3 лежит в репозитории: `app/web/ui-kit/assets/vendor/quill/`, подключается `PublicationEditorAsset`, поверх вендорной темы — `app/web/ui-kit/assets/css/publication-editor.css`). Панель инструментов ограничена тем, что выводит канал: **жирный**, *наклонный*, подчёркнутый, зачёркнутый, `код` и ссылка (`TOOLBAR_FORMATS`) — шрифтов, размеров, заголовков, списков, цитат, цветов и выравнивания в форме нет, потому что Telegram их не рисует.

Размеченный текст хранится раздельно: `text` записи — обычные символы без меток, а разметка — список сущностей сообщения в той же форме, в какой их принимает Telegram API (`MessageEntities`: `bold`, `italic`, `underline`, `strikethrough`, `code` и `text_link` со ссылкой). `parse_mode` не отправляется никогда — именно поэтому смещения сущностей считаются по символам текста, а не по парным `**` или `__`.

- **Носителем данных остаётся textarea.** Скрытое поле части (`textarea.publication-text-part`, имя `publicationText[]`) — то же поле, что и до редактора: счётчики, лимиты, разбивка, слияние и отправка формы читают его. Quill стоит в соседнем `div.publication-editor-field` и служит видимой поверхностью. Три правила связывают их: запись в `field.value` переносит сущности вместе с текстом и перекрашивает редактор (`paintEditor`); ввод в редактор пишет значение через нативный сеттер, перечитывает список у документа и рассылает обычный `input` — то самое событие, которое страница слушает и без редактора; курсор отвечает от редактора, потому что `selectionStart`, `selectionEnd`, `setSelectionRange` и `focus` переопределены у каждого экземпляра поля, — поэтому разрез у курсора остаётся разрезом там, где его видит человек.
- **Список уходит на сервер вторым скрытым полем блока.** Рядом с textarea лежит `input[type=hidden].publication-format-field` с именем `publicationFormatting[]`, в него пишется JSON сущностей этой части. `SiteController::publicationFormatsFromRequest()` читает два списка позиционно — так же, как `imageGroupsFromRequest()` читает альбомы, — поэтому N-й список отвечает N-й части, а пропущенное поле (запись старше редактора) возвращается пустым списком.
- **Индексы совпадают сами.** Telegram считает смещения в кодовых единицах UTF-16, и `String#length` в браузере считает их же, так что позиция в редакторе, позиция в textarea и смещение сущности — одно число; эмодзи за базовой плоскостью не сдвигает ничего. На сервере то же значение считает `MessageEntities::utf16Length()`.
- **Экран и есть то, что уходит.** `paintEditor` перекрашивает поле по списку, а потом перечитывает список у документа (`entitiesFromOps`): сущность, не влезшая в текст, отрезается, соседние прогоны одного формата склеиваются, а порядок остаётся по возрастанию смещения — то, чего требует `MessageEntities::assertFitsText()`. Перечитывание правит и то, чего редактор хранить не может: пустая строка в конце значения не сохраняется, и в textarea возвращается ровно тот текст, какой вышел в редакторе.
- **Сущности едут вместе со своим текстом.** Нумерация частей, подстановка из форума, ручная и автоматическая разбивка, слияние и перенос выделения работают с двумя списками сразу. Переписывание поля на месте ведёт `remapEntities` (разбор по общему началу и общему концу), разрез части — `splitEntitiesAt`, перенос выделения — `takeEntities`, `exciseEntities` и `shiftEntities`, склейка двух частей — `joinedFormats`, а `sortEntities` и `joinAdjacent` приводят результат к каноническому виду. Подробно о судьбе списков при разбивке — в разделе «Разбивка длинного текста на части».
- **Панель отвечает на нажатие кнопки мыши, а не на `click`** — Quill отменяет `click`, чтобы редактор не потерял фокус. Слушатель `paste` навешан на контейнер в capture-фазе и вставляет только текст: иначе в форму приходят заголовки, цвета и разметка той страницы, откуда его скопировали. Там же адрес, пришедший вместе с текстом, становится ссылкой — см. «Ссылка в тексте».
- **Запись на редактирование** подставляет в поле и его сущности: элемент списка несёт их в атрибуте `data-formatting`, `parseFormatting()` читает строку, а дальше список живёт в поле как разметка его же текста. Сами списки записей (черновики, посты, удалённые) остаются текстом без разметки — раскрашивается только форма и её предпросмотр.
- **Сервер проверяет список так же, как лимит текста.** `PublicationsService::saveParts()` и `saveFromForm()` сначала снимают пробелы по краям (`trimFormatting()` — тот же `slice()`, что и у подписи), затем `assertPartValid()` вызывает `assertFitsText()`: пустая сущность, сущность за границами текста, список не по порядку и ссылка без http(s)-адреса дают `InvalidArgumentException` — flash, и ни одна запись не записана.
- **В канал разметка уходит списком `entities`.** `ChannelService::publishText()`, `publishPhotos()` и `editPostText()` принимают `MessageEntities` и отдают его `NutgramChannelClient` как `entities` у текста и `caption_entities` у подписи. Публикация с альбомом режется на подпись и продолжение по порогу `CAPTION_MAX_LENGTH`, и список режется тем же `slice()`: в подписи остаются отрезки разметки её куска, в продолжение уходят остальные, уже отсчитанные от начала своего текста.

Спойлера в списке нет: встроенного спойлера у Quill нет, и для него пришлось бы писать собственный blot. Блочные форматы — цитата, заголовок, список, `pre` — исключены тем же правилом, что ограничивает панель: форма даёт ровно то, что Telegram рисует внутри строки текста.

### Заголовок части

Первая строка сообщения, набранная жирным, — так канал отделяет тему публикации от её текста. Поле «Заголовок» (`#publicationTitleInput`, имя `publicationTitle`) стоит над редактором первой части, а каждая прочая часть получает своё в клонированном блоке (`.publication-title-field`, имена `publicationPartTitle[]`). Заполнять его не обязательно: пустое поле (как и поле из одних пробелов) значит сообщение без заголовка, и уходит ровно тот текст, что набран в редакторе.

- **Заголовок — отдельная колонка, а не начало текста.** `title text NOT NULL DEFAULT ''` живёт в четырёх таблицах публикаций рядом с `formatting` и `button` (миграция `m260928_000001_add_title_to_publications`), поэтому `text` записи остаётся тем, что человек набрал, а сообщение канала собирает `PublicationData::messageText()` и `messageEntities()` в момент отправки. Запись, созданная до появления колонки, — пустой заголовок, то есть то же сообщение, что и раньше.
- **Нумерация частей переезжает в конец заголовка.** Часть со своим заголовком уходит в канал строкой «Заголовок. Часть 2»: `PublicationData::splitHeader()` узнаёт начало текста по тому же образцу, что и `stripPartNumber()` страницы, снимает его с текста и ставит после заголовка через точку. Что написал сам автор — точку или двоеточие после номера — то и остаётся; строка «Часть 2» в textarea при этом не меняется, и поле формы по-прежнему хранит её.
- **Жирным становится вся строка заголовка.** `MessageEntities::underHeading()` добавляет `bold` от нуля до её конца и сдвигает за неё сущности текста — на длину заголовка, на пустую строку после него и минус тот номер, который заголовок из текста забрал. Без последней поправки жирный прогон уехал бы на «Часть 1» дважды, потому что смещения в `formatting` отсчитаны от начала сохранённого текста, а он начинается с этой строки.
- **Экран и есть то, что уходит.** `composedMessage()` переносит тот же разбор на страницу: `update()` рисует в предпросмотре заголовок жирной первой строкой над телом, `updateCounters()` показывает длину уже собранного сообщения, а `headingReserve()` отнимает от лимита части её заголовок (плюс пустую строку), так что разбивка начинается раньше, если заголовок длинный. Сервер считает то же по собранному тексту: `assertPartValid()` меряет `messageOf()` против `TEXT_MAX_LENGTH` и говорит «Заголовок с текстом должен быть не длиннее 4096 символов» (нижняя граница у этой проверки больше не своя — о ней говорит требование текста либо альбома, см. «Альбом вместо текста»).
- **Списки читаются позиционно.** `SiteController::publicationTitlesFromRequest()` ставит общее поле на место первой части и добавляет клонированные (`partFieldsFromRequest`) — тем же порядком, каким читаются альбомы, списки сущностей и кнопки, — поэтому N-е заглавие отвечает N-й части. Пустая строка колонки значит, что у этой части заголовка нет.
- **Любая перестройка частей рассаживает заголовки заново.** `setTextParts()` принимает список заголовков и пишет их в поля после клонирования, а места, где часть появляется или исчезает, называют это явно: ручная и автоматическая разбивка и перенос выделения дают новой части пустое поле, слияние убирает поле той части, которой больше нет — у сообщения одна первая строка, и остаётся заголовок той части, в которую слили.
- **Запись на редактирование подставляет свой заголовок**, элемент списка несёт его в атрибуте `data-title`, а `loadText()` отдаёт его первой части; подстановка из форума сама по себе заголовка не приносит — у темы форума своё название, и без переключателя шапки формы оно остаётся первой строкой текста. Очистка формы после сохранения убирает его вместе с остальными полями.
- **Переключатель «Первая строка — в заголовок»** (`publicationTitleFromFirstLine`) стоит справа в шапке карточки «Новая публикация» — в том же `justify-content-between` ряду, что и её заголовок, и объясняет себя поповером самой группы (см. «Подсказка элемента» в «Стили и скрипты страниц»). Он говорит не о записи, а о том, как читать подгрузку: с ним `firstLineAsHeading()` снимает первую строку у текста, который приносят «Опубликовать» топика или поста, «Тред целиком» и «Тред по частям», и отдаёт её в поле «Заголовок» той части, куда лёг этот текст. У тофика первой строкой стоит его название (кнопка кладёт его перед текстом), у поста — первая набранная им строка. Снятая строка из текста исчезает, а не повторяется в двух полях. Одной строкой текст не режется: если за первой строкой ничего не осталось, поле заголовка пустое, а текст приходит целиком — пустую часть без своего альбома отвергает `assertPartValid()`. В «Треде по частям» заголовок берёт на себя только первая часть, та, в которую лёг топик; остальные приходят со своими пустыми полями, как приходили и раньше. Состояние переключателя живёт в сессии — ключ `titleFromFirstLine`, тот же порядок, что у фильтров форума и у порядка списков: `actionPublications()` решает его через `syncTitleFromFirstLine()` (сессия, которая уже держала переключатель, не даёт ссылке его повернуть; сессия, которая его ещё не держала, принимает `?titleFromFirstLine=1` из адреса), `publicationsUrl()` ставит этот параметр обратно, а `change` тумблера уходит POST на `site/title-from-first-line-save` — тот пишет сессию и отвечает адресом, который JS подставляет через `mirrorUrl`. Ничего на странице ради него не перерисовывается: переключатель говорит о том, как читать подгрузку, а не о том, что показать. В `publication-create` состояние не уходит, и очистка формы его не трогает — настройка чтения переживает и несколько подгрузок подряд, и перезагрузку страницы.
- **Списки записей показывают собранное сообщение.** `_item_post.php`, `_item_draft.php` и `_item_deleted.php` выводят `headingAndBody()` записи: жирную строку заголовка над текстом без съеденного им номера.

### Ссылка в тексте

Ссылка — одна из шести сущностей и единственная со своим адресом: `text_link` стоит над куском текста, а адрес живёт у самой сущности, поэтому в `text` записи не появляется ничего. Ссылку ставят двумя путями: её набирают через панель редактора и её проставляет сама страница там, где текст приходит в форму извне.

- **Панель спрашивает русским окном, а не системным `prompt()`.** На кнопке ссылки Quill зовёт `prompt()` — окно браузера: его заголовок не перевести, адрес уже стоящей ссылки в поле не подставляется, и то, что пустой ответ ссылку убирает, в нём ничем не сказано. Обработчик `link` переопределён при подключении редактора (`modules.toolbar.handlers.link` → `openLinkDialog`), и страница показывает своё окно Bootstrap (`#publicationLinkModal`, рядом с окном планирования): поле «Адрес ссылки», «Применить», «Отмена» и «Убрать ссылку». Окно работает с выделением, как и прочие кнопки панели: ничего не выделено — flash «Выделите текст, который станет ссылкой.», и адрес не набирается.
- **Одно окно добавляет, правит и убирает.** Курсор, стоящий внутри ссылки, раскрывается до всей ссылки (`enclosingLink` читает список сущностей части, а не документ), её адрес подставляется в поле, а «Убрать ссылку» видна только над уже стоящей ссылкой. Пустое поле значит ровно то же: `formatText(…, 'link', '')` снимает разметку, и текст остаётся обычным. Окно, закрытое «Отменой» или крестиком, выделение не трогает, а `linkTarget` снимается на `hidden.bs.modal`, чтобы запоздалый «Применить» не написал в уже забытую часть.
- **Хост без протокола читается как https, любая другая схема отвергается.** `linkAddressOf` дописывает `https://` адресу, набранному без схемы, и отвечает отказом на всякую прочую — flash «Ссылка принимает адрес http:// или https://.», и окно ждёт лучшего адреса. Причина не в Telegram, а в самом редакторе: `Link.PROTOCOL_WHITELIST` у Quill — `http, https, mailto, tel, sms`, и всё остальное редактор молча превращает в `about:blank`, поэтому на его же проверку полагаться нельзя. Глубокие ссылки Telegram (`tg://`) остаются за кнопками-ссылками части: у них своё поле и своя проверка на сервере.
- **Адрес, пришедший текстом, становится ссылкой сам.** Каждый адрес, над которым ещё нет ссылки, оборачивается ею, а протокол из текста вычитается: в сущность уходит `https://awd.ru`, над текстом остаётся `awd.ru`. `linkifyParts()` вызывается из `setTextParts()` — при открытии записи на редактирование, при подстановке из форума, при загрузке треда и при всякой перестройке частей — и стоит до `applyPartNumbers()`, чтобы нумерация перенесла новые сущности вместе с их текстом. Тот же `linkifyEditor()` одного поля стоит в слушателе `paste` сразу после вставки: адрес, попавший в буфер обмена, человек явно не собирался терять, а курсор возвращается на конец вставки за вычетом снятых протоколов.
- **Адрес опознаётся по схеме.** `findLinks()` берёт всё, что началось с `http://` или `https://` и не прерывается пробелом, угловатой скобкой, кавычкой или `«»`; хост без протокола адресом не считается, поскольку не отличается от слова, в котором стоит. Из конца адреса выбрасываются знаки препинания, которыми его обычно окружают (`. , ; : ! ? » « ' " … ]`), и закрывающая скобка, которой в адресе не открывали, — адрес в скобках и адрес перед точкой берутся целиком. Адрес, хоть немного покрытый уже стоящей над ним ссылкой, пропускается, поэтому повторный проход ничего не удваивает и автоматику можно вызывать вперемешку с перестройками частей.
- **Разметку сдвигает сам редактор, а не счёт.** `linkifyEditor()` правит документ Quill — `deleteText()` протокола и `formatText()` ссылки, оба с источником `api`, чтобы слушатель `text-change` не написал зеркало поверх, — а список сущностей после прохода перечитывается у документа (`entitiesFromOps`), и только тогда в поле пишется значение. Так отрезки разметки соседей уходят на новые места сами, и серверная проверка (`assertFitsText()`) получает тот же список, что рисует экран.
- **Автоматика не трогает то, чего не видит.** Напечатанное в редакторе не проверяется: адрес, который человек набрал сам, остаётся текстом, пока он не выделит его и не нажмёт кнопку панели, — молча переписывать набранное было бы хуже самого текста. Текст, пришедший с форума ссылкой, адреса не содержит вовсе: `ForumPageDomParser::htmlToText()` выбрасывает `href` тега `<a>`, и в форму приходит одна метка. Разбивка адреса между частями практически не случается, поскольку `splitIntoParts()` режет по пробелу, а внутри адреса пробела нет, — и сканер разрезанный пополам адрес не чинит.

### Emoji в тексте

Emoji — обычный текст: форма не хранит про них ничего, а панель и поиск по `:` лишь помогают поставить символ в текст части. Тот же символ, что человек принёс с клавиатуры, попадает в `text` записи, уходит в канал тем же `text` и рисуется в предпросмотре как есть.

- **Таблица лежит в репозитории.** `app/web/ui-kit/assets/vendor/emoji/trvl-emoji.js` — 1921 emoji, порядок и категории которых взяты из UTS #51 `emoji-test.txt` (только последовательности уровня fully-qualified), а русские слова — из аннотаций CLDR для `ru` (имя и производные ключи); обе под Unicode License v3, о чём говорит соседний `.LICENSE.txt`. Подключает файл `PublicationEditorAsset`, перед Quill. Одна строка на emoji, табами: сам символ, номер категории, имя, ключи — ключи объекта над каждой строкой стоили бы дороже, чем занимают сами слова.
- **Ищутся emoji по началу слова.** `emojiSearch(query, list, limit)` ставит имя выше ключей — ключ есть свободная ассоциация, и на «кнопку» ключуется секундомер, — внутри одного ранга порядок остаётся порядком таблицы, то есть Unicode, где частые emoji категории идут раньше редких. `emojiKey()` снимает регистр, `ё` и пробелы между словами, поэтому «ёлка» и «Елка » ищутся одинаково. Пустой запрос не просит ничего; панель кнопки показывает `EMOJI_SEARCH_LIMIT` = 60 ответов, а без запроса — `EMOJI_BROWSE_LIMIT` = 160 emoji выбранной категории.
- **Два пути делят одну панель.** Узел `#publicationEmojiPanel` — это `popover popover-rich bs-popover-auto` из `ui-kit/popovers.html`: его `popover-arrow`, `popover-header` («Emoji» с иконкой `bi-emoji-smile`) и `popover-body > .p-1` рисует тема (скругление, тень, фон шапки и границы ширины 350–380px в `main.min.css`), а своими остаются `position: fixed`, `z-index: 1080` и `width: 380px` — та же `max-width` правила `.popover-rich`, только записанная страницей, потому что на произволе содержимого карточка встала бы на свои 350px `min-width`, а восемь столбцов emoji большего не просят; всё три стоят составным селектором `.popover.publication-emoji-panel`, чтобы порядок подключения стилей не перебил их. Восемь столбцов сетки заданы как `minmax(0, 1fr)` с `overflow-x: hidden`, иначе трек растёт от стоящего в нём и не держит карточку: самый широкий ответ, который список оставляет (семья из четырёх), не дотягивает до целого столбца двух пикселей. Ячейка при этом квадратная: `aspect-ratio: 1` даёт ей высоту того столбца, в котором она стоит, а фигуру по центру держит сама сеточная коробка, потому что строка фиксированной высоты не успевает за стороной, которую решила ширина карточки; поле списка поднято до `12.7rem` — ровно пять таких рядов. Панель перенесена в `body` и выводится той же `popupPoint()`, что и всплывающее окно переноса выделения, только якорь берёт разный: `emojiAnchor()` ставит панель кнопки на прямоугольник `.ql-emoji` (`buttonPoint()` даёт её середину и обе границы), а панель двоеточия — на курсор (`caretPoint()`), поэтому карточка сдвигается по горизонтали ровно настолько, чтобы стрелка встала над тем, что её открыло, — над смайлом либо над курсором. Сторону выбирает прокрутка: пока над якорем хватает места, панель стоит над ним и носит стрелку на нижнем крае, когда не хватает — уходит под якорь, и стрелка встаёт на край верхний. Ставит стрелку сама страница, потому что Popper, который обычно владеет ею, здесь не при чём: `placeEmojiPanel()` пишет панели `data-popper-placement` (`top` и `bottom` — это стороны якоря, а не курсора) и уводит `.popover-arrow` к якорю через `translate()`, не подпуская её ближе чем на 1rem к углу карточки. Кнопка панели (`.ql-emoji`, иконка `bi-emoji-smile`) добавляется в уже собранную панель после монтирования редактора: Quill собирает свои контролы при конструировании и об этой не знает, а отвечает она на `mousedown`, как и прочие её кнопки, — `click` редактор отменяет, и курсор ушёл бы из поля. Кнопка сделана flex-контейнером по центру с `.bi::before { display: block }`: Quill заводит свои иконки svg и загоняет их прямо в высоту кнопки, а глиф иконочного шрифта ставится на базовую линию строки, которая не есть середина краски, поэтому без этого смайл смотрелся ниже соседей и крупнее них. Её панель показывает поле поиска и ряд категорий; двоеточие в тексте показывает ту же сетку без них, поскольку слово уже набрано.
- **Список спрашивает у шрифта, что тот рисует.** `emojiSupported(list, measure, single, missing)` оставляет в панели только то, что машина рисует своей одной фигурой. Неудачи у шрифта две, и у каждой свой вопрос. Чего шрифт не составляет, то рисует отдельными глифами, между которыми стоит джойнер `U+200D`, и вместе они близки к двум одиночным emoji: меряет canvas — тот даёт тот же advance, что и ячейка, — и всё, что вышло за полторы ширины, из списка уходит, чем на этом шрифте снимаются 70 наборов из 248 («лицо в тумане», «сердце в огне», бородатый человек, человек с рыжими волосами, лица со стрелками). Полторы, а не две, потому что между двумя ответами есть зазор: семья из четырёх, которую шрифт рисует одна, занимает 1.41 одиночного, а распавшиеся на два глифа начинаются с 1.64. Спрашивается только то, в чём есть джойнер — шире одного глифа в таблице ничего не рисуется. О том, что у шрифта нет совсем никакой фигуры, ширина не говорит ничего: квадратик последнего средства ровно так же широк, как emoji, который он замещает, — про это спрашивается краска. Символ, фигуры которому шрифт не знает, выходит пиксель в пиксель тем же квадратиком, что и кодовая точка, которой нет ни в одном шрифте на любой машине (`U+10FFFF`), и на этом втором вопросе (`emojiMissing`) остаются за бортом 134 строки таблицы без джойнера — всё, что Unicode выпустил после Emoji 12.1, на чём Segoe UI Emoji сборки 19045 молчит («плавящееся лицо», «лицо со слезой», «трещина», зевота и прочее); всего таблица из 1921 строки теряет на этой машине 204. Монохромные по замыслу при этом остаются на месте: проверка по цвету краски и по её разбросу отбросила бы «чёрный квадрат», «чёрный круг», «белое сердце» и «чёрный флаг» вместе с квадратиками, а сравнение с настоящим квадратиком — не отбрасывает. Оба вопроса идут шрифту, а не заводятся списком исключений: более новый шрифт отвечает на них наоборот и возвращает то, что этот теряет. Список один для панели кнопки, для поиска и для двоеточия, поэтому «огонь» больше не выдаёт «сердце в огне»; в тексте этим наборам не препятствуют — принятый с клавиатуры emoji уходит в канал как есть, а шрифт, который их составляет, получает их обратно.
- **Вопрос задаётся при заполнении панели, а не при её сборке.** Спрашивать шрифта о всей таблице при инициализации нельзя: первое знакомство Chrome с символом стоит десятых долей миллисекунды, и 1921 строка складываются в полсекунды занятого потока, который страница тратила бы до первого ответа на любой прочий клик. `emojiListOf(word)` зовёт `emojiSupported` по той выборке, которую панель собирается показать: категорию целиком — до обрезка до `EMOJI_BROWSE_LIMIT`, чтобы откачанная шрифтом строка не оставила в странице пустого места, а ответ на слово — после обрезка до `EMOJI_SEARCH_LIMIT`, поскольку его хвост ранжирован и держит не то, что человек ищет. Одна загрузка панели стоит потому не больше шестидесяти обращений к шрифту, а целая категория — от 31 до 168 миллисекунд при первом её открытии (headless без GPU — до 285; на живом портале первое открытие панели стоило 215.9 мс, а повторный поиск по поле — 0.1 мс). Ответ держится в памяти самой функции (`answers`), поэтому повторное открытие той же категории стоит десятые доли миллисекунды, а вся страница ни о чём не спрашивает, пока панель не открыта. Машину, которая не рисует вообще ничего, — где и `U+1F600` выходит квадратиком, — спрашивать бесполезно: там вопрос о краске снимается целиком и остаётся один вопрос ширины, иначе панель осталась бы пустой.
- **Двоеточие ищет только там, где могло начаться слово.** `:` в начале текста или после пробела и открывающего знака (`« ( [ {` и кавычки), а за ним буквы, цифры и `-`: поэтому «Время:30», «https://awd.ru» и русское «Время:» панель не зовут. `↓` и `↑` идут по сетке с переходом через край и прокруткой, `Enter` и `Tab` берут подсвеченный, `Esc` убирает панель и больше не показывает её над тем же словом, пока оно не изменится; любой прочий символ, прокрутка, изменение размера окна и всякая перестройка частей закрывают её, а `←` и `→` остаются курсору слова — и в тексте части, и в поле поиска. Пока поле поиска пусто, ничему не подсвечено место, и `Tab` уходит из панели, как из любой прочей.
- **Вставка идёт только через редактор.** `deleteText()` слова-короткода с источником `api` и `insertText()` символа с источником `user` — тот же путь, по которому проходит напечатанная буква, поэтому слушатель `text-change` сам перечитывает список сущностей у документа, сам пишет зеркало textarea, сами обновляются счётчики и самим запускается разбивка. Курсор возвращается за вставленный emoji — но только когда часть ещё стоит на месте: запись зеркала могла разрезать её и переложить все поля, кроме первого. Следствие того же пути: emoji, вставленный в конец жирного слова, попадает в его прогон, как в него попадает буква, — канал на emoji ничего не рисует, и список становится шире ровно на то же, на что его расширил бы любой прочий напечатанный там знак.
- **Emoji стоит двух символов — ровно столько, сколько отсчитывает канал.** Индексы совпадают сами (см. «Форматирование текста»): и `String#length`, и `MessageEntities::utf16Length()` считают кодовые единицы UTF-16, поэтому счётчик поля, лимит сообщения и смещения сущностей переносят его без всякой особой арифметики.
- **Разрез части не рвёт emoji.** `wholeCharacter()` — чистая функция в том же разделе, где остальная арифметика сущностей, — отступает назад, пока позиция разреза стоит внутри последовательности: между двумя половинами парного символа, перед `U+FE0F`, `U+FE0E`, `U+20E3` и оттенком кожи, с любой стороны `U+200D` и между двумя региональными индикаторами флага. Её зовут жёсткий разрез `splitIntoParts()` и тот остаток, куда в `manualCut()` и `middleCut()` не попал ни один мягкий разрез; разрез по пробелу, строке и абзацу в ней не нуждается, поскольку всегда стоит рядом с пробелом. Без неё половина символа ушла бы в одно сообщение, а вторая — в следующее.
- **Чего в этом нет.** Оттенков кожи и ручной сборки последовательностей: панель отдаёт ровно те наборы, какие Unicode считает самостоятельными emoji, а не составляет новые из базы и модификатора. Недавних и избранных: для них нужно хранилище — колонка настроек или localStorage. И никакого обращения к Telegram: у Bot API метода поиска emoji нет (`searchEmojis` и `getEmojiKeywords` живут в TDLib и MTProto и читают локальные данные самого клиента), так что своим столом страница пользуется всегда.

### Кнопки-ссылки

Под сообщением канал рисует кнопки с адресами — тем же приёмом канал ведёт читателя на опрос или на анкету. Форма набирает их строками под полем альбома: строка — одна кнопка с надписью и адресом, а весь набор строк отвечает за клавиатуру одного сообщения.

- **Кнопки принадлежат части — как её текст и её альбом.** Строками первой части служит общее поле формы (`#publicationButtonBox`, имена `publicationButtonText[]` и `publicationButtonUrl[]`), а каждая прочая часть получает свои строки в клонированном блоке (`.publication-part-button`, имена `publicationPartButtonText0[]` / `publicationPartButtonUrl0[]` у второй части, `…1[]` у третьей и далее — номер группы на единицу меньше номера части). У первого блока собственная коробка скрыта и выключена (`d-none` + `disabled`) — невыгружаемое поле не уходит на сервер и не сдвигает части списка, ровно как скрытый альбом первого блока.
- **Одну кнопку дают двумя полями, а кнопки — строками.** Ряд — сетка `div.row.gx-2.gy-2.align-items-center.publication-button-row`: поле надписи в `col-sm-4`, поле адреса в `col-sm` (берёт всю ширину, что осталась после надписи и колонки иконок), а колонка `col-sm-auto` держит `bi-arrow-up-short` (`.publication-button-up`), `bi-arrow-down-short` (`.publication-button-down`) и `bi-x-lg` (`.publication-button-remove`) — все три колонки стоят одной строкой, как поля `row gx-4` из `ui-kit`; порог взят `sm`, а не `md`: поле в 33 % ширины и без того тесно при 768, а ниже 576 колонки становятся в столбик — так же, как это делает пример сетки на узком экране. Иконка `bi-plus-lg` (`.publication-button-add`) стоит под рядом справа (`float-end`) и подсказка обтекает её слева; зазор в `ms-3` держит текст от иконки на расстоянии, иначе последняя строка прилипает к её краю. Иконки удаления и добавления — `btn-icon` из `ui-kit/assets/css/main.min.css`, тот же вид, что у кнопки сохранения, и обе стоят у одного правого края рамки: у иконки удаления его задаёт собственная колонка сетки, у иконки добавления — край всплывающего блока. Всплывающая иконка учитывается в высоте только того блока, который владеет собственным контекстом форматирования, поэтому и рамка поля, и коробка части стоят в `display: flow-root` — иначе иконка вылезала бы за нижний обводок белой карточки, а текст начинался бы под ней, а не рядом с ней; подключённому Bootstrap такой утилиты (`d-flow-root`) не хватает, поэтому две коробки называют способ отображения сами. `buttonFieldsOf()` находит поля ряда по классу, а не по позиции, поэтому обёртки-колонки именам и id строк не помеха. `addButtonRow()` клонирует первый ряд коробки, снятый с разметки до всякой правки (`buttonRowTemplate`), `removeButtonRow()` убирает тот ряд, в котором нажата иконка, а последняя строка коробки не убирается: пустая строка и есть сообщение без кнопки, и `updateButtonRows()` прячет всю колонку иконок, пока рядов меньше двух, — адресное поле тогда дотягивается до того же правого края, у которого стоит иконка добавления. Три иконки — `btn-icon`, поэтому каждая стоит 36px (`padding: .5rem .95rem` из правила `.btn-icon.btn` плюс глиф в `1em`), а между ними остаётся пробел слова, перенесённый в разметке, то есть колонка занимает около 124px против 44px одной иконки удаления; ниже 576px колонки встают в столбик, поэтому поле адреса этой потери не чувствует.
- **Порядок строк — это порядок клавиатуры.** `moveButtonRow(button, step)` переставляет ряд внутри той коробки, где он стоит: ряд встаёт перед тем, кто должен остаться позади него, — при подъёме это сам сосед сверху, при спуске ряд за соседом снизу. Соседа нет — ничего не происходит, поэтому у первой строки «вверх», а у последней «вниз» выключены, а не спрятаны: колонка от этого не дёргается, а рука не тянется к тому, чего сделать нельзя. После перестановки `nameButtonRows()` перебивает `id` по новой позиции ряда (метка коробки по-прежнему смотрит на его первую строку), а `name` остаётся тем же списком, поэтому на сервер набор уходит тем же позиционным чтением и в том же порядке, в каком его видит человек, — он же порядок предпросмотра и порядок клавиатуры канала. Перестановка в общем поле переезжает и в коробки частей: обработчик иконок вызывает `syncPartButtons()` тем же порядком, что правка текста общего поля; перестановка в коробке части до общего поля не доходит.
- **Под сообщением не больше десяти кнопок.** `LinkButtons::MAX_BUTTONS` — граница портала, а не Bot API: после десяти кнопок клавиатура становится меню. На ней останавливает добавление и `addButtonRow()` с гаснущей иконкой, и `LinkButtons::assertValid()` — тот же предел держит вручную собранный запрос. В карточку «Лимиты Telegram» число не попало именно потому, что его задаёт портал.
- **Поле кнопок стоит в рамке карточки доски.** `div.kanban-item.publication-field-frame.p-3.rounded-2.bg-white` держит в себе переключатель «ссылки из текста», коробку строк и чекбокс «в каждой части» — тот же обводок `1px solid #dfe5ea` по белому, что у элементов колонки в `ui-kit/tasks.html`. Рамка стоит внутри `.kanban-items`, поэтому её собственное правило перебивает hover доски (`border: 1px dashed #ff7d5c; cursor: move`): иначе рамка под курсором притворялась бы перетаскиваемой карточкой. Селектор повторяет классы доски, чтобы выиграть специфичностью, а не порядком подключения листов. `ui-sortable-handle` элементам `tasks.html` к рамке не перешёл: на странице `sortable` не инициализирован, перетаскивать тут нечего. Класс рамки называется `publication-field-frame`, а не по имени кнопок: той же рамкой обведены и альбомы — поле «Изображения публикации» вместе с «Файлами публикации», и поле альбома каждой прочей части (см. «Открытие на редактирование»), — чтобы любой набор полей формы читался одной группой.
- **Чекбокс «Кнопки-ссылки в каждой части»** (`publicationButtonEveryPart`) виден только тогда, когда в форме больше одной части. Включённый он показывает и включает коробки всех прочих частей, подставив в них строки общего поля (`syncPartButtons`), — дальше набор каждой части правят отдельно. Снятый чекбокс прячет и выключает коробки: их значения остаются в форме, но на сервер не уходят, поэтому такие части уходят в канал без кнопок.
- **Пока чекбокс включён, общее поле задаёт тон всем коробкам.** `syncPartButtons()` стоит и в обработчике чекбокса, и в обработчике `input` общего поля, и в обработчике его иконок, поэтому добавленная наверху строка появляется у каждой части, а правка, внесённая в коробку части, до общего поля не доходит.
- **Переключатель «Ссылки из текста в кнопки-ссылки»** (`publicationLinksToButtons`) стоит наверху слева рамки «Кнопки-ссылки» — `div.form-check.form-switch` ровно в том виде, в каком его рисует вендорный лист: группа отступлена на ширину своего тумблера, а тумблер вынесен назад тем же отрицательным `margin-left`, так что его левый край совпадает с левым краем полей под ним, и многострочная подпись держится столбцом правее тумблера. Никаких `float` тут не нужно: float'ом пустили бы саму группу — и строки кнопок ушли бы под неё. То, что переключатель делает, стоит не строкой под ним, а в поповере самой группы (см. «Подсказка элемента» в «Стили и скрипты страниц»). С записью переключатель не уходит: на сервер встанут те строки, которые он добавил, а его собственное состояние уходит отдельно — в сессию. Пока он включён, любое изменение текста части отодвигает отсчёт (`armLinksToButtons()`), и `fillButtonsFromText()` дописывает адреса этого текста в строки той же части через 10 секунд после последней правки (`__LINKS_TO_BUTTONS_IDLE`). Отсчёт начинается и сразу после включения переключателя — текст, который в форме уже стоит, дожидаться правки не обязан, — и гаснет вместе с ним; снят переключатель — незапустившийся разбор уже не запустится. Ставит отсчёт и `setTextParts()`, поэтому его догоняет и текст, лёгший в поля не с клавиатуры: ручную и автоматическую разбивку, слияние, подстановку с форума и открытие записи на редактирование.
- **Состояние этого переключателя живёт в сессии** — ключ `linksToButtons`, тот же порядок, что у переключателя «Первая строка — в заголовок»: `actionPublications()` решает его через `syncLinksToButtons()` (сессия, которая уже держала переключатель, не даёт ссылке его повернуть; сессия, которая его ещё не держала, принимает `?linksToButtons=1` из адреса), `publicationsUrl()` ставит этот параметр обратно, а `change` тумблера уходит POST на `site/links-to-buttons-save` — тот пишет сессию и отвечает адресом, который JS подставляет через `mirrorUrl`. Ничего на странице ради него не перерисовывается: он говорит о том, что форма сделает с текстом, а не о том, что показать.
- **Поворот тумблера и отсчёт разборки — одно действие.** `watchLinksSwitch(armLinksToButtons)` стоит вместо прежнего отдельного слушателя: обработчик `change` сначала ставит отсчёт, потом пишет сессию, а отказ сервера возвращает тумблер в прежнее состояние и ставит отсчёт заново — иначе он остался бы висеть на состоянии, которое страница отвергла. В очистку формы после сохранения записи переключатель не входит: он настройка чтения, а не поля записи, и перезагрузка страницы приносит его обратно включённым — вместе с отсчётом, который текст с адресами ставит сам.
- **Адресом текста считает `addressesInText()`** — те же голые адреса, что сканирует `findLinks()` (с тем же отрезанным хвостом знаков препинания), плюс адрес каждой `text_link`-сущности части, то и ссылка, спрятанная под словом. Повторяющийся в тексте адрес называется один раз. Ссылки на изображения отбрасывает `IMAGE_ADDRESS` — те же суффиксы (`gif`, `jpe?g`, `png`, `webp` перед `?`, `#` или концом строки), что берёт парсер форума (`ForumPageDomParser`) и что принимает альбом части: такой адрес уже уходит в канал картинкой, и кнопка под ним только повторила бы его.
- **Дописывает, ничего не трогая.** Ряды, набраные вручную, остаются как стоят, а адрес, который в строках этой части уже есть, второй раз не добавляется: `known` строится из `buttonsOf(box)`, пропущенных через `linkAddressOf()`, поэтому набранное без схемы `awd.ru/x` уже считается этим адресом и не повторяется как `https://awd.ru/x`. Убранная вручную кнопка вернётся при следующем изменении текста — переключатель читает текст, а не помнит, что было убрано. Сверх `__BUTTON_LIMIT` строк не встаёт: `writeButtons()` обрезает набор тем же пределом, что и иконка добавления.
- **Надпись кнопки короткая: домен и первый кусок пути** (`buttonLabelOf()`): `www.` отбрасывается, query и фрагмент не зовутся, остаётся `awd.ru/viewtopic.php`. Обрезка идёт по байтам (`__BUTTON_LABEL_BYTES`, он же `LinkButton::TEXT_MAX_LENGTH`), поэтому переключатель никогда не впишет надпись, которую отверг бы `assertValid()`, и режет он на границе буквы, а не посреди кириллицы.
- **У разбитой публикации каждая часть берёт адреса своего текста, поэтому её коробка включается сама:** если частей больше одной и чекбокс «Кнопки-ссылки в каждой части» снят, `fillButtonsFromText()` ставит его в `checked` и вызывает `updateButtonBoxes()` — скрытая коробка выключена, а выключенное поле на сервер не уходит. Дальше действует обычное правило общего поля: правка строки первой части вызывает `syncPartButtons()` и заменяет наборы прочих частей строками общего поля; добавленное переключателем вернётся при следующем изменении текста.
- **Любая перестройка частей рассаживает кнопки заново.** `setTextParts()` после разбивки, слияния, подстановки из форума и открытия записи на редактирование вызывает `syncPartButtons()` и `updateButtonBoxes()`, перебивает у коробки `data-text`/`data-url` и через `nameButtonRows()` — `name` и `id` каждого ряда (`publicationPartButtonText2-0`, `…-1`, …), поэтому строки не остаются вразнобой с частями, а коробка не переживает ту часть, которой уже нет; метка коробки указывает на первую её строку.
- **Списки читаются позиционно.** `SiteController::publicationButtonsFromRequest()` собирает каждой части `LinkButtons::fromPairs()` над двумя её списками — общего поля для первой, клонированных групп для прочих (`partRowGroupsFromRequest()` даёт имена по числу частей) — тем же порядком, каким `imageGroupsFromRequest()` читает альбомы, а `publicationFormatsFromRequest()` — списки сущностей, так что N-й набор отвечает N-й части. Группы, которой в запросе нет (коробка части оставалась выключенной), соответствует пустая клавиатура.
- **Хранятся кнопки в той же строке, что и её текст**: jsonb-колонка `button` со списком пар `[{'text': …, 'url': …}, …]`, а читается и пишется через `LinkButtons` — `fromStored()` переносит любую форму колонки: список, одиночный объект строки, записанной до появления списка, пустой объект, `[]`, строку JSON и `null` строки, записанной до появления колонки. Миграции колонка не потребовала: изменился только её JSON, а не её тип.
- **Половинка пары — не кнопка.** `LinkButtons::assertValid()` на каждом пути записи (`PublicationsService::saveDraft()`, `schedulePost()`, `saveParts()`, `saveFromForm()`) бросает `InvalidArgumentException`, если у строки заполнен только один из двух полей: flash на страницу, ни одна запись не записана. Надпись ограничена 64 байтами — Telegram считает их байтами, а не буквами, поэтому 33 кириллические буквы уже слишком длинно, — адрес 2048 символами и только схемами `http://`, `https://` и `tg://`. Совсем пустой ряд кнопкой не считается и выпадает из набора ещё в `fromPairs()` — ряд с одной половинкой остаётся, чтобы его отверг именно `assertValid()`.
- **В канал кнопки уходят `reply_markup`.** `NutgramChannelClient::toKeyboard()` берёт `LinkButtons::rows()` — не больше `MAX_ROWS` (двух) рядов, набор делится между ними поровну, а лишняя кнопка достаётся нижнему ряду, — и даёт на каждый ряд свой `addRow()`: Telegram рисует ряды клавиатуры одна под другой, а внутри ряда делит ширину сообщения между её кнопками, поэтому двое встают одна под другой, трое — одна сверху и две снизу, а десятеро заполняют два ряда по пятеро. Так же рассажены кнопки у бота, чьей раскладкой мы сверялись: в выгрузке переписки с ним (3327 сообщений с клавиатурой, лежит вне репозитория) все 1383 набора из двух кнопок стоят столбиком, а набора из двух кнопок в единственном ряду там нет ни одного. Пустой список не даёт `reply_markup` вовсе, поэтому сообщение без кнопок отправляется ровно тем же запросом, что и раньше. У текста и у одиночного фото клавиатура стоит в том же вызове (`sendMessage`, `sendPhoto`), альбом же клавиатуры не принимает: `sendMediaGroup` не знает `reply_markup`, поэтому клавиатура части с картинками достаётся первому фото отдельным `editMessageReplyMarkup` — и только когда кнопки есть.
- **Изменение чинит клавиатуру, а не оставляет старую.** `editMessageText` без `reply_markup` оставляет ту клавиатуру, что висела на сообщении, поэтому `editChannelMessageText` отдаёт `toReplacementKeyboard()`: клавиатуру кнопок — когда они есть, пустой `InlineKeyboardMarkup` — когда записи больше нечего показать. Иначе пост, у которого убрали кнопку, остался бы с ней в канале.
- **Превью показывает то, что выйдет в канал.** Правило всего блока «Предпросмотр публикации»: он обязан быть как можно ближе к настоящему сообщению канала, поэтому раскладку любой его части правят вместе с тем, что отправляет сервер, а не одну сторону.
- **Превью рисует кнопки под текстом своей части теми же рядами.** `renderPreviewKeyboard()` берёт то число рядов, что страница выносит из `LinkButtons::MAX_ROWS` (`__KEYBOARD_MAX_ROWS`), и режет набор по той же арифметике рядов, какой пакует клавиатуру `toKeyboard()`, — и кладёт ряды в `div.telegram-preview-keyboard-row` (`display: flex`, `gap: .5rem`), где каждой кнопке (`.telegram-preview-button`) достаётся равная доля ширины (`flex: 1 1 0`). Сами кнопки ненастоящие — `<span>`ы с `textContent`: предпросмотр ничего не открывает и не приносит в страницу чужую ссылку. Пара, заполненная наполовину, не показывается ничем — превью рисует ровно то, что примет Telegram.
- **Запись на редактирование подставляет свои кнопки**: элемент списка несёт их в атрибуте `data-button` (`LinkButtons::toJson()` в `_item_post.php`, `_item_draft.php`, `_item_deleted.php`), `parseButtons()` читает строку — и список новой записи, и одиночный объект старой, — `fillButtons()` рассаживает её по строкам общего поля и по коробкам частей; очистка формы после сохранения убирает их вместе с остальными полями.

### Разбивка длинного текста на части

Одно сообщение Telegram вмещает 4096 символов (`ChannelService::TEXT_MAX_LENGTH`), поэтому поле «Текст публикации» не ограничено `maxlength`, а длинный текст разбивается на части. Разбивка выполняется в JS страницы (`splitIntoParts`) в трёх местах: при подстановке текста из форума, при открытии записи на редактирование и при вводе, пока поле в форме одно.

- В форме остаётся первое поле, остальные клонируются из него; каждое со своей меткой («Часть 2», «Часть 3», …) и счётчиком символов. Имена полей — `publicationText[]`, поэтому на сервер уходят все части. Из одного блока клонируется и поле альбома части (`publicationPartImages[]`), и поле её сущностей (`publicationFormatting[]`), и коробка его кнопок (`publicationPartButtonText{N-1}[]`, `publicationPartButtonUrl{N-1}[]`), так что списков в форме всегда столько же, сколько частей.
- Граница режется по пустой строке, затем по переводу строки, затем по пробелу; если ни одного разделения нет, текст режется жёстко. Часть короче половины лимита не допускается — остаток добирается следующим разрезом.
- Кнопка «Разделить» (`publicationSplitPart`, клиентская, на сервер не уходит) разрезает одну часть на две вручную. Граница — курсор в поле: он подтягивается к ближайшему концу предложения (`. ! ? …` перед пробелом, в пределах `__SNAP_RANGE` — настройка «Поиск границы при ручной разбивке», 600 символов по умолчанию), а если предложения рядом нет — к началу слова, и только потом остаётся там же, где стоит. Без курсора (и когда он у самого края поля) текст делится примерно посередине: сначала по пустой строке, затем по переводу строки, затем по границе слова и лишь потом жёстко.
- Курсор берётся из поля, которое держало фокус последним: клик по кнопке уводит `activeElement` на себя, поэтому поле запоминается на событии `focusin`. Смещение курсора отсчитывается от текста без префикса `Часть N`, обе половинки очищаются от пробелов на разрезе, а пустой или почти пустой текст не разрезается вовсе. Фокус переходит ко второй части в начало текста.
- Рядом с «Разделить» стоят три кнопки ручного разбивания всего текста — «По абзацам», «По строкам» и «По предложениям» (`splitWholeText`, атрибут `data-split-whole`). Каждая берёт текст всех полей, склеенных пустой строкой, и режет его по границе своего рода: абзац — блок, отделённый двойным и более чем двойным переносом строки (`\n{2,}`), строка — участок между любыми переносами (`\n+`), предложение — текст до `.`, `!`, `?` или `…` перед пробелом (тем же правилом, что и привязка курсора в `manualCut`). В отличие от автоматической разбивки части не упаковываются до половины лимита: есть граница — начинается и часть, пусть в ней одно слово. Кусок, который не влезает в сообщение, дорезает `splitIntoParts`, поэтому сервер его принимает. Пустые куски (несколько пустых строк подряд, перенос в начале или в конце) в поля не попадают, а если границ своего рода в тексте нет вовсе, текст остаётся одной частью.
- Выделение текста в любом из полей (мышью или `shift` + стрелки) показывает две плавающие кнопки — «Переместить в предыдущую часть» и «Переместить в следующую часть»; они появляются только когда полей два или больше. Кусок встаёт в начало следующей части либо в конец предыдущей, шов склеивается пустой строкой, а пробел, который выделение унесло с собой, остаётся в исходной части, чтобы слова не слиплись.
- Часть, опустевшая после переноса, из формы убирается, а на её краях (первая «назад», последняя «вперёд») текст получает собственную часть. Кнопки живут в `.publication-selection-actions` (`position: fixed`, узел переносится в `body`), позиция считается от конца выделения: редактор сам говорит, где рисуется его текст, — `caretPoint()` берёт `getBounds()` нулевой ширины на этой позиции и складывает с координатами поля. На сервер при этом ничего не уходит: правятся те же поля `publicationText[]` и `publicationFormatting[]`.
- Кнопка «Объединить» (`.publication-merge-row`, клиентская, на сервер не уходит) стоит под полем каждой части, кроме последней, и сливает её с частью ниже: два поля ввода становятся одним, текст склеивается через пустую строку — тем же швом, что у автоматической разбивки и переноса выделения. Курсор встаёт на место стыка; пустая часть при объединении просто исчезает.
- Ряды кнопок пересчитываются при каждой смене состава частей, поэтому последней части кнопки не достается, а нумерация `Часть N` после слияния расставляется заново. Если склеенный текст перестал вмещаться в одно сообщение, он уходит в обычную автоматическую разбивку (`splitIfNeeded()`).
- Альбом едет вместе со своим текстом. Ручная и автоматическая разбивка одной части оставляет весь её альбом первой половинке — вторая начинается без картинок (`splitPartAtCaret`, `alignGroups` + `splice`). Слияние двух частей складывает их альбомы в один (`unionGroups`): порядок тот же, что у частей, а ссылка, которую показывали обе, называется один раз. Перенос выделения отдаёт альбом опустевшей части соседу, который принял её текст, а часть, родившаяся на краю формы, начинается пустой. Разбивка всего текста («По абзацам» и друзья) режет текст заново и уже не угадывает, какой из новых частей принадлежала ссылка, поэтому все альбомы сводятся в первый (`flattenGroups`). Файлы, взятые пикерами, едут при этом рядом со ссылками тех же частей и подчиняются тем же правилам (см. «Файлы альбома»).
- Чекбокс «Нумерация частей» дописывает в начало каждого фрагмента строку `Часть N`. Префикс входит в текст сообщения, поэтому на него резервируются символы лимита; нумерация проставляется только когда частей две или больше и снимается вместе с чекбоксом. Чекбокс клиентский и на сервер не отправляется. Заголовок части урезает её бюджет так же: символов лимита касается не только текст поля, но и первая строка, которую из него составляет страница (`headingReserve()`, `partLimit()` — см. «Заголовок части»).
- Чекбокс «Равномерно распределить изображения между частями» (`publicationDistributeImages`) на сервер не уходит: он существует ровно для одного действия — раздать альбом первой части по полям всех частей (`distributeImages`), после чего снимается сам, потому что дальше форма отправляет то, что в полях записано. Список режется на непрерывные куски, отличающиеся по размеру не больше чем на одну картинку, лишние достаются первым частям (`groupImages` — та же раскладка, что считает предпросмотр); делятся при этом ссылки и файлы одного альбома вместе, чтобы кусок, попавший в часть, не терял ни своей картинки, ни своего файла. Без раздачи весь альбом остаётся первой части, а остальные части уходят без изображений.
- Под полем альбома каждой части стоят две кнопки — «Переместить изображения в предыдущую часть» и «Переместить изображения в следующую часть» (`moveImageGroup`, атрибут `data-move-album`, клиентские, на сервер не уходят). Кнопка переносит весь альбом поля к соседу — и ссылки, и файлы его пикера: принятые ссылки встают после тех, что в поле-приёмнике уже были (там же `unionGroups`, так что ссылка, которую показывали оба поля, называется один раз), а поле, из которого ушли, опустошается. У последней части «следующей» части нет, поэтому её кнопка скрыта (ряды пересчитываются вместе с рядами «Объединить»), а «в предыдущую часть» у части второй ведёт в общее поле `publicationImages`, которое и есть альбом первой части. Пустой альбом никуда не переносится: случайный клик не должен оборачиваться потерей ссылок соседа. Замечания опустевшего поля — о мёртвых ссылках и о принятых файлах — снимаются вместе со списком.
- При сохранении каждая часть становится самостоятельной записью той же таблицы (`PublicationsService::saveParts`): связь с форумом достаётся первой части, а изображения — каждой из них в своём количестве, ровно сколько лежит в её поле (`imageGroupsFromRequest`), и кнопка — каждой из них своя, ровно какая лежит в её паре полей (`publicationButtonsFromRequest`), и заголовок — каждой из них свой, ровно какой лежит в её поле (`publicationTitlesFromRequest`); `published_at` первой части берётся из поля даты, каждая следующая — позже предыдущей на «Интервал между частями публикации» (настройка `partsOffsetMinutes`, по умолчанию 1 минута; меньше частоты задачи `publish-due` она быть не может — см. «Страницы настроек»). Все части одной публикации записываются одним вызовом репозитория в транзакции (`createPosts()` / `createDrafts()`), поэтому сбой на середине не оставляет половину публикации в таблице. Периодическая задача `publishDue()` выбирает ожидающие посты по возрастанию `id`, поэтому части уходят в канал одна за другой, каждая со своим списком `image_urls`, своей кнопкой и своим заголовком.
- Разбитый текст можно сохранить только как новую запись: при открытой на редактирование записи несколько полей вызывают `InvalidArgumentException`. Сервер проверяет лимит каждой части так же, как и прежде, и не пишет ни одной записи, если какая-то часть не прошла проверку.

В блоке предпросмотра текст всегда выводится в обёртке `.event-content` — по одному блоку на каждую часть, даже когда публикация не разбита. Разбитая публикация уходит в канал несколькими сообщениями, поэтому каждая обёртка повторяет будущее сообщение: свои картинки сверху сеткой альбома (`.publication-preview-album`, см. «Сетка альбома в предпросмотре»), текст части подписью под ними; у части без своих картинок остаётся только текст, а у части без текста — только её картинки, потому что так канал показывает альбом без подписи (см. «Альбом вместо текста»). Текст обёртки раскрашен списком сущностей своей части (`renderFormattedText`): он режется по границам отрезков разметки, а каждый кусок заворачивается во вложенные теги тех сущностей, что над ним стоят. Под полями ввода тот же раздел: общее поле показывает альбом первой части, блок каждой прочей части — свой. Порог подписи (`ChannelService::CAPTION_MAX_LENGTH`, 1024 символа) предпросмотр не режет — текст части показывается целиком, а в канал он уйдёт подписью с продолжением отдельным сообщением. Под текстом обёртки встаёт кнопка её части (`.telegram-preview-button`) — отдельная на каждую строку набора, если оба поля строки заполнены целиком; у публикации без кнопок обёртка выглядит ровно так, как выглядела до появления поля.

### Файлы альбома

У каждого поля альбома стоит второе, дополняющее его, — «Файлы публикации» и «Файлы этой части» (`<input type="file" accept="image/*" multiple>`): картинку в альбом можно взять не только ссылкой, но и файлом с локального компьютера. Отдельного поля в базе у файла нет — он сохраняется на сервере, и в `image_urls` той же части становится одной ссылкой больше, поэтому ни сохранение публикации, ни отправка в канал ничего о загрузке не знают.

- Имена пикеров повторяют имена полей со ссылками: общее поле — `publicationImageFiles[]`, пикер части с номером `N` — `publicationPartImageFiles{N-1}[]` (клонированный блок получает имя на каждой перестройке частей). Скобки в имени обязательны: без них PHP оставил бы в `$_FILES` последний файл множественного выбора. Пикер первого блока формы, как и его поле со ссылками, скрыт и выключен (`d-none` + `disabled`), поэтому на сервер не уходит и части не сдвигает. `SiteController::withUploadedImages()` читает альбомы по именам, а не по порядку пришедших файлов, — пустой пикер одной части не перекладывает файлы соседней.
- Выбранные файлы живут в JS рядом со списком ссылок (`readFileGroups()`, `writeFileGroup()` через `DataTransfer` — другого способа записать `input.files` у скрипта нет) и едут вместе со своим текстом: `moveImageGroup`, `mergeParts`, `splitPartAtCaret`, `splitWholeText`, перенос выделения и раздача `distributeImages` работают с обоими списками, а `albumPictures()` даёт полям превью ссылки и файлы одним списком.
- Проверка мёртвых ссылок до пикеров дела не касается: `probeImage` просит загрузкой только строки, а у файла своей ссылки до сохранения нет.
- Картинка выбранного файла строится через `URL.createObjectURL` и держится в `WeakMap` (`fileUrls`) по одному объекту на файл: превью перерисовывается на каждое нажатие клавиши и не должно каждый раз покупать новый URL.
- Пределы задаёт страница настроек — «Размер загружаемого файла» (`imageUploadMaxMb`) и «Файлов в альбоме части» (`imageUploadLimit`). Форма отсекает лишнее до отправки: крупный файл и всё, что не влезло в лимит альбома, в пикер не попадают и перечисляются в плашке под его полем (`.publication-files-notice`: `Файлы крупнее 10 МБ в альбом не добавлены (N): …`, `Файлов больше 10 в альбоме не будет (N): …`; та же судьба `d-none`, что и у плашки мёртвых ссылок). Сервер перепроверяет то же самое (`validatedUpload`) и бросает `InvalidArgumentException`: flash, ни один файл не сохранён, ни одна запись не записана. Все файлы читаются и проверяются до того, как первый из них покинет временный каталог, поэтому альбом, отвергнувший один файл, не оставляет в хранилище половину своих картинок.
- `storeUpload()` кладёт файл в `@webroot/uploads/publications/ГГГГММ/` под случайным именем (`bin2hex(random_bytes(8))`), а расширение берёт из результата `getimagesize()`, а не из имени, которое придумал браузер: принимаются JPEG, PNG, GIF и WebP (`UPLOAD_IMAGE_TYPES`). Ссылка собирается из `getHostInfo()` и `@web`, то есть картинку отдаёт тот же веб-сервер и на тех же основаниях, что и остальное содержимое `web/`: `docker/nginx/default.conf` уже кэширует её на семь дней и принимает запрос до 32 МБ, `docker/php/php.ini` поднят до `upload_max_filesize=30M`, `post_max_size=32M`, `max_file_uploads=60`, а каталог `app/web/uploads/` в git не попадает.
- Крупный запрос отсекает веб-сервер раньше портала: `client_max_body_size 32m` в `docker/nginx/default.conf` не принимает тело больше 32 МБ и отвечает `413` само, до PHP такой запрос не доходит. Форма на это честна ровно настолько, насколько её слушатель: ответ не JSON, `postForJson` считает его неудачей, и страница показывает «Не удалось обновить списки: HTTP 413». Тело, которое PHP выбрасывает сам как большее `post_max_size`, — случай веб-сервера без своего предела: ни полей, ни файлов портал не получает, и `actionPublicationCreate` смотрит на `CONTENT_LENGTH` при пустом теле, отвечая flash-ом «Запрос больше разрешённого сервером размера…» вместо публикации с пустым текстом.
- Файл крупнее `upload_max_filesize` (30M), но мельче потолка веб-сервера, PHP забирает из запроса сам и помечает `UPLOAD_ERR_INI_SIZE`; `validatedUpload` читает код ошибки первым и отвечает «Файл «…» дошёл до сервера не полностью.» — это единственный способ увидеть предел PHP, потому что предел страницы (`imageUploadMaxMb`, по умолчанию 10M) строже обоих.
- Комментарии в `docker/php/php.ini` — только через `;`. Строка с `#` разбор не отбрасывает, а обрывает его (в сообщении ошибки оказывается скобка из текста комментария), и всё, что написано ниже, до PHP не доходит: пределы остаются системными 2M/8M/20, картинка крупнее 2M не доезжает до портала, а страница настроек между тем позволяет выбрать 10M и не подозревает, что PHP её обещание не выполнит.
- Файл после сохранения от ссылки ничем не отличается: в записи лежит список URL, поэтому повторное открытие публикации показывает загруженную картинку ссылкой на портал.

### Строки альбома и их порядок

Альбом части держат два поля — textarea со ссылками и пикер файлов, — и до этой правки порядок у них был один-единственный: строки поля, а за ними картинки файлов. Переставить файл выше первой ссылки было нечем, хотя канал кладёт первой ту картинку, что стоит в альбоме выше всех. Переключатель «Каждое изображение в своём поле» стоит первым в рамке альбома — над подписью «Изображения публикации», а в блоке части над своей «Изображения этой части», — как тумблер «Кнопки-ссылки в каждой части» первым стоит в рамке кнопок: он раскладывает альбом в список строк — по строке на картинку, — а textarea убирает с глаз.

- **Один порядок на весь альбом.** Строки — не два списка, а один: картинка из пикера и картинка, названная ссылкой, стоят в нём рядом и переставляются одними стрелками. Сами поля при этом остаются собой: строки лишь показывают их одним списком, а вся правка над ними пишется обратно в три поля — textarea, пикер и маску.
- **Textarea скрыта классом и никогда не выключена.** Выключенное поле не уходит в запросе, и альбом доехал бы до канала без единой ссылки; `d-none` забирает его только с глаз, строки в нём живут и при включённом переключателе.
- **Третье поле альбома — маска порядка.** `publicationImageOrder` для первой части, `publicationPartImageOrder[]` для каждой прочей — список идёт позиционно рядом с полями ссылок (`SiteController::maskGroupsFromRequest()`). Токен на картинку: `l` — следующая строка поля, `f` — следующий файл пикера; `fllf` значит «файл, две ссылки, файл». Поле скрытое, и на сервер оно едет вместе с остальным альбомом.
- **Маску слушает сервер.** `withUploadedImages()` сохраняет файлы и передаёт альбом `weaveAlbum()`: тот кладёт ссылки, ставшие картинками, туда же, куда их поставил человек, а не в хвост. Токен поля, которое уже опустело, пропускается, а всё, что ни один токен не назвал, дописывается следом — в порядке своего поля.
- **Маска, которой нет, ничего не портит.** Короткая маска досчитывается обычным порядком (картинка, появившаяся в альбоме после неё, встаёт за остальными), а маска длиннее альбома или с токеном из чужого поля не читается вовсе: альбом сохраняет прежний порядок ссылок, а за ними картинки файлов — ровно то, что делал портал до этой правки. Поэтому устаревшая маска не съедает и не переставляет картинку, которой она не знает, а форма, где переключатель не трогали, уходит на сервер так же, как уходила раньше.
- **В записи порядка уже нет.** Маска — дело формы: в `image_urls` остаётся сам список, уже переплетённый `weaveAlbum()`-ом, поэтому запись, открытая на редактирование, показывает альбом в том порядке, в каком он ушёл в канал, — только как ссылки и с пустой маской. Каналу и правда не нужно знать ничего: он читает `image_urls` сверху вниз, и первым изображением части в него встаёт ровно та картинка, что держали наверху.
- **Чистая половина правила живёт в JS.** `plainAlbumMask`, `isAlbumMask`, `orderAlbum`, `splitAlbum`, `maskOfAlbum`, `moveAlbumPicture`, `removeAlbumPicture` — в том же registerJs-участке, что и прочие чистые функции страницы, и их держат проверки `pubjs/test.js` (раздел «the order of one album»); `setAlbumOrder()` пишет три поля по одному списку, так что порядок не приходится держать в двух местах. Тот же разбор зеркалит PHP: `albumMaskFromValue` / `isAlbumMask` / `plainAlbumMask` / `weaveAlbum`, проверенные отдельным scratch-харнессом над частными методами контроллера.
- **Строка без адреса — ещё не картинка.** Пустая строка стоит за картинками альбома, обе её стрелки выключены, и первый символ переносит её в альбом (в конец, где она и стояла); стёртый адрес возвращает строку обратно. Знак `+` (`bi-plus-lg`) открывает такую строку, `✕` (`bi-x-lg`) убирает картинку из альбома — у файла вместе с тем забирая его из пикера, — а у пустой строки просто закрывает её. Коробка строк при наборе не перерисовывается: каретка стоит в этом поле, и новый узел забрал бы её, — поэтому правка клавиатурой проходит только по выключенным стрелкам (`markAlbumRowFlags()`), а перестановка стрелками (`bi-arrow-up-short` / `bi-arrow-down-short`) перерисовывает и уводит фокус за картинкой. Стрелки на краях альбома выключены, а не сняты, — колонка не дерётся, как и у строк кнопок-ссылок.
- **Порядок этот видно везде.** `albumPictures()` читает `readAlbumOrder()`, поэтому полоса под полем, её слайдер, сетка предпросмотра и счётчики картинок стоят ровно в том порядке, в каком альбом уйдёт в канал (см. «Полоса альбома и её слайдер», «Сетка альбома в предпросмотре»). Раздача «Равномерно распределить изображения между частями» и две кнопки `data-move-album` переносят картинки вместе с их порядком: принятый альбом переписывает маску принимающей части, поэтому переплетение ссылок и файлов после переноса остаётся тем же.
- **Каждый блок части получает свой переключатель.** Клонированный блок parts переименовывает id своего переключателя (`publicationPartAlbumRows{N}`) и метку `for` рядом с ним, а поле маски остаётся списком (`publicationPartImageOrder[]`), поэтому имена сдвигаются вместе с полями ссылок. Перестройка частей (`setTextParts`) переписывает поля альбомов, а вместе с ними забывает пустые строки и перерисовывает строки тех блоков, где переключатель включён.
- **Состояние переключателя не уезжает на сервер.** Он ничего не описывает в записи — он описывает, как показать альбом, — поэтому не хранится в сессии (в отличие от «Ссылки из текста в кнопки-ссылки»), не участвует в адресе страницы и остаётся включённым, когда форма очищается после сохранённой публикации.

### Альбом вместо текста

Часть публикации держится не только на тексте: `PublicationsService::assertPartValid()` требует от неё либо слов, либо собственного альбома, поэтому пустое поле редактора рядом с заполненным полем альбома — это запись, а не отказ. В канал такая часть уходит альбомом без подписи — ровно тем, каким Telegram показывает картинки, которым нечего сказать.

- **Спасает часть её собственный альбом.** Четвёртым аргументом `assertPartValid()` получает список картинок именно этой части: у `saveDraft()`, `schedulePost()` и `saveFromForm()` это `imageUrls` записи, у `saveParts()` — `albums[$index]`, то есть N-е поле альбома, прочитанное позиционно рядом с N-м текстом (`SiteController::imageGroupsFromRequest`), а первой части принадлежит общее поле `publicationImages`. Ссылки и файлы пикера — один список, поэтому альбом, собранный из файлов, спасает часть так же, как альбом из ссылок.
- **Заголовок и кнопки частью не становятся.** Пустое поле без картинок не пишется вовсе: flash «Публикации нужны текст или хотя бы одно изображение.», и ни одна часть публикации не записана — как и при любой прочей отвергнутой проверке. Жирная строка заголовка над пустым текстом и набранный набор кнопок-ссылок сами по себе сообщением быть не могут, и предпросмотр их не показывает: `partIsShown(text, pictures)` берёт частью и текст, и альбом. `saveParts()` снимает пробелы по краям до проверки (`trim`), поэтому поле из одних пробелов — то же отсутствие текста.
- **Подпись уходит отсутствием, а не пустой строкой.** `ChannelService::publishPhotos()` больше не отказывает на пустом тексте, а `NutgramChannelClient::sendPhotoMessage()` и `sendPhotoGroupMessage()` при пустой подписи не ставят в запрос ни `caption`, ни `caption_entities`: пустая строка была бы подписью нулевой длины вместо её отсутствия, а API различает это. Продолжения у такой части нет — резать против `CAPTION_MAX_LENGTH` нечего, и второе сообщение за альбомом не идёт.
- **Предпросмотр рисует часть без текстовой строки.** `partIsShown(text, pictures)` решает, показывать ли часть в блоке «Предпросмотр публикации» (у неё есть слова или свои картинки), а разделитель обёрток опускает `<p class="publication-preview-part">`, когда текста нет: обёртка остаётся своими картинками, как остаётся ими настоящее сообщение канала. Функция чистая и проверена четырьмя проверками `pubjs/test.js`, а placeholder блока теперь появляется только тогда, когда во всей форме нет ни текста, ни альбома.
- **Проверка длины говорит только о длине.** «Текст публикации должен быть не длиннее 4096 символов» («Заголовок с текстом…» — когда заголовок есть) заменил «от 1 до 4096 символов»: нижняя граница перестала быть границей длины, о ней теперь отдельное требование — текст либо альбом.
- **Нумерация частей пустых частей не оставляет.** Чекбокс «Нумерация частей» дописывает в начало каждой части строку `Часть N` (см. «Разбивка длинного текста на части»), и этот префикс уходит на сервер вместе с текстом поля, поэтому часть, размеченная нумерацией, пустой не бывает — альбом без подписи живёт там, где человек оставил поле пустым сам.

### Сетка альбома в предпросмотре

Картинки части стоят над её подписью той же сеткой, какой их кладёт канал: одна во всю ширину сообщения, две рядом, три и четыре — где первая лежит во всю ширину над прочими (двумя или тремя). Альбом длиннее четырёх становится на базовую сетку листа — два столбца квадратных плиток, столько рядов, сколько просит сам альбом, — и показывает все свои картинки: потолок предпросмотра — размер одной медиагруппы канала, десять штук, а не четыре плитки коллажа. Что не влезает в десять, уходит за счётчик `+N` на последней плитке, потому что те картинки отправщик несёт уже вторым альбомом, отдельным сообщением.

- **Раскладку считает чистая `albumLayout(count)`.** Она даёт число плиток, признак того, первой ли из них лечь во всю ширину (`wide`), и число картинок, оставшихся за счётчиком: `1 → {1, false, 0}`, `3 → {3, true, 0}`, `4 → {4, true, 0}`, `5 → {5, false, 0}`, `10 → {10, false, 0}`, `11 → {10, false, 1}`, `0 → {0, false, 0}`. Счёт её держат девять проверок `pubjs/test.js`; `renderAlbumGrid()` строит по ней `div.publication-preview-album.album-N` из `div.publication-album-cell` с `<img>` и `span.publication-album-more`. Раскладку плиткой ведёт лист, а не скрипт: правила держат классы `album-1`, `album-3` и `album-4` в `publications.php`, а `wide` ничем не читается — он описание того же правила, которое держат проверки.
- **Четыре картинки кладёт не квадрат, а плитка вверху и три снизу.** Прежнее «два на два» оказалось нашим правилом, а не каналом: снимок настоящего поста из четырёх фото при ширине содержимого пузыря 430px держит верхнюю плитку 430×281 (1.53:1), три под ней — 141×106 (1.33:1), швы 4px, всю группу — 430×391. Поэтому у `album-4` шесть колонок: первая плитка занимает все шесть с `aspect-ratio: 3 / 2`, каждая из трёх нижних — две с `aspect-ratio: 4 / 3`. На живом портале группа выходит `614x564` (верхняя `614x409`, три нижние `203x152`), то есть отношением высоты к ширине 0.92 против 0.91 у канала, — а не квадратом, каким была прежняя сетка. Тот же ряд держал и альбом длиннее четырёх — это снято: у него свои плитки, а `album-4` больше не принимает на себя чужие картинки.
- **Потолок сетки — десять картинок, и это потолок медиагруппы канала, а не полосы.** Число берётся не с потолка: страница читает `ChannelService::ALBUM_MAX_PHOTOS` рядом с прочими своими границами и отдаёт скрипту переменной `__ALBUM_MAX`, а `albumLayout()` сравнивает с ней длину альбома — тем же числом, каким `publishPhotos()` режет картинки на `sendMediaGroup`, так что предпросмотр и отправщик не разъедутся, если лимит когда-нибудь поменяется. Классов `album-5`…`album-10` в листе нет, и это не забыто, а намеренно: они падают на базовое правило `repeat(2, minmax(0, 1fr))` с квадратной клеткой, то есть на ту же сетку, на которой уже стоят две картинки. У полосы под полем ввода свой отрез — `imagesPreviewLimit` (10, «Превью изображений в форме»), — и к предпросмотру он отношения не имеет: `+N` сетки считает то, что канал унесёт во второй альбом, а не то, что не влезло в полосу.
- **Сетка выходит за пределы отступа обёртки.** `margin: -1rem -1rem .5rem` снимает `p-3` со своих сторон, потому что фото в сообщении канала касается его краёв; скруглены только углы всей группы (сверху, а у `album-only` — со всех четырёх сторон), швы между плитками прямые, `gap: 2px`.
- **Плитка не задаёт ширину своей колонки.** `grid-template-columns: repeat(2, minmax(0, 1fr))`: плитка, у которой нет своего отношения, иначе растягивает колонку сама, и альбом из трёх картинок на живом портале забирал у сообщения 614px левой плиткой — колонки `614px 306px` в коробке тех же 614px, — выталкивая правые за край. Та плитка держала оба ряда и отношения не имела; первая плитка сегодняшнего альбома из трёх стоит `grid-column: span 2` с `aspect-ratio: 2 / 1` и потому размеров не задаёт, а две прочие — квадраты по половине ширины, так что группа выходит квадратом (замерено пробой: `614x615`, верхняя плитка `614x307`, нижние `306x306`). Пол по нулю остаётся стражем на тот случай, если плитка снова перестанет считать себя сама — проба над той же сеткой с `repeat(2, 1fr)` и над вертикальными фото числа не меняет.
- **Одиночная картинка держит свои пропорции.** У `album-1` одна колонка, у её клетки `aspect-ratio: auto`, а у `img` — `height: auto` с `max-height: 18rem` и тем же `object-fit: cover`: выше, чем стоит обёртке, фото не вырастает и обрезается, а не сплющивается.
- **Плитки не кликабельны.** Слайдер альбома живёт на полосе под полем ввода (см. «Полоса альбома и её слайдер»); предпросмотр рисует сообщение и ничего не открывает — как и его кнопки-ссылки.
- **Прежних поверхностей предпросмотра больше нет.** `#publicationPreviewImages` (полоса под карточкой), `#previewCardImgEl` (картинка самой карточки) и `updateSingleImagePreview()` удалены: у альбома одна дорога — в обёртку своей части, поэтому публикация из одной части больше не рисует картинки в стороне от своего сообщения. `renderImagesPreview()` остаётся и служит полосам у полей ввода.

### Полоса альбома и её слайдер

Под полями альбома картинки стоят не прямоугольниками, а полосой `stacked-images` из `ui-kit/avatars.html`: тема рисует её кружками в 48px, наехавшими друг на друга собственным `margin-right: -15px`, в белой обводке и растущими под курсором (`transform: scale(1.15)` вместе с тенью). От страницы — только два правила: `cursor: pointer`, потому что картинка полосы зовёт слайдер, а не просто висит, и `object-fit: cover`, потому что вендорское правило меряет квадратную аватарку, а фото альбома чаще горизонтальное — без подрезки оно сплющилось бы в этот квадрат.

Полосу называет класс `publication-album-strip`; его носят и общее поле (`#publicationImagesPreview`), и блок каждой прочей части. `renderImagesPreview` остаётся за ней одной: она отрезает `imagesPreviewLimit` (10) картинок, и плашка `+N` (`plus bg-danger`) говорит о том, что в полосу не влезло. Предпросмотр сообщения считает свой потолок сам — десять картинок одной медиагруппы (см. «Сетка альбома в предпросмотре»).

Прямоугольных превью на странице больше нет: у предпросмотра была своя пара 120px-поверхностей (`.publication-part-images`, `#publicationPreviewImages`), и обе убраны, потому что полоса стоит в рамке у полей ввода, а предпросмотр обязан быть как можно ближе к настоящему сообщению канала (см. «Кнопки-ссылки», «Сетка альбома в предпросмотре») — значит, картинку он рисует сеткой самого канала, и правится эта сетка вместе с тем, что отправляет сервер, а не одна.

Клик по картинке полосы разворачивает слайдер этого альбома — `carousel slide` ровно той формы, что даёт `ui-kit/carousel.html`: `carousel-indicators`, `carousel-inner` с `.carousel-item` и две стрелки `carousel-control-prev` / `carousel-control-next`. Клик по прочей картинке того же альбома переставляет слайдер на неё, клик по той, на которой он стоит, убирает слайдер, а картинка прочего альбома открывает свой слайдер, закрыв тот, что стоял: смотреть можно только на один альбом. Плашка `+N` открывает слайдер на первой из не влезших в полосу картинок.

Решение, что делать клику (`open` / `slide` / `close`), — чистая функция `stripAction(open, clicked)`, и проверена она в `pubjs/test.js` четырьмя проверками; в обработчике остаётся расставить узлы. Узел слайдера стоит в разметке каждой рамки альбома, а не строится на клик, — клон блока части уносит слайдер вместе с собой. Имя (`publicationAlbumCarousel` + счётчик) узел получает в момент открытия, и это же имя вписывается в `data-bs-target` его собственных указателей и стрелок: два слайдера одной формы не могут отвечать одному id. Экземпляр перед перерисовкой снимается (`dropAlbumCarousel` → `dispose()`), иначе переоткрытый узел застал бы старый экземпляр на уже несуществующих слайдах.

Слайдер держит картинку по высоте, а не по ширине (`max-height: 24rem`, `object-fit: contain`): полоса режет фото в кружок, а смысл слайдера — посмотреть фото, поэтому оно хранит свои пропорции, а то, что оно не взяло, остаётся фоном, который даёт `bg-light-subtle`. У альбома из одной картинки указателей нет, а обе стрелки спрятаны (`d-none`): переставлять нечего, и они только легли бы на само фото.

Слайдер следует за формой. `updateImages()` после любой правки альбома зовёт `refreshAlbumSliders()`: список картинок не изменился — слайдер не трогается (его перерисовка — это новый экземпляр Bootstrap, и дёргать его на каждое нажатие клавиши не за что); изменился — собирается заново на той же картинке, а если альбом под ней усох, на последней оставшейся. Альбом, потерявший все картинки, и блок, ушедший из формы вместе со своей частью, закрывают свой слайдер. `clearEditingState()` закрывает их до перестройки блоков: узел, в котором стоит слайдер, может оказаться тем, который перестройка уберёт со страницы.

### Блок «Удаленные»

Блок «Удаленные» на странице публикаций выводит записи из `publications_deleted` по убыванию `updated_at` (самые свежие сверху). Бейдж статуса отражает фазу удаления: **«Удалено»** — сообщение ещё в канале (`deleted_at` пуст, его ждёт задача `telegram/delete-due`), **«Удалено из канала»** — сообщение уже удалено (`deleted_at` заполнен).

У элементов блока три кнопки-иконки, восстанавливающие запись без открытия формы (логика в `PublicationsService`):

- **«Опубликовать»** (`publishDeleted`) — запись удаляется из `publications_deleted` и добавляется в таблицу публикаций: `created_at` сохраняется, `published_at` и `updated_at` — текущее время, старый `telegram_id` сбрасывается (новое сообщение получит свой id после отправки в канал). Ожидающееся удаление из канала отменяется вместе с архивной строкой
- **«Запланировать публикацию»** (`scheduleDeleted`) — запись удаляется из `publications_deleted` и добавляется в таблицу публикаций с датой из модального окна: `created_at` сохраняется, `updated_at` — текущее время, `telegram_id` сбрасывается; задача `publishDue()` отправит пост в канал по наступлении `published_at`
- **«Перенести в черновик»** (`moveDeletedToDraft`) — запись удаляется из `publications_deleted` и добавляется в таблицу черновиков: `created_at` сохраняется, `updated_at` — текущее время (момент перемещения), `telegram_id` сбрасывается

Редактирование удалённой записи (карандаш или двойной клик) открывает форму «Новая публикация» с источником `deleted` и добавляет два сценария к таблице выше: кнопка **«Опубликовать»** восстанавливает запись как запланированный пост с датой из поля формы, кнопка **«Сохранить»** — как черновик; в обоих случаях архивная строка `publications_deleted` удаляется, а ожидающееся удаление из канала отменяется.

### Блок «Форум»

Страница публикаций идёт рядами на всю ширину: сверху блок «Форум» — белая карточка `card`, в ней две красные карточки одна под другой, «Фильтры» и список топиков; под ним блок превью и формы — та же белая карточка, в ней жёлтые карточки «Предпросмотр публикации» и «Новая публикация», превью над формой; ниже три блока записей («Публикации», «Черновики», «Удалённые»).

Блок «Форума» собран по разметке kanban-доски из UI-kit (`ui-kit/tasks.html`): красные карточки стоят в контейнере `kanban-items ui-sortable`, сам контейнер обёрнут в белую `card mb-4 p-3`, колонка — `kanban-board`. Каждая карточка — `card p-3 border border-danger to-do` с заголовком `icon-box sm … bi-list-task …` и круглым счётчиком справа. В счётчике «Фильтров» — сколько из трёх фильтров включено, в счётчике «Форума» — сколько топиков эти фильтры оставляют (`totals.forum`); второй обновляется вместе с блоком (см. «Бесконечная прогрузка списков»), первый пересчитывает JS по положению тумблеров и слайдера.

Превью и форма устроены так же, только цветами колонки «In Progress» той же доски: одна белая `card mb-4 p-3`, в ней `kanban-items ui-sortable` с двумя карточками `card p-3 border border-warning in-progress` — превью, под ним форма, — с заголовком `icon-box sm … bi-hourglass-split text-warning …`. Счётчика справа в этих заголовках нет: превью и форма показывают одну часть, а не список, считать там нечего. Обычные `card-header` блоков заменены этими заголовками, `card-body` и `card-footer` остались как были (правило `.preview-card > .card-body` продолжает работать — класс переехал на жёлтую карточку).

Вложенные в жёлтые карточки `card-body` и `card-footer` лишены своих отступов (`padding: 0`, у подвала — ещё и `padding-top: 0.5rem` под разделительной чертой): и в красных, и в жёлтых карточках содержимое отодвигает от цветной рамки только `p-3` самой карточки, иначе `card-body` добавил бы сверху ещё по 1rem со каждой стороны, и текст уехал бы от края дальше, чем заголовок.

**Высота карточки «Форум».** Карточка списка топиков (`#pub-forum-block`) стоит на высоту, которая остаётся от видимой части страницы за вычетом шапки: `height: calc(100vh - var(--app-header-height, 64px))`, где `100vh` — та самая видимая часть. Шапка (`app-header` layout'а `dashboard`, приклеена к верху окна) не отдаётся правилу как число, поэтому её измеряет страница: `syncAppHeaderHeight()` пишет её высоту в `--app-header-height` на корневом элементе при инициализации, на каждом `resize` и ещё раз на `load`. Число это не одно на всех ширинах: ниже `lg` в шапку встаёт логотип-марка в 46px, и она становится 70px, а на десктопе её держат поле поиска и аватар по 40px — 64px (отсюда и запасное значение правила, которое к тому же точное, пока JS не отработал). Растёт внутри карточки только коробка списка: `#pub-forum-block > .scroll350` получает `flex: 1 1 0` и `min-height: 0`, — карточка и так flex-колонка (это bootstrap-овский `card`), а flex-элемент без `min-height: 0` не сжимается ниже своего содержимого, и список, в котором сотни топиков, растянул бы карточку дальше всякой формулы. Три блока записей при этом стоят уже не на своих 350px — см. «Высота блоков записей» ниже. Строка заголовка (два тумблера и пара кнопок сортировки) сохраняет свою высоту и на узком окне переносится в несколько рядов, коробке достаётся то, что не взято. Формула задаёт высоту, а не место: над этой карточкой стоит «Фильтры», поэтому её нижний край доезжает до низа окна только когда её верх встал под шапку. Измерено в настоящем окне (`file://` проба на реальных стилях темы и живом OverlayScrollbars, headless Chrome): при 1424×805 шапка 64px, карточка 741px = 805 − 64, коробка списка 659px = 741 − 34px отступа и рамки − 32px строки заголовка − 16px её `mb-3`, и `.os-viewport` те же 659px; при 804×605 шапка 70px, карточка 535px = 605 − 70, строка заголовка свернулась в 102.61px, коробке осталось 382.39px.

**Высота блоков записей.** Карточки «Публикаций», «Черновиков» и «Удалённых» стоят на половину видимой части окна: `height: 50vh` по селектору `.card.publication-list-block` (класс лежит на самой `card`, вне `#pub-*-list`, поэтому AJAX-перерисовка списка его не снимает). Тема держит их коробки прокрутки на `height: 350px`, а это число — доля не всякого экрана: треть окна в 1080px и больше самой видимой карточки в низком. Высоту блоки спрашивают у окна, а не у места под приклеенной шапкой, как её спрашивает карточка «Форума»: тот блок прокручивает документ сам и потому обязан влезать между шапкой и низом, эти же три сидят на странице, которая прокручивается, и место под шапкой уже занят им — считай высота у половины окна отсчитана от верхнего края карточки, а не от шапки. Список получает всё, что останется после строки заголовка и отступов карточки, теми же двумя flex-правилами: `> .card-body` делается колонкой с `min-height: 0`, а `> .card-body > .scroll350` получает `flex: 1 1 0` поверх `height: auto` и своего `min-height: 0` — без последнего коробка, в которой сотни строк, растянула бы карточку дальше всякой доли (см. ту же оговорку про карточку «Форума»). Специфичность селектора — 0,2,0, то есть два класса против одного у bootstrap-овского `.card`, поэтому порядок подключения стилей высоту не перебивает. Блок с одной записью и блок без записей держат свою половину ровно так же, как держали свои 350px. Измерено в настоящем окне (`file://` проба вне репозитория на реальных стилях темы и на разметке трёх карточек с их заголовками, переключателями и `.scroll350`, headless Chrome): при окне 1440×900 — viewport 1424×805, карточка 402.5px, строка заголовка 54.781px, `card-body` 347.719px, коробка списка 315.719px, в ней `.os-viewport` 316px видимых при 720px содержимого, то есть список прокручивается; при окне 1440×700 — viewport 605px, карточка 302.5px, коробка 215.719px. До правки обе карточки выходили по 436.781px при обоих окнах.

Поле ввода текста формы подстраивает высоту под содержимое (не больше 80% видимой области), но не при каждом нажатии клавиши, а через 5 секунд после последнего изменения: измерение высоты требует `height: auto`, на время которого поле схлопывается до двух строк и утаскивает за собой прокрутку страницы.

Блок «Форум» выводит топики форума awd.ru (таблица `topic`, только `login_required = FALSE`) по убыванию `published_at`; к каждому топику — его посты (таблица `post`, связь по `topic_id`) по убыванию `posted_at`. И то и другое начинается с первой страницы: порция задаётся настройками «Тем форума в блоке» (`forumTopicsPageSize`) и «Ответов в теме» (`forumPostsPageSize`, обе по 10 по умолчанию) — `ForumRepository::latestTopicsWithPosts($topics, $posts)` и `ForumRepository::topicPosts` читают их из `publications_setting`; дальше подключается прокрутка (см. «Бесконечная прогрузка списков»). Счётчик у топика показывает всё обсуждение, а не то, что сейчас видно: `postsTotal` приходит из той же выборки. Топики и посты переключаются по отдельности — см. «Сортировка списков».

У топика выводятся полностью, без обрезок: `source_url` (кликабельная ссылка), `title`, `published_at`, `content_text` (полный текст), `content_html` (полный HTML-исходник в свёрнутом блоке `<details>` — экранирован, поскольку исходный HTML форума содержит рекламные скрипты), `image_urls` (все изображения кликабельны). У постов: `number`, `title`, `published_at` (`posted_at`), `content_html`, `content_text` и `source_url` — тоже полностью. Имена и аватары авторов подтягиваются из таблицы `member` (при отсутствии аватара — иконка-заглушка).

Посты не выводятся, пока парсер их не сохранил: у недавно появившихся топиков постов ещё может не быть, тогда у топика отображается счётчик «0», а коробки прокрутки постов у него нет вовсе — догружать нечего.

#### Тред топика в форму

Рядом с кнопкой «Опубликовать» у топика стоят ещё две — «Тред целиком» и «Тред по частям» (`PublicationsUi::threadButtons`, `.forum-thread-btn`). Обе подставляют в форму текст топика и тексты всех постов его обсуждения; различаются они только тем, что делают с этими текстами, когда те пришли: первая складывает их в один, вторая отдаёт каждой сущности свою часть.

- Посты догружаются с сервера в момент нажатия: кнопка уходит POST на `/forum-thread` с `{topic}`, `SiteController::actionForumThread` читает всё обсуждение через `ForumRepository::topicThread`. Ни страниц, ни фильтров, ни статусов эта выборка не знает — в тред идут все строки `post` топика, включая уже опубликованные в канал. Одно правило блока сохраняет: топик, требующий авторизации, остаётся без треда (`t.login_required = FALSE`)
- Из поста в форму идёт только `content_text` — его `number`, заголовок и даты в ответ не попадают
- Сам топик не запрашивается: его текст, заголовок и альбом лежат в атрибутах кнопки «Опубликовать» этой же строки, куда их кладёт `_item_topic` (`threadEntities` достаёт их через `row.querySelector('.forum-publish-btn')`, поэтому кнопке треда не нужно нести тот же текст второй раз)
- Порядок постов задаёт сессия (`publicationsSort.forumPosts`), а не клиент: перевёрнутый блок отдаёт тред от старого поста к новому, первой частью при этом остаётся топик
- «Тред целиком» (`loadText`) собирает заголовок и текст топика и тексты постов через пустую строку в одно поле; не влезший в сообщение текст дорезает обычная разбивка — см. «Разбивка длинного текста на части». Название топика остаётся первой строкой этого поля, а переключатель «Первая строка — в заголовок» перекладывает её в поле «Заголовок» — см. «Заголовок части»
- «Тред по частям» (`setTextParts`) кладёт топик первой частью, а каждый пост — отдельной. За лимит часть не выходит: каждый текст перед раскладкой проходит через `splitIntoParts`, так что сущность длиннее сообщения занимает несколько частей. Включённый переключатель «Первая строка — в заголовок» отдаёт название топика заголовку первой части; прочим частям он его не даёт
- Сущность без текста частью не становится — `saveParts` пустую часть без альбома отвергает. Её изображения при этом не теряются: `threadTexts` фильтрует только тексты, `threadImageGroups` смотрит на все сущности треда, и альбом безымянной сущности доезжает до следующей части того же поля
- Каждой части — альбом её сущности: ссылки топика в первую часть (то есть в общее поле `publicationImages`), ссылки поста — в поле той части, куда лёг этот пост (`writeImages(index, …)`). Сущность, разрезанная на несколько частей, отдаёт весь свой альбом первой из них. Одна и та же ссылка топика и поста в одном поле не повторяется (`unionGroups`), а «Тред целиком» складывает все ссылки треда в общее поле первой части
- Альбом проходит тот же `writeImages`, что и любое заполнение формы, поэтому мёртвые ссылки отсекаются и здесь, и называются в замечании под тем полем, из которого их убрали (см. «Открытие на редактирование»)
- Форма, заполненная тредом, — новая запись: `publicationSource` становится `new`, а `forumEntityType` / `forumEntityId` — `topic` и id топика, так что сохранённые части привяжутся к обсуждению. Открытая на редактирование запись при этом закрывается и снимает свой бейдж
- Кнопок нет у топика без постов (`postsTotal = 0`): его тред — это и есть его текст, который уже отдаёт «Опубликовать»
- Пока тред грузится, обе кнопки молчат (`threadInFlight`), иначе второй ответ перезаписал бы поля формы посреди первого. Ответ не пришёл — flash `Не удалось загрузить тред: …`, и кнопки снова работают

#### Статусы топиков и постов

Топик и пост помечаются строкой в таблицах `publications_topic_map` / `publications_post_map`: `telegram_id IS NULL` — элемент отмечен кнопкой «Просмотрено» (`ForumRepository::markTopicViewed` / `markPostViewed`), заполненный `telegram_id` — опубликован в канале. В блоке «Форум» это бейдж «Просмотрено» или «Опубликовано» с дополнением `TG: <telegram_id>`; элемент без строки в таблице-маппинге считается непросмотренным и неопубликованным.

Если у топика ровно один привязанный пост, топик и этот пост — один и тот же элемент: «Просмотрено» и публикация в канал проставляются обоим, в обе стороны (`ForumRepository::mirrorSolePost` / `mirrorTopicOfSolePost`). Тот же `telegram_id` записывается и в вторую строку, но уже имеющийся `telegram_id` не перезаписывается — пост или топик могли быть опубликованы отдельным сообщением раньше. Топики с несколькими постами не зеркалятся: один обработанный пост ничего не говорит об остальных.

#### Фильтры блока «Форум»

Карточка «Фильтры» стоит над списком топиков в том же блоке «Форум» и содержит три переключателя и два слайдера: «С изображениями» (`withImages`), «С привязанными постами» (`withPosts`), «С ссылками» (`withLinks`), «Кол-во изображений» (`imagesCount`) и «Кол-во ссылок» (`linksCount`; у обоих слайдеров `0` — без ограничения). Фильтры влияют только на выборку «Форума» (топики и их посты), списки публикаций, черновиков и удалённых записей не затрагивают; состояние хранится в нормализованном виде (`SiteController::normalizeForumFilters`).

- «С изображениями» оставляет топики, у которых есть свои изображения или хотя бы один пост с изображениями; списки постов сжимаются до постов с изображениями
- «Кол-во изображений» оставляет топики ровно с `imagesCount` изображений, а среди постов — посты ровно с `imagesCount` изображений
- «С ссылками» и «Кол-во ссылок» считают ссылками адреса `http://` / `https://` в тексте записи — в том же `content_text`, который блок показывает и который уходит в форму. Ссылка, спрятанная в `<a href>` под словом, в тексте адресом не лежит, поэтому в счёт не входит: фильтр оставляет ровно то, что потом читается в полях формы
- Количество адресов считается не на чтении: у `topic` и `post` рядом стоит колонка `links_count`, которую пишет парсер (`ForumRepository::saveTopic()` / `savePost()` считают `preg_match_all('~https?://~')` по тому же `content_text`, что и записывают), и выборка сравнивает целое число строки. Миграция `m260930_000001_add_links_count_to_forum_tables` заводит столбец обычным `integer` и считает им уже сохранённый текст — дальше база над ним ничего не вычисляет. Считать адреса на чтении означало бы пройтись регуляркой по тексту каждого поста каждого топика (замер на 844 тысячах постов — десятки секунд на счётчик топиков)
- «С привязанными постами» — правила ниже
- Условия счётчиков и переключателей читает и пост, которым топик держится на странице: `postImageFilterSql()` и `postLinkFilterSql()` дают их и списку постов (строка `bp`), и правилу топика (строка `fp`), поэтому помеченный «Просмотрено» топик не остаётся в выборке из-за поста, который фильтр не пустил. До этого такой пост держал топика, сам в список постов не попадал, и строка выходила с «💬 0» и ни одним постом. `topicFilterSql()` общая у `latestTopicsWithPosts()` и `countTopics()`, так что счётчик на заголовке карточки, окно прокрутки и сам список говорят об одном наборе строк

Синхронизация фильтра с сессией и URL: состояние живёт в сессии (`forumFilters`) и является единственным источником истины, адресная строка — его зеркало. Так же держат своё состояние оба переключателя формы — «Первая строка — в заголовок» (ключ `titleFromFirstLine`, см. «Заголовок части») и «Ссылки из текста в кнопки-ссылки» (ключ `linksToButtons`, см. «Кнопки-ссылки»).

- Любое изменение фильтра (переключение тумблера, отпускание слайдера) уходит на `site/forum-filter-save`, сохраняется в сессию и перезапрашивает блоки по ajax
- Ответ сервера содержит `url` — адрес, соответствующий сохранённому состоянию (`SiteController::publicationsUrl`, она же учитывает порядок списков, порядок топиков по длине текста и оба переключателя формы, см. «Сортировка списков»), отрендеренный блок «Форум» и `totals` того же состояния; JS подставляет адрес в строку браузера через `history.replaceState` (`mirrorUrl`) и подменяет содержимое блока, целиком страницу не перезагружает. `totals` идут в `resetPaging` (сколько ещё догружать) и в счётчик топиков на заголовке карточки
- При открытии страницы активный фильтр сессии приоритетен над GET-параметрами: перезагрузка или переход по ссылке не «включают» фильтр обратно. Если в сессии активного фильтра нет, она принимает параметры запроса. Когда URL не совпадает с состоянием сессии, `actionPublications` отвечает 302 на адрес из `publicationsUrl()`; сравнение идёт по нормализованным значениям фильтров, порядков и двух переключателей формы (`viewStateDisagreesWithSession()`), поэтому цикл редиректов невозможен
- Сессию очищает только кнопка «Очистить» в карточке фильтров (`site/forum-filter-clear`); порядок списков она не трогает — адрес после очистки остаётся с параметрами перевёрнутых блоков

Правила фильтра «С привязанными постами» (`ForumRepository::latestTopicsWithPosts` при `$withPostsOnly = true`):

1. у топика нет привязанных постов в таблице `post` — топик не показывается
2. топик непросмотрен и неопубликован — показываются все его привязанные посты, независимо от того, просмотрены или опубликованы они
3. топик просмотрен или опубликован, но среди его постов есть хотя бы один непросмотренный и неопубликованный, который к тому же проходит фильтры шапки, — показываются все посты топика
4. топик не показывается, если и он сам, и все его привязанные посты просмотрены или опубликованы — и так же, когда сам топик помечен, а среди его непросмотренных постов не осталось ни одного, что проходит фильтры шапки

Обработанные посты из правил 2 и 3 приходят в выборку со своими статусами, поэтому у них выводятся бейджи «Просмотрено»/«Опубликовано» и `TG: <telegram_id>`. Лимит «первые N постов» (`forumPostsPageSize`) сохраняется и при активном фильтре. Счётчик топиков при этом не обещает непустой список под каждой строкой: непросмотренный топик остаётся в выборке по своему статусу, и если под фильтр шапки прошёл он сам (скажем, его собственный альбом ровно из двух картинок), а его посты — ни один, строка стоит с «💬 0». У помеченного топика такого больше нет — он держится только постом, который фильтрует сама страница. Верх ползунка «Кол-во изображений» — настройка `imagesCountFilterMax`, верх ползунка «Кол-во ссылок» — `linksCountFilterMax` (обе по 100 по умолчанию); каждая из них одновременно и потолок, который принимает сервер: значение выше своей настройки `normalizeForumFilters()` снижает до неё же. Топик с единственным постом исчезает из выборки сразу после обработки любой из двух сторон — см. «Статусы топиков и постов».

### Сортировка списков

Блок «Публикации» выводит записи по убыванию `published_at`, блок «Черновики» — по убыванию `updated_at`, блок «Удаленные» — по убыванию `updated_at` (самые свежие сверху). Блок «Форум» сортируется по двум полям сразу: топики — по `topic.published_at`, посты внутри топика — по `post.posted_at`.

В шапке каждого из трёх блоков записей стоит переключатель «Сначала старые» (`.form-check.form-switch`, id `pubSortPosts` / `pubSortDrafts` / `pubSortDeleted`), в шапке «Форума» — два: «Сначала старые топики» (`pubSortForumTopics`) и «Сначала старые посты» (`pubSortForumPosts`); оба стоят в правой части заголовка, перед круглым счётчиком топиков `#forumTopicsTotal`, и вместе с ним лежат в одном `d-flex flex-wrap align-items-center gap-3`, поэтому на узкой ширине переносятся на вторую строку заголовка, а не вылезают за карточку. Переключатель разворачивает порядок своего списка: выборка идёт тем же `ORDER BY`, но по возрастанию, и вторичным ключом тоже по возрастанию (`PublicationRepository::order`, `ForumRepository::latestTopicsWithPosts`), поэтому страницы не перекрываются и в обратном порядке. Порядок относится к одному списку — остальные продолжают показывать то, на что читатель смотрел.

Рядом с этими двумя переключателями в шапке «Форума» стоит пара кнопок «Сначала короткий текст» / «Сначала длинный текст» (`btn-group` из двух `input.btn-check` с их `label.btn-outline-primary`, id `pubForumTextAsc` / `pubForumTextDesc`): она разворачивает список топиков по длине их собственного текста. Кнопки именно пара — нажатие одной снимает другую, а повторное нажатие уже нажатой убирает сортировку вовсе, и список возвращается к порядку по дате. Задевает это только топики: посты каждого обсуждения продолжают идти в своём порядке дат, иначе тред перестал бы читаться как тред. Порядок задаёт `ForumRepository::latestTopicsWithPosts` параметром `$textOrder` — `'asc'` и `'desc'` дают `ORDER BY t.text_length …, t.id …` тем же направлением, любое иное значение оставляет `ORDER BY t.published_at … NULLS LAST, t.id …`. Вторичным ключом идёт тот же `t.id`, повёрнутый вместе с сортировкой, поэтому страницы, которые догружает прокрутка блока, не перекрываются и в этом порядке, а `countTopics()` остаётся тем же числом: сортировка не меняет набор строк, только порядок.

- Порядок хранится в сессии (`publicationsSort`, значения — реальные булевы `posts`/`drafts`/`deleted`/`forumTopics`/`forumPosts`), нормализует его `SiteController::normalizePublicationsSort`; всё, что не `true` и не `'1'`, оставляет список по умолчанию. По умолчанию это прямой порядок, а настройка «Порядок записей по умолчанию» (`blockOrderDefault`) переворачивает его у того, кто ещё ничего не переключал; переключатель в сессии важнее настройки
- Переключатель уходит POST на `/publication-sort` с `{block, oldest}`; сервер отвечает блоком, к которому переключатель принадлежит, отрисованным с первой страницы нового порядка, и `applyBlocks` подменяет только его разметку. Имя переключателя и имя блока — не одно и то же: `forumTopics` и `forumPosts` перерисовывают один и тот же блок `forum` (`SiteController::PUBLICATIONS_SORT_BLOCKS`)
- Так как лимит постов топика берётся в том же порядке, перевёрнутый блок «сначала старые посты» отдаёт самые старые посты обсуждения, а не самые свежие в обратном порядке; то же касается топиков
- Записи без даты остаются в конце списка при обоих порядках (`NULLS LAST` у даты топика и поста)
- Прокрутка блока после переключения продолжает уже новый порядок: `actionPublicationPage` читает сессию там же, откуда и первую страницу
- Перерисовка блока после переключения сбрасывает и остановку после сбоя: `resetPaging` снимает `failed`, и блок снова догружается до конца нового списка
- Если запрос о порядке не прошёл, переключатель возвращается в прежнее положение и показывает flash: список-то остался прежнего порядка, и положение тумблера не должно врать
- Порядок переживает перезагрузку страницы (он в сессии) и зеркалится в адресную строку, как фильтры «Форума»: перевёрнутый список даёт параметр `?postsOldest=1` / `?draftsOldest=1` / `?deletedOldest=1` / `?forumTopicsOldest=1` / `?forumPostsOldest=1`, а `publicationsUrl()` собирает из них вместе с фильтрами один адрес — `site/publications?withImages=1&postsOldest=1`
- Ответ `/publication-sort` несёт этот `url`, и JS подставляет его через `history.replaceState`; ответ `/publication-page` адреса не имеет, поэтому прокрутка списков в строку браузера не лезет
- При открытии страницы перевёрнутый список сессии приоритетен над параметрами адреса (перезагрузка не «возвращает» порядок), пустая сессия принимает GET; когда адрес не совпадает с состоянием, `actionPublications` отвечает 302 на `publicationsUrl()`
- Длина текста считается не на чтении: у `topic` рядом с `links_count` стоит колонка `text_length`, которую пишет парсер (`ForumRepository::saveTopic()` считает `mb_strlen()` по тому же `content_text`, что и записывает; `char_length()` PostgreSQL даёт то же самое число), и выборка сравнивает целое число строки. Миграция `m261001_000001_add_text_length_to_topic` заводит её обычным `integer NOT NULL DEFAULT 0` и считает им уже сохранённые тексты. Считать длины на чтении означало бы пройтись по тексту каждого топика до того, как `LIMIT` отбросит их большинство: на 58 922 топиках прогретая выборка с `char_length(content_text)` стоит 1,2 с, с готовым числом — 0,17 с
- Порядок пары хранится в сессии ключом `forumTextOrder` — `''` (без сортировки), `'asc'`, `'desc'`; `SiteController::normalizeForumTextOrder()` оставляет `'asc'` и `'desc'` как есть, а всё остальное читает как `''`. `syncForumTextOrder()` при открытии страницы отдаёт приоритет сессии, которая уже держала порядок (ей не мешает ссылка с другим порядком), а пустая принимает `?forumTextOrder=asc|desc` из адреса; `publicationsUrl()` возвращает параметр в строку браузера, и несовпадение адреса с сессией уходит 302 — на том же сравнении `viewStateDisagreesWithSession()`
- Нажатие кнопки уходит POST на `/forum-text-order-save` с `{forumTextOrder}` (пустое значение — снятая сортировка): сервер пишет сессию и отвечает блоком `forum` с первой страницы нового порядка, `totals` того же состояния и `url` для `mirrorUrl`. Соседнюю кнопку снимает сам браузер (`btn-check` живёт до запроса), поэтому при отказе обе возвращаются в положение, которое показывала страница, и показывается flash — список-то остался прежнего порядка

### Бесконечная прогрузка списков

Блоки «Публикации», «Черновики», «Удаленные» и «Форум» показывают не весь список, а первую страницу: `publicationPageSize` записей (настройка «Записей в блоке», 10 по умолчанию; «Форум» к ней добавляет свои две — см. «Блок «Форум»»). Сколько строк в списке всего, `actionPublications` отдаёт вместе с блоками (`totals`), поэтому браузер знает, есть ли что догружать.

- Прокручивается сам блок (его `.os-viewport` внутри `.scroll350`), а не страница. Когда до нижнего края остаётся не больше `__SCROLL_EDGE` (настройка «Отклик прокрутки», 80px по умолчанию), `loadNextPage` отправляет POST на `/publication-page` с `{block, offset}`
- Сколько прочитано в блоке, считается по строкам его собственного селектора (`__BLOCK_ROWS`): `.activity-log` у трёх списков записей и `.thread` у «Форума». Строка «Форума» содержит вложенные посты, поэтому число строк списка и число показанных элементов — разные величины
- Прокрутка не всплывает, поэтому слушатель на странице один — `scroll` на `document` в фазе перехвата; свой блок находится по `closest('.scroll350')` (`pagedBlockOf`). Прокрутка чужого блока, обсуждения внутри топика или окна страницы запроса не вызывает
- `actionPublicationPage` берёт следующий кусок списка через `PublicationsService::posts()` / `drafts()` / `deleted()` с `LIMIT`/`OFFSET` и возвращает уже отрендеренные строки: элементы живут в отдельных partials `_item_post` / `_item_draft` / `_item_deleted` / `_item_topic` / `_item_reply`, поэтому на клиент приходит разметка, а не записи. Кусок берётся в том порядке, который сейчас показывает блок (см. «Сортировка списков»)
- Ответ приносит новый `offset` и `total`; `offset >= total` — запросов больше нет. Ответ сервера — единственный источник того, сколько прочитано: JS не считает страницы сам
- Ошибка догрузки останавливает блок (`failed`) и показывает flash один раз: читатель стоит на том же нижнем крае, и повторный запрос уходил бы на каждый пиксель прокрутки
- Любое изменение данных (сохранение формы, публикация, перемещение, удаление) перезапрашивает блоки целиком: `applyBlocks` возвращает первую страницу и сбрасывает состояние прокрутки (`resetPaging`) по `totals` того же ответа
- Пустое состояние блок рисует вне списка элементов (`_block_*` выводит либо `<p>`, либо набор `_item_*`), поэтому догрузка не может продублировать «Публикаций пока нет»

#### Два уровня прокрутки в «Форуме»

«Форум» догружается двумя уровнями, и каждый спрашивает только своё:

- Топики идут через тот же `/publication-page` с `{block: 'forum', offset}`: `actionPublicationPage` вызывает `ForumRepository::latestTopicsWithPosts` с `OFFSET`, а `total` приносит `ForumRepository::countTopics()` — сколько топиков оставляют текущие фильтры
- Посты одного топика идут на `/forum-post-page` с `{topic, offset}` и возвращают только посты этого обсуждения (`ForumRepository::topicPosts`). Ответ имени блока не носит, поэтому ответ с чужим `topic` отбрасывается
- Обсуждение живёт в своей `<div class="thread-replies">` с `max-height` и `overflow-y: auto` (`app/web/ui-kit/assets/css/publication-editor.css`, `overscroll-behavior: contain`): первая порция постов (`forumPostsPageSize`) видна, остальные открываются прокруткой коробки. Полоса у неё обычная, браузерная: OverlayScrollbars навешивается только на `.scroll350` и только на document-ready, а коробки приходят после. Правило лежит именно в этом файле, а не в `app/web/css/site.css`: страницу ведёт layout `dashboard`, который подключает `DashboardAsset` и `PublicationEditorAsset`, а `site.css` входит только в `AppAsset` страниц `main` — правило, записанное туда, на портале не применяется
- Положение обсуждения JS не хранит — `data-topic`, `data-offset` и `data-total` лежат в разметке самой коробки, которую принёс сервер. Перерисовка блока фильтром или переключателем порядка возвращает каждое обсуждение на первую страницу нового набора бесплатно, а топик без постов остаётся без коробки
- Слушатель `scroll` сначала смотрит на `closest('.thread-replies')` и только потом ищет блок по `closest('.scroll350')`: коробка постов сидит внутри списка топиков, и без этого порядка её прокрутка читалась бы как нижний край списка — один жест грузил бы и топики, и посты
- Сбой считается раздельно: `failed` коробки глушит только её обсуждение, `failed` блока — только список топиков; `busy` у коробки свой, на DOM-узле (`__busy`), и в `paging`-состояния блоков не попадает
- Прокрутка в середине коробки и прокрутка обсуждения, которое показано целиком, запроса не вызывают: тот же `__SCROLL_EDGE`, что у блоков

Ограничение выборки `LIMIT`/`OFFSET`: если список меняется между догрузками одной страницы (появился новый пост, запись удалили), строка может повториться или оказаться пропущенной. Перезагрузка страницы и любое действие формы сбрасывают чтение на первую страницу. ### Статус записи в списке

Бейдж строки блока «Публикации» печатает `PublicationsUi::statusBadge()`, и говорит он о канале, а не о часах: «Опубликовано» (`bg-success`) — только у записи с заполненным `telegram_id`, тем номером сообщения, который Telegram вернул при отправке. Запись без него, у которой `published_at` уже наступил, стоит «В очереди» (`bg-warning text-dark`) — срок прошёл, а сообщения в канале нет. У записи с будущей датой — «Запланировано» (`bg-info`). До этого «Опубликовано» включало и наступившую дату, поэтому запись, которую задача не смогла отправить, выглядела отправленной, а канала в это время ничего не показывал.

Кнопка «Опубликовать» есть у обеих неотправленных строк — и у запланированной, и у застрявшей в очереди; её нажатие в канал ничего не шлёт, оно только передвигает `published_at` на текущее время, так что повторный клик очередь не удваивает.

Очередь (`publishDue()`, задача `telegram/publish-due`) берёт посты с пустым `telegram_id` по возрастанию `id` и на каждую запись тратит три попытки: между ними пауза растёт (`2 с × номер попытки`), а если API сам попросил подождать (`retry_after` — так отвечает перегруженный канал), ждёт по его слову, но не дольше 10 с, чтобы проход не перешагнул через своё расписание. Запись, которая не ушла и после третьей попытки, логируется одной строкой с числом попыток, пропускается, и очередь занимается следующими; `telegram_id` у неё остаётся пустым, поэтому следующий проход берёт её снова. Терминального состояния у очереди нет — «В очереди» может стоять и сутки, пока не вернётся связь с Telegram или пока запись не правят. Один случай очередь отпускает раньше, чем он выглядит сбоем: клавиатура альбома доклеивается к первому фото отдельным запросом, и если канал отвечает на него `message is not modified`, этот набор кнопок на сообщении уже стоит — альбом в канале есть, а до записи это не дошло. Отказом перемены, которой не требовалось, `NutgramChannelClient::sendPhotoGroupMessage()` считает отправку состоявшейся и отдаёт номер сообщения, запись получает `telegram_id` и из очереди уходит — а не просит у канала тот же альбом каждые пять минут.

### Метки времени в списках

Каждый элемент списка показывает все даты, которые есть у его строки в БД (`PublicationsUi::dateMeta`): в «Публикациях» — `published_at` с подписью «Опубликовано» у записи, у которой есть `telegram_id`, и «Запланировано» у той, у которой его нет (подпись держится за канал, а не за дату, — см. «Статус записи в списке»), затем `created_at` («Создано») и `updated_at` («Обновлено»); в «Черновиках» — только `created_at` и `updated_at`, поскольку колонки `published_at` у `publications_draft` нет; в «Удаленных» — все четыре, добавляется `deleted_at` («Удалено»), а дата публикации подписывается по тому же признаку, что и в «Публикациях»: запись могла попасть в архив до отправки в канал.

Пустое значение своей строки не выводит: `deleted_at` пуст, пока сообщение ещё ждёт задачи `telegram/delete-due`, и тогда остаётся только бейдж «Удалено». Значения в разметке остаются в UTC (атрибут `data-utc`), клиент подставляет их в часовом поясе пользователя (`renderUtcTimes`, `.utc-time`) — как и в остальных блоках страницы, и в том формате, который задан настройкой «Формат даты и времени» (см. «Страницы настроек»).

### Страницы настроек

Меню портала (`app/views/layouts/dashboard.php`) ведёт на две страницы настроек: «Настройки публикаций» (`/settings`, `SiteController::actionSettings`, вид `app/views/site/settings.php`) и «Настройки парсера» (`/parser-settings`, вид `parser-settings.php`). Пунктов-заглушек, которые вели в никуда (`href="#!"`), в боковом меню больше нет — ссылкой стало только то, что действительно открывается; в выпадающем меню пользователя такой пункт ещё живёт (см. «Профиль» в шапке).

#### Настройки публикаций

Каждая величина описана один раз — в схеме `PublicationSettingsService` (`app/shared/Settings/Service/PublicationSettingsService.php`): подпись поля, тип, границы, единица измерения и подсказка под полем. Из той же схемы миграция `m260925_000001_create_publications_setting` сеет таблицу `publications_setting` (строка `code` → `value` на каждую величину), поэтому дефолты приложения и дефолты базы не могут разойтись.

Первые три и `scrollEdgePx` правят прокруткой списков (см. «Бесконечная прогрузка списков»), `imageProbeTimeoutMs` и `splitSnapRangeChars` — поведением формы (см. «Открытие на редактирование» и «Разбивка длинного текста на части»), `imagesPreviewLimit` — числом превью под полем альбома, `imageUploadMaxMb` и `imageUploadLimit` — файлами, которые альбом берёт с компьютера (см. «Файлы альбома»), `imagesShownLimit` — числом картинок, которые рисует элемент списка (`PublicationsUi`), `scheduleMinuteStep` и `scheduleHorizonHours` — шагом минут и дальностью выбора даты публикации, `imagesCountFilterMax` и `linksCountFilterMax` — двумя ползунками фильтра «Форума», остальные — тем, что следует из их подписей.

- Числа читаются через `all()`, `value()` и `intValue()`: значение, которого в таблице нет или которое вышло за границы, возвращается границей (`normalize()`), а неизвестный вариант выбора — дефолтом, поэтому вызывающему коду не надо проверять то, что он прочитал. Писание наоборот: `save()` отвергает первую же неподходящую величину `InvalidArgumentException`-ом, страница показывает flash и не сохраняет ничего. Один запрос читает таблицу один раз — значения держатся в кэче сервиса.
- «Интервал между частями публикации» упирается в пол, которого у него в схеме нет: части не могут уходить в канал чаще, чем задача, которая раз за разом смотрит в очередь на публикацию. Частота этой задачи живёт в `.env` (`TELEGRAM_PUBLISH_CRON_SCHEDULE`), `cronIntervalMinutes()` вычитает её из расписания (`*/n`, `*`, список минут — с учётом перехода через полночь; нераспознанное расписание даёт 1), а на странице она только показана: карточка «Очередь публикации» печатает расписание как есть, а подсказка поля — нижнюю границу. Тот же пол держит и `saveParts()`, который сдвигает `published_at` частей, и форма, которая его отправляет: записанное ниже границы значение при чтении поднимается до границы, а попытка сохранить его отвергается.
- «Порядок записей по умолчанию» задаёт, как стоят блоки у того, кто ещё ничего не переключал; переключатель в шапке блока, записанный в сессию, важнее настройки (см. «Сортировка списков»).
- «Формат даты и времени» — один формат на весь портал: `DATE_FORMATS` переводит его в токены моментума, которыми говорит выбор даты и клиентская подстановка времени из UTC (`utcToPickerValue`, `renderUtcTimes`), а PHP-виды форматируют даты тем же значением через `asDatetime('php:…')` (смена формата потому не требует правки ни одной страницы).
- Карточка «Лимиты Telegram» перечисляет числа, которые задаёт сам Telegram, а не портал (`telegramLimits()` над константами `ChannelService` и `LinkButton`): 4096 символов текста сообщения, 1024 подписи, 255 описания канала, 10 картинок в альбоме, резерв под строку «Часть N» и пределы кнопки-ссылки — 64 байта надписи и 2048 символов адреса. Они показываются и не редактируются: длиннее лимита текст не примет API, а не это приложение.

#### Настройки парсера

Страница делит `parser_config` на две карточки. «Запрос к форуму» — поведение HTTP: ожидание ответа страницы, число повторов, пауза перед повтором (мкс), бюджет редиректов, коды ответов, на которые запрос повторяется, адрес входа на форум, страниц на одну сущность и часовой пояс источника («Диапазоны источников» — `base_url`, `t_from`, `t_to` и активность каждой строки конфигурации).

- Числовые величины замкнуты в `ParserSettingsService::bounds()` (1–300 секунд, 0–10 повторов, 0–5000000 мкс паузы, 0–20 редиректов, 1–100000 страниц), коды ответов читаются списком через запятую и проверяются на формат статуса HTTP, адреса — на `http(s)`, часовой пояс — по `DateTimeZone::listIdentifiers()`, диапазон сущностей — на неотрицательность и `t_from <= t_to`. Неподходящее значение — `InvalidArgumentException` до первой записи, flash на страницу.
- Восемь «поведенческих» колонок относятся ко всему парсингу сразу, а не к одной строке конфигурации, поэтому форма пишет их во все строки одним `UPDATE`, а сервис читает из первой (`ForumRepository::parserTunables()`). Пока таблица пуста, `tunables()` отдаёт `ParserSettingsService::DEFAULTS` — те же числа, что сеет миграция `m260925_000002_add_parser_tunables_to_parser_config`.
- Отсюда эти числа попадают туда, где раньше были зашиты: `ForumHttpClient` получает таймаут, повторы, паузу, адрес логина, бюджет редиректов и список кодов, парсеры страниц — часовой пояс сайта (`ForumPageDomParser::$siteTimezone`), обходчики постов и альбомов — потолок страниц (`maxPages`). И web- и console-состав (`app/config/web.php`, `app/config/console.php`) собирают их одинаково, а `ParserSettingsService` — синглтон, так что один проход читает таблицу один раз.

#### Секреты и режим отладки

`cookieValidationKey`, `YII_DEBUG` и `YII_ENV` из кода убраны и живут в `.env`: `COOKIE_VALIDATION_KEY` (генерация — `php -r "echo bin2hex(random_bytes(32));"`), `YII_DEBUG`, `YII_ENV`; compose прокидывает их в контейнер, а `app/web/index.php` и `app/yii` читают через `getenv()`. Без этих переменных приложение работает как production, а без ключа Yii не подписывает cookies сессии и CSRF, то есть не принимает ни один запрос, который их несёт. Ни на одной странице настроек эти значения не показываются — страница настроек не место для секретов.

В журнал секреты не попадают по той же причине: у обоих `FileTarget` (`app/config/web.php`, `app/config/console.php`) стоит `logVars => []`. Без него Yii дописывает к выгрузке дампы `$_GET`, `$_POST`, `$_FILES`, `$_COOKIE`, `$_SESSION` и `$_SERVER`, а в console-процессе `$_SERVER` — это всё окружение контейнера, то есть токен бота и пароли базы и форума; в запросе туда же попали бы пароль из формы входа и cookies сессии. Отладочный контекст в этих дампах не нужен: причины сбоев пишутся в текст самой записи (`{"id":24,"error":"cURL error 7: …"}`, `topic_id`, счётчики статистики).

### Стили и скрипты страниц

Ничего не собирается: каждый файл лежит в `app/web/` и подключается bundle-ом Yii — `AppAsset` для старой разметки (`_head.php`: вход, «О программе», «Контакты», страница ошибки), `DashboardAsset` для порталовых страниц (`dashboard.php`), `PublicationEditorAsset` поверх последнего для редактора публикаций. Две раскладки не пересекаются, поэтому на одной странице `AppAsset` и `DashboardAsset` не встречаются.

- **jQuery на странице ровно один, и это копия из ui-kit.** `assetManager.bundles` в `app/config/web.php` переопределяет `yii\web\JqueryAsset`: вместо `@bower/jquery/dist` он публикует `app/web/ui-kit/assets/js/jquery.min.js` (в `publishOptions.only` — один этот файл), а `DashboardAsset` приносит `JqueryAsset` через `$depends`, чтобы его плагины встали в HTML после него. Копии совпадают версией (обе 3.7.1), поэтому двойной jQuery не ломал вёрстку — он молча убивал поведение: любой bundle, просящий jQuery (а это каждый `yii\bootstrap5\Widget`), печатал копию Yii второй, `window.jQuery` становился тем вторым объектом, а плагины, зарегистрированные на первом, исчезали со страницы — пропадали выбор даты и прокрутки списков. На странице публикаций `initAll()` спотыкался о первый же вызов `daterangepicker` — уже после того, как поставил себе `runOnce`, — и форма не инициализировалась вовсе.
- **Подсказка элемента живёт в его поповере.** То, что делает поле или переключатель, стоит не строкой под ним, а в Bootstrap-поповере самого элемента: `data-bs-toggle="popover" data-bs-trigger="hover" data-bs-placement="top-start" data-bs-custom-class="popover-info"` и текст в `data-bs-content` — ровно тот приём, каким это показывает `ui-kit/popovers.html`. Триггер — сам элемент, а не его подпись: у переключателя и чекбокса это вся группа `div.form-check` (под курсор попадает и тумблер, и текст рядом), у поля — его `label`. `title` не задан ни у одного из семи, и Bootstrap не рисует шапку поповера вовсе. Коробка триггера при этом обрезана по ширине самого триггера и не растёт шире карточки (`[data-bs-toggle="popover"] { width: max-content; max-width: 100%; }`): Bootstrap ставит поповер серединой над серединой коробки, и растянутые на всю карточку группа чекбокса или `label` поля уводили подсказку к её середине — и отвечали бы на наведение в пустую правую половину строки. Поповеры пятого Bootstrap'а не включаются сами собой — их нужно создавать, и `custom.js` делает это для каждого `[data-bs-toggle="popover"]`, но с настройками по умолчанию; скрипт подключается в конце `<body>` и выполняется раньше готового кода страницы, а `getOrCreateInstance()` уже существующему экземпляру своих настроек не навязывает, поэтому `initAll()` сначала снимает экземпляр, поставленный `custom.js` (`dispose()`), и только потом создаёт свой. Контейнером ставится `document.body`: форма стоит в карточках, и внутри своего родителя поповер обрезался бы по их краям; исключение — подсказка поля «Адрес ссылки», которой контейнером назначен сам `.modal`, поскольку она должна остаться внутри диалога, который объясняет, и исчезнуть вместе с ним. `data-bs-placement="top-start"` само по себе до Popper'а не доходит: таблица прикрепления Bootstrap'а знает четыре стороны и `auto`, но не варианты с выравниванием, и подсказка такого триггера остаётся висеть в левом верхнем углу страницы, поэтому размещение передаётся вручную — `popperConfig: { placement: el.dataset.bsPlacement }`. Запасными размещениями Bootstrap считает базовые стороны, так что при перевороте (длинный текст переключателя, которому сверху не хватило бы места) выравнивание `start` теряется и поповер встаёт над серединой триггера. `data-bs-html` не ставится нигде: тексты простые, а с этим атрибутом Bootstrap вставил бы их разметкой. Остались видимыми три подписи, которые принадлежат не элементу, а блоку: «Фильтры применяются к топикам ниже», «Текст обновляется по мере ввода» и «Запись сохраняется в БД и будет отправлена в канал TRVL в заданное время»; счётчики частей и уведомления под полем альбома — живой текст, его hover'ом не покажешь.
- **Иконки — тот файл, что уже несёт ui-kit.** `AppAsset::$css` подключает `ui-kit/assets/fonts/bootstrap/bootstrap-icons.css` (у `DashboardAsset` он в `$css` был и раньше), а `yii\bootstrap5\BootstrapIconAsset` не подключается нигде: он публикует `@vendor/twbs/bootstrap-icons/font`, а этого пакета в зависимостях нет — `twbs/bootstrap-icons` числится лишь необязательной зависимостью `yii2-bootstrap5`, которая прямо предлагает добавить её самому. Пока за иконками просили именно bundle-ом, `InvalidConfigException` получался на каждой странице, собранной через `main.php`.

### Логотип и фавикон

Знак TRVL — «большой круг»: окружность, нарисованная как маршрут (сплошная дуга — пройденное плечо, пунктир — плечо впереди, оранжевое кольцо — точка назначения), и надпись TRVL на хорде этого круга. Два цвета: чернильный `#64739e` и акцентный `#e0713a` — только у точки. Векторные рисунки лежат рядом с остальными картинками веб-документов: `app/web/images/trvl-logo.svg` (словесный знак, 200×57), `app/web/images/trvl-mark.svg` (то же в квадрате 64×64) и `app/web/favicon.svg` (иконка вкладки, 32×32). У всех проставлены `width`/`height` наряду с `viewBox`: без них браузер не знает естественного размера SVG, а шапка ui-kit ограничивает логотип только сверху (`max-height: 46px`), поэтому картинка схлопывается в нуль.

- `app/views/layouts/dashboard.php` берёт их из `@web/images` (`$brandUrl`): в сайдбаре — словесный знак (`.app-brand .logo-full`, 161×46 в боксе 250 px), в мобильной шапке — квадратная марка (`.app-brand-sm .logo`, 46×46). Логотипы ui-kit (`ui-kit/assets/images/logo*.svg`) больше нигде не подключаются.
- Кнопка «закрепить» (`#pin-sidebar`) сужает сайдбар до 70 px, а `.app-brand` просто обрезает всё, что не влезло: от словесного знака оставалось кольцо с огрызком первой буквы. Поэтому в бокс положены обе картинки, и `registerCss` в закреплённом состоянии прячет `.logo-full`, показывая вместо него `.logo-mini` в 46×46.
- Фавикон — не уменьшенный знак, а перерисованный: пунктирное плечо и линейка-хорда на 16 px рассыпаются в грязь, поэтому в кольце остаётся одна буква T.
- Ссылки на иконку отдаёт общий partial `app/views/layouts/_favicon.php`: SVG как `rel="icon"` и прежний `app/web/favicon.ico` как `rel="alternate icon"` для клиентов, которые просят `/favicon.ico` сами. Partial подключён и из `_head.php` (старая разметка логина/ошибок), и из `dashboard.php`, так что правило живёт в одном месте.
- Страницы логина, «О программе», «Контакты» и подвал старой разметки остаются на логотипе Yii (`yii3_full_*` в `app/web/images/`) — там своя, не порталовая вёрстка.
- Лист сравнения десяти вариантов, из которого взят «большой круг», лежит рядом в `trvl-logos/` (`index.html` + папки `01-disc/ … 10-map/`) и в репозиторий не входит: каталог исключён локально в `.git/info/exclude`, так что на другой машине его может не быть.

## Публикации в канал

Подробная документация по функциональности публикаций и интеграции с Telegram каналом вынесена в отдельный файл [PUBLICATIONS.md](PUBLICATIONS.md).

Краткий обзор:

- Публикации хранятся в четырёх таблицах: `publications_post` (основные посты), `publications_draft` (черновики), `publications_edited` (история редактирования), `publications_deleted` (soft-delete архив)
- Отправка в Telegram выполняется исключительно через периодические задачи (`telegram/publish-due`, `telegram/delete-due`, `telegram/edit-due`), а не напрямую из формы
- Управление каналом Telegram (описание, посты, закрепление, удаление) реализовано в `ChannelService`
- Клиент канала ждёт ответа 30 секунд (`NutgramChannelClient::REQUEST_TIMEOUT`): пять секунд, которые Nutgram просит по умолчанию, уходят не на ответ API, а на установку соединения — первый вызов прохода мерился на локальном портале пятнадцатью секундами, а задача, не дождавшаяся ответа, повторяется через пять минут
- Консольные команды доступны через `TelegramController` (`php yii telegram/*`)
- Конфигурация требует `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHANNEL_ID` в `.env`; там же живут `COOKIE_VALIDATION_KEY`, `YII_DEBUG`/`YII_ENV` и `TELEGRAM_PUBLISH_CRON_SCHEDULE`

Для полной информации см. [PUBLICATIONS.md](PUBLICATIONS.md).

## Адреса страниц

Страницы и эндпоинты доступны по коротким путям: `/` — дашборд, `/publications` — страница публикаций, `/settings` — «Настройки публикаций», `/parser-settings` — «Настройки парсера», `/login`, `/contact`, `/about`, `/captcha`, а также POST-эндпоинты `/publication-create`, `/publication-publish`, `/publication-to-draft`, `/publication-schedule`, `/publication-delete`, `/publication-page`, `/forum-post-page`, `/forum-thread`, `/publication-sort`, `/title-from-first-line-save`, `/links-to-buttons-save`, `/forum-text-order-save`, `/channel-description`, `/forum-viewed`, `/forum-filter-save`, `/forum-filter-clear`, `/settings-save`, `/parser-settings-save`. Плоские имена совпадают с id действий `SiteController`, поэтому перечень правил в `app/config/web.php` (`urlManager`, `enablePrettyUrl` + `showScriptName => false`) и есть список публичных адресов.

Фильтры блока «Форум», порядок списков, порядок топиков по длине текста и оба переключателя формы в правилах не участвуют и остаются строкой запроса: `/publications?withImages=1&withPosts=1&imagesCount=3&forumTextOrder=asc&titleFromFirstLine=1&linksToButtons=1`.

Маршрутам вне списка (`site/error`, модули `gii` и `debug`) правила не нужны: при `enableStrictParsing => false`, если ни одно правило не совпало, путь сам становится маршрутом, а `Url::to()` для такого маршрута выдаёт форму `/controller/action`. Вид `?r=` при включённом `enablePrettyUrl` не читается, поэтому сохранённые раньше адреса вроде `/index.php?r=site%2Fpublications` открывают дашборд.

`index.php` из адреса убирает веб-сервер: `app/web/.htaccess` в Apache-варианте и `try_files $uri $uri/ /index.php?$query_string;` в `docker/nginx/default.conf` и в nginx-конфиге Windows-окружения — конфиги менять не потребовалось.

## Релизы

Релизы публикуются автоматически на [GitHub Releases](https://github.com/Resident234/TRVL/releases) через GitHub Actions (`.github/workflows/release.yml`).

Порядок выпуска релиза:

1. Добавить в `CHANGELOG.md` секцию `## [X.Y.Z] - ГГГГ-ММ-ДД` (формат Keep a Changelog)
2. Закоммитить и запушить изменения в `master`
3. Создать и запушить тег:

```
git tag vX.Y.Z
git push origin vX.Y.Z
```

Workflow срабатывает на пуш тега `v*`: извлекает секцию соответствующей версии из `CHANGELOG.md` (префикс `v` срезается автоматически) и создаёт релиз с именем тега и телом из заметок CHANGELOG. Если такой релиз уже существует, его тело не перезаписывается — при необходимости обновить заметки пересоздайте релиз или отредактируйте его вручную.
