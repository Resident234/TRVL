# TRVL

Версия проекта: **0.2.0** (см. [CHANGELOG.md](CHANGELOG.md)).

## Архитектурное решение

### Основа решения

Для проекта TRVL принимается **слоистая архитектура**. Подход основан на описании технологической платформы и Yii-приложения в статье «Слоистая архитектура на основе фреймворка yii» [1], а структура прикладных компонентов дополнительно сопоставляется с официальной моделью Yii 2 [2] [3].

> Слоистая архитектура — это такая архитектура системы, при которой система состоит из упорядоченной совокупности программных подсистем, называемых слоями, такой, что:
>
> 1. на каждом слое ничего не известно о свойствах и даже существовании последующих, более высоких слоёв;
> 2. каждый слой взаимодействует с непосредственно предшествующим, более низким слоем через заранее определённый интерфейс, не зная внутреннего устройства нижележащих слоёв;
> 3. каждый слой располагает ресурсами, которые он либо скрывает от других слоёв, либо предоставляет непосредственно следующему слою через абстракции.
>
> Практическое следствие для TRVL: зависимости направлены сверху вниз, а детали реализации скрыты за контрактами и публичными API модулей.

В классической схеме статьи технологическая платформа разделяется на **Core layer**, **Shared layer** и **Application layer**. Для TRVL сохраняется эта модель. Docker, nginx, PHP-FPM и PostgreSQL рассматриваются как среда исполнения и инфраструктурная граница, а не как повод нарушать логические границы прикладных слоёв.

### Слои TRVL

| Слой | Назначение | Что находится в слое | Что слой не должен знать |
|---|---|---|---|
| **Core** | Низкоуровневые, стабильные и переиспользуемые технические абстракции | Yii 2, Composer-зависимости, базовые контракты, DTO/результаты, технические исключения, общие утилиты и абстракции доступа к инфраструктуре | Конкретные сценарии приложения, канал TRVL, конкретные источники и пользовательские процессы |
| **Shared** | Переиспользуемая бизнес-функциональность и интеграционные модули | Модули сущностей, профилей, источников, публикаций, стилей, медиа, тегов, актуальности и Telegram; публичные сервисы, репозитории и адаптеры модулей | Конкретные контроллеры и представления приложения, конкретную конфигурацию одного приложения и детали других Shared-модулей |
| **Application** | Сценарии конкретного продукта и его пользовательские интерфейсы | Тонкие web-контроллеры, console-команды, конфигурация, сборка use-case сценариев, приложение TRVL, dashboard и специфические представления | Внутреннее устройство Shared-модулей, SQL, HTTP-клиенты, Telegram API и конкретные способы хранения данных |

Направление зависимостей для бизнес-кода: **Application → Shared → Core**. Core не зависит от Shared и Application. Shared не импортирует классы Application. Application обращается к Shared только через его публичные контракты, сервисы, команды, DTO и результаты. Прямой обход слоя, например вызов SQL из контроллера или обращение Application к внутреннему классу Shared-модуля, запрещён.

Инфраструктурные детали подключаются на границе системы. PostgreSQL, HTTP-источники, Telegram, файловое хранилище, нейронные сервисы и средства обработки изображений должны быть скрыты за интерфейсами и адаптерами. Конкретные реализации связываются с интерфейсами конфигурацией Yii и контейнером приложения. Поэтому замена PostgreSQL, API-адаптера или реализации генерации текста не должна требовать изменения use-case кода.

### Правила слоёв

Каждый слой обязан предоставлять следующему слою только необходимую абстракцию. Внутренние модели, SQL-запросы, структуру таблиц, HTTP-ответы, токены, файловые пути и SDK-объекты не должны утекать через публичный API модуля.

Связь между слоями выполняется через параметры, команды, DTO, типизированные результаты и исключения. Использование общих глобальных массивов, глобальных переменных и неявного состояния для обмена данными между слоями запрещено. Сервисы должны получать зависимости явно через конструктор или через конфигурацию композиционного корня.

`Yii::$app` и другие service locator-механизмы допускаются в entry points, конфигурации и composition root, где собираются зависимости приложения. В бизнес-коде предпочтительны явные зависимости и интерфейсы; бизнес-сервис не должен самостоятельно искать глобальный компонент, открывать соединение с БД или создавать внешний SDK-клиент.

### Application layer: тонкие контроллеры и команды

Web-контроллеры и console-команды являются точками входа. Они принимают и минимально валидируют входные данные, преобразуют их в команду или DTO, вызывают use-case сервис и формируют HTTP-, console- или JSON-ответ.

Контроллеры и команды не должны содержать правила парсинга, планирования публикаций, выбора стиля, преобразования изображений, работы с Telegram, SQL-запросов или сложных ветвлений предметной области. Такая логика располагается в Shared-модулях и вызывается через их публичное API.

Application layer отвечает за композицию конкретного продукта. Например, сценарий «поставить текст в очередь, обработать стиль и отправить на публикацию» может быть собран в Application-сервисе из публичных операций модулей очереди, стиля и публикации, но внутреннее устройство этих модулей ему неизвестно.

### Shared layer: функциональные модули

Функциональность, которая может быть использована более чем одним сценарием или приложением, оформляется как модуль с чёткой границей. На первом этапе модуль может находиться внутри Application, но при появлении второго потребителя его необходимо выделить в Shared без изменения публичного API.

В перспективе в TRVL должны быть выделены следующие функциональные области:

| Модуль | Ответственность |
|---|---|
| **Source/Entity** | Источники, сущности, посты, идентификация элементов и фиксация изменений |
| **Profile** | Профили, описания и слоганы |
| **Parsing** | Получение и нормализация данных из источников; повторный проход и обнаружение обновлений |
| **Publication** | Посты, порядок публикации, отложенная публикация и очереди |
| **Style** | Хранение образцов текста, структуры и выбранных стилей |
| **Media** | Изображения, преобразования и будущий логотип-вотермарк |
| **Tagging/Actuality** | Теги и примечания с датой актуальности информации |
| **Telegram** | Интеграция с каналом TRVL и будущим Telegram-ботом |
| **Settings** | Подстраиваемые величины страницы публикаций, их описание в одной схеме и хранение в `publications_setting` (`app/shared/Settings`, выделен из Publication) |
| **Dashboard** | Только если интерфейс нельзя оставить в Application; бизнес-операции остаются в Shared |

Каждый модуль должен скрывать свои модели хранения и инфраструктурные детали. Другие модули обращаются к нему через сервисы, интерфейсы, команды и DTO. Например, модуль Publication не должен требовать от вызывающего кода знания таблиц PostgreSQL, а модуль Style не должен заставлять контроллер работать с конкретной реализацией AI-провайдера.

В Yii 2 модуль является самодостаточной единицей, которая может включать `Module.php`, модели, контроллеры, представления, конфигурацию и консольные команды [3]. Для TRVL это используется как организационный механизм, но границы слоёв важнее одной только структуры каталогов: наличие каталога `models` не делает любой код внутри него бизнес-логикой автоматически.

### Предлагаемая организация каталогов

Текущий Yii Basic Application остаётся рабочей точкой входа. По мере развития проекта структура должна эволюционировать в сторону явного разделения приложения и переиспользуемых модулей:

```text
TRVL/
├── app/                         # Application layer и Yii entry points
│   ├── commands/                # тонкие console-команды
│   ├── controllers/             # тонкие web-контроллеры
│   ├── modules/                 # специфичные для приложения модули
│   ├── views/                   # представления приложения
│   ├── config/                  # конфигурация и composition root
│   ├── web/                     # публичный document root
│   ├── tests/                   # тесты приложения и сценариев
│   └── yii                      # console entry script
├── shared/                      # Shared layer, добавляется при выделении модулей
│   ├── modules/
│   ├── contracts/
│   └── config/
├── core/                        # Core layer проекта, если собственных абстракций станет достаточно
│   ├── contracts/
│   ├── dto/
│   ├── exceptions/
│   └── support/
├── docker/                      # среда исполнения, вне бизнес-слоёв
├── config/                      # конфигурационные шаблоны проекта
├── docker-compose.yml
└── README.md
```

Пока отдельные `core/` и `shared/` ещё не выделены в коде, это не является основанием для размещения бизнес-логики в контроллерах. Новая функциональность должна сразу проектироваться как кандидат на отдельный модуль с публичным API и возможностью последующего перемещения из `app/modules` в `shared/modules`.

### Конфигурация и подмена реализаций

Конфигурация Yii используется как слой связывания зависимостей и как средство уменьшения связанности. Компонент получает стабильный идентификатор или интерфейс, а конкретный класс выбирается в configuration/composition root. Замена локального адаптера на REST-клиент, одного хранилища на другое или одного AI-провайдера на другой не должна требовать изменений в контроллерах и use-case сценариях.

Конфигурация окружения, секреты и параметры подключения не должны зашиваться в исходный код. Локальные значения передаются через `.env` и Compose, а код получает их через конфигурационный слой. Секреты не коммитятся и не выводятся в логи.

### Модель данных и PostgreSQL

PostgreSQL является инфраструктурой хранения. Таблицы, индексы, SQL и ORM/ActiveRecord-модели относятся к нижнему уровню модуля и не должны становиться контрактом для Application layer. Use-case сервисы работают с репозиториями или доменными API, а не с прямыми SQL-запросами.

Схема данных должна поддерживать идентификацию источника и внешнего элемента, дату последнего наблюдения, версию или хэш содержимого, состояние обработки и дату актуальности. Это позволит реализовать повторный полный проход диапазона без дублирования, обнаружение изменений и добавление новых элементов. Конкретные таблицы и поля будут проектироваться отдельным этапом, когда начнётся реализация парсинга.

### Тестируемость и развитие

Каждый Shared-модуль должен иметь тесты публичного API и основных бизнес-правил. Инфраструктурные адаптеры тестируются отдельно от use-case сценариев. Application-тесты проверяют сборку сценариев и точки входа, но не должны дублировать внутренние тесты Shared-модулей.

В дальнейшем система сборки, миграций, CI, Selenium, очереди и фоновые процессы добавляются как инфраструктура вокруг слоёв, не разрушая их границы. Новая технология не должна становиться причиной прямой зависимости контроллеров от внешнего SDK или хранилища.

### Архитектурные критерии при code review

Перед добавлением функциональности необходимо ответить, к какому слою и модулю она относится, какой публичный контракт предоставляет и какой нижний слой использует. Следует проверить, не знает ли нижний слой о верхнем, не протекают ли наружу детали хранения или SDK, не появилась ли бизнес-логика в контроллере и можно ли заменить инфраструктурную реализацию через конфигурацию.

Функциональный блок считается корректно выделенным, если его можно вызвать из другого Application-сценария через публичный API, протестировать без реального внешнего сервиса и при необходимости перенести между приложениями без переписывания внутренней логики. Это поддерживает ключевые цели подхода из статьи: повторное использование, расширяемость, единый деплой и возможность менять детали реализации без изменения верхних слоёв [1].

### Модель данных

Публикации канала TRVL хранятся в четырёх таблицах PostgreSQL, а подстраиваемые величины страницы публикаций — в пятой:

| Таблица | Назначение |
|---|---|
| `publications_post` | Посты канала: запланированные (`published_at` в будущем, `telegram_id` пуст) и уже опубликованные (`telegram_id` заполнен) |
| `publications_draft` | Черновики — записи до отправки в Telegram |
| `publications_edited` | Архив редактирования опубликованных постов (те же поля, что у поста, плюс `edited_at`); пустой `edited_at` означает, что сообщение в канале ещё не заменено новым текстом |
| `publications_deleted` | Архив удалённых постов — soft-delete (те же поля, что у поста, плюс `deleted_at`); пустой `deleted_at` означает, что сообщение ещё не удалено из канала |
| `publications_setting` | Настройки публикации: строка на каждую подстраиваемую величину (`code` → `value` + `updated_at`), сид берётся из схемы `PublicationSettingsService` |

Данные форума (см. [PARSER.md](PARSER.md)): `topic` — топики, `post` — посты топиков, `member` — профили участников (авторы топиков и постов), `parser_config` — диапазоны сущностей и поведение запросов парсеров (см. «Настройки парсера»).

Четыре таблицы публикаций держат один и тот же набор полей, и у них есть общее — `formatting jsonb NOT NULL DEFAULT '[]'` (миграция `m260926_000001_add_formatting_to_publications`): `text` остаётся обычным текстом, а разметка этой строки лежит отдельным списком сущностей сообщения рядом (см. «Форматирование текста»). Пустой список — обычный текст, то есть ровно то, что записано в любой строке, созданной до появления колонки. Тем же порядком рядом лежит и кнопка-ссылка строки — `button jsonb NOT NULL DEFAULT '{}'` (миграция `m260927_000001_add_button_to_publications`, см. «Кнопка-ссылка»): пара `{text, url}` той же записи; пустой объект — сообщение без кнопки, то есть ровно то, что записано в любой строке, созданной до появления колонки. Рядом стоит и заголовок строки — `title text NOT NULL DEFAULT ''` (миграция `m260928_000001_add_title_to_publications`, см. «Заголовок части»): жирная первая строка, которая в `text` не входит и добавляется к сообщению при отправке; пустая строка — сообщение без заголовка, то есть ровно то, что записано в любой строке, созданной до появления колонки.

### Открытие на редактирование

При нажатии на кнопку-иконку редактирования (или двойном клике по элементу списка) публикация любого типа — черновик, запланированная, опубликованная или удалённая — открывается на редактирование в форме «Новая публикация»: текст подставляется в поле ввода, заголовок — в поле над ним (атрибут `data-title` строки, пустой заголовок остаётся пустым полем), дата публикации (для постов и удалённых записей с непустым `published_at`) — в поле даты, а тип и id исходной записи передаются скрытыми полями `publicationSource` / `publicationSourceId`.

Время публикации в списках и в атрибуте `data-published-at-utc` хранится в UTC, а поле даты формы работает с местным временем пользователя, поэтому при подстановке значение переводится в часовой пояс пользователя (`utcToPickerValue()`) и в обратной форме возвращается на сервер, где `normalizeDate()` приводит его обратно к UTC. У записи без `published_at` (черновик) поле даты остаётся таким, каким было в форме.

У каждой части разбитой публикации — свой альбом. Блок части несёт поле `publicationPartImages[]` со своей подписью («Изображения этой части»), своим пикером файлов, своей плашкой замечаний и своим превью; альбомом первой части служит общее поле «Изображения публикации» (`publicationImages`) под списком, поэтому у первого блока собственное поле скрыто и выключено (`d-none` + `disabled`) — невыгружаемое поле не уходит на сервер и не сдвигает части списка. Порядок при этом один и тот же: `publicationText[]` и `publicationPartImages[]` читаются позиционно (`SiteController::imageGroupsFromRequest`), так что N-е поле текста соответствует N-му полю альбома.

Вместе с текстом в поле альбома подставляется список `image_urls` — из редактируемой записи или из элемента форума (атрибут `data-image-urls`), и в форму он попадает не как есть. Форум хранит ссылки, которые он прочитал когда-то, а файл за ссылкой к этому времени мог исчезнуть; заметить это до отправки альбома в канал можно только одним способом — запросив каждую ссылку, чем и занимается JS страницы (`writeImages`, `probeImage` через `new Image()`). В поле остаются ссылки, ответившие загрузкой; та, что не ответила вовсе, мёртвой не считается — по истечении `__IMAGE_PROBE_TIMEOUT` (настройка «Ожидание проверки картинки», 6 с по умолчанию) она остаётся в поле. Альбом записывается в поле целиком сразу, а не по мере ответов, чтобы форма, отправлённая посреди проверки, не потеряла живую картинку; список сужается, когда ответили все. Проверка и сужение живут отдельно у каждого альбома: счётчик `albumWrites[index]` растёт от любой записи в это поле — и от заполнения, и от руки, — поэтому опоздавший ответ не трогает поле, которого к его приходу уже нет.

Отброшенные ссылки в форму не подгружаются и перечисляются под тем полем, из которого их убрали: у общего поля это `#publicationImagesNotice`, у поля части — `.publication-images-notice` её же блока (`Мёртвые ссылки в изображения не добавлены (N): …`), и то и другое скрыто (`d-none`), когда терять нечего. Очистка формы после сохранения идёт через ту же `writeImages`, поэтому замечание убирается вместе со ссылками.

### Сценарии сохранения

Дальнейшее поведение зависит от типа редактируемой записи и нажатой кнопки — «Опубликовать» или «Сохранить». Восемь сценариев (логика в `PublicationsService::saveFromForm`, `app/shared/Publications/Service/PublicationsService.php`):

| Редактируемая запись | Кнопка | Что происходит |
|---|---|---|
| Запланированная публикация | **Опубликовать** | Штатное обновление в таблице публикаций: `published_at` обновляется текущим значением соответствующего поля формы, `updated_at` — временем изменения, `created_at` сохраняется в неизменном виде |
| Запланированная публикация | **Сохранить** | Запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `updated_at` — текущее время, то есть момент перемещения в черновик; `created_at` сохраняется в неизменном виде |
| Опубликованная публикация | **Опубликовать** | Запись удаляется из таблицы публикаций и добавляется в `publications_edited`: копируются значения всех полей, `updated_at` — текущее время, `edited_at` остаётся пустым |
| Опубликованная публикация | **Сохранить** | Запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `updated_at` — текущее время, то есть момент перемещения в черновик; `created_at` сохраняется в неизменном виде |
| Черновик | **Опубликовать** | Запись удаляется из таблицы черновиков и добавляется в таблицу публикаций; `updated_at` — текущее время, `created_at` сохраняется в неизменном виде |
| Черновик | **Сохранить** | Штатное обновление в таблице черновиков; `updated_at` — время изменения, `created_at` сохраняется в неизменном виде |
| Удалённая запись | **Опубликовать** | Запись удаляется из `publications_deleted` и добавляется в таблицу публикаций с датой из поля формы; `created_at` сохраняется, `updated_at` — текущее время, `telegram_id` сбрасывается; ожидающееся удаление из канала отменяется |
| Удалённая запись | **Сохранить** | Запись удаляется из `publications_deleted` и добавляется в таблицу черновиков; `created_at` сохраняется, `updated_at` — текущее время (момент перемещения), `telegram_id` сбрасывается; ожидающееся удаление из канала отменяется |

Отдельно от формы работают кнопки-иконки на элементах списков:

- **«Опубликовать» на черновике** — запись удаляется из таблицы черновиков и добавляется в таблицу публикаций; `created_at` без изменений, `updated_at` и `published_at` — текущее время (пост сразу готов к отправке в канал периодической задачей)
- **«Опубликовать» на запланированной публикации** — запись перестаёт быть запланированной: `published_at` и `updated_at` становятся равными текущему времени, `created_at` не меняется
- **«Переместить в черновик» на публикации** (пост любого типа — запланированный или опубликованный) — запись удаляется из таблицы публикаций и добавляется в таблицу черновиков; `created_at` не меняется, `updated_at` — текущая дата и время
- **«Удалить» на публикации или черновике** — запись перемещается в `publications_deleted`: `created_at` и `published_at` сохраняют свои значения (у черновика `published_at` остаётся пустым), `updated_at` заполняется текущим временем, `deleted_at` не заполняется. Периодическая задача `telegram/delete-due` затем удаляет сообщение из канала по `telegram_id` (у записей без `telegram_id` — черновиков и запланированных постов — сообщения в канале не было, им `deleted_at` проставляется сразу) и записывает в `deleted_at` время удаления. Если канал сообщения уже не содержит (`message to delete not found`), это и есть нужный результат: запись получает `deleted_at` как при обычном удалении и из очереди уходит, а не повторяется каждые пять минут.

Общие правила всех сценариев:

- `created_at` исходной записи всегда сохраняется неизменным;
- `updated_at` всегда устанавливается в текущее время — момент обновления или перемещения между таблицами;
- отправка в Telegram из формы не выполняется: записи уходят в канал только периодической задачей `publishDue()` по наступлении `published_at`.

Для новой записи (форма открыта без редактирования) кнопка «Опубликовать» создаёт запланированный пост, кнопка «Сохранить» — новый черновик.

### Форматирование текста

Текст части набирается в редакторе Quill (версия 2.0.3 лежит в репозитории: `app/web/ui-kit/assets/vendor/quill/`, подключается `PublicationEditorAsset`, поверх вендорной темы — `app/web/ui-kit/assets/css/publication-editor.css`). Панель инструментов ограничена тем, что выводит канал: **жирный**, *наклонный*, подчёркнутый, зачёркнутый, `код` и ссылка (`TOOLBAR_FORMATS`) — шрифтов, размеров, заголовков, списков, цитат, цветов и выравнивания в форме нет, потому что Telegram их не рисует.

Размеченный текст хранится раздельно: `text` записи — обычные символы без меток, а разметка — список сущностей сообщения в той же форме, в какой их принимает Telegram API (`MessageEntities`: `bold`, `italic`, `underline`, `strikethrough`, `code` и `text_link` со ссылкой). `parse_mode` не отправляется никогда — именно поэтому смещения сущностей считаются по символам текста, а не по парным `**` или `__`.

- **Носителем данных остаётся textarea.** Скрытое поле части (`textarea.publication-text-part`, имя `publicationText[]`) — то же поле, что и до редактора: счётчики, лимиты, разбивка, слияние и отправка формы читают его. Quill стоит в соседнем `div.publication-editor-field` и служит видимой поверхностью. Три правила связывают их: запись в `field.value` переносит сущности вместе с текстом и перекрашивает редактор (`paintEditor`); ввод в редактор пишет значение через нативный сеттер, перечитывает список у документа и рассылает обычный `input` — то самое событие, которое страница слушает и без редактора; курсор отвечает от редактора, потому что `selectionStart`, `selectionEnd`, `setSelectionRange` и `focus` переопределены у каждого экземпляра поля, — поэтому разрез у курсора остаётся разрезом там, где его видит человек.
- **Список уходит на сервер вторым скрытым полем блока.** Рядом с textarea лежит `input[type=hidden].publication-format-field` с именем `publicationFormatting[]`, в него пишется JSON сущностей этой части. `SiteController::publicationFormatsFromRequest()` читает два списка позиционно — так же, как `imageGroupsFromRequest()` читает альбомы, — поэтому N-й список отвечает N-й части, а пропущенное поле (запись старше редактора) возвращается пустым списком.
- **Индексы совпадают сами.** Telegram считает смещения в кодовых единицах UTF-16, и `String#length` в браузере считает их же, так что позиция в редакторе, позиция в textarea и смещение сущности — одно число; эмодзи за базовой плоскостью не сдвигает ничего. На сервере то же значение считает `MessageEntities::utf16Length()`.
- **Экран и есть то, что уходит.** `paintEditor` перекрашивает поле по списку, а потом перечитывает список у документа (`entitiesFromOps`): сущность, не влезшая в текст, отрезается, соседние прогоны одного формата склеиваются, а порядок остаётся по возрастанию смещения — то, чего требует `MessageEntities::assertFitsText()`. Перечитывание правит и то, чего редактор хранить не может: пустая строка в конце значения не сохраняется, и в textarea возвращается ровно тот текст, какой вышел в редакторе.
- **Сущности едут вместе со своим текстом.** Нумерация частей, подстановка из форума, ручная и автоматическая разбивка, слияние и перенос выделения работают с двумя списками сразу. Переписывание поля на месте ведёт `remapEntities` (разбор по общему началу и общему концу), разрез части — `splitEntitiesAt`, перенос выделения — `takeEntities`, `exciseEntities` и `shiftEntities`, склейка двух частей — `joinedFormats`, а `sortEntities` и `joinAdjacent` приводят результат к каноническому виду. Подробно о судьбе списков при разбивке — в разделе «Разбивка длинного текста на части».
- **Панель отвечает на нажатие кнопки мыши, а не на `click`** — Quill отменяет `click`, чтобы редактор не потерял фокус. Слушатель `paste` навешан на контейнер в capture-фазе и вставляет только текст: иначе в форму приходят заголовки, цвета и разметка той страницы, откуда его скопировали. Там же адрес, пришедший вместе с текстом, становится ссылкой — см. «Ссылка в тексте».
- **Запись на редактирование** подставляет в поле и его сущности: элемент списка несёт их в атрибуте `data-formatting`, `parseFormatting()` читает строку, а дальше список живёт в поле как разметка его же текста. Сами списки записей (черновики, посты, удалённые) остаются текстом без разметки — раскрашивается только форма и её предпросмотр.
- **Сервер проверяет список так же, как лимит текста.** `PublicationsService::saveParts()` и `saveFromForm()` сначала снимают пробелы по краям (`trimFormatting()` — тот же `slice()`, что и у подписи), затем `assertPartValid()` вызывает `assertFitsText()`: пустая сущность, сущность за границами текста, список не по порядку и ссылка без http(s)-адреса дают `InvalidArgumentException` — flash, и ни одна запись не записана.
- **В канал разметка уходит списком `entities`.** `ChannelService::publishText()`, `publishPhotos()` и `editPostText()` принимают `MessageEntities` и отдают его `NutgramChannelClient` как `entities` у текста и `caption_entities` у подписи. Публикация с альбомом режется на подпись и продолжение по порогу `CAPTION_MAX_LENGTH`, и список режется тем же `slice()`: в подписи остаются отрезки разметки её куска, в продолжение уходят остальные, уже отсчитанные от начала своего текста.

Спойлера в списке нет: встроенного спойлера у Quill нет, и для него пришлось бы писать собственный blot. Блочные форматы — цитата, заголовок, список, `pre` — исключены тем же правилом, что ограничивает панель: форма даёт ровно то, что Telegram рисует внутри строки текста.

### Заголовок части

Первая строка сообщения, набранная жирным, — так канал отделяет тему публикации от её текста. Поле «Заголовок» (`#publicationTitleInput`, имя `publicationTitle`) стоит над редактором первой части, а каждая прочая часть получает своё в клонированном блоке (`.publication-title-field`, имена `publicationPartTitle[]`). Заполнять его не обязательно: пустое поле (как и поле из одних пробелов) значит сообщение без заголовка, и уходит ровно тот текст, что набран в редакторе.

- **Заголовок — отдельная колонка, а не начало текста.** `title text NOT NULL DEFAULT ''` живёт в четырёх таблицах публикаций рядом с `formatting` и `button` (миграция `m260928_000001_add_title_to_publications`), поэтому `text` записи остаётся тем, что человек набрал, а сообщение канала собирает `PublicationData::messageText()` и `messageEntities()` в момент отправки. Запись, созданная до появления колонки, — пустой заголовок, то есть то же сообщение, что и раньше.
- **Нумерация частей переезжает в конец заголовка.** Часть со своим заголовком уходит в канал строкой «Заголовок. Часть 2»: `PublicationData::splitHeader()` узнаёт начало текста по тому же образцу, что и `stripPartNumber()` страницы, снимает его с текста и ставит после заголовка через точку. Что написал сам автор — точку или двоеточие после номера — то и остаётся; строка «Часть 2» в textarea при этом не меняется, и поле формы по-прежнему хранит её.
- **Жирным становится вся строка заголовка.** `MessageEntities::underHeading()` добавляет `bold` от нуля до её конца и сдвигает за неё сущности текста — на длину заголовка, на пустую строку после него и минус тот номер, который заголовок из текста забрал. Без последней поправки жирный прогон уехал бы на «Часть 1» дважды, потому что смещения в `formatting` отсчитаны от начала сохранённого текста, а он начинается с этой строки.
- **Экран и есть то, что уходит.** `composedMessage()` переносит тот же разбор на страницу: `update()` рисует в предпросмотре заголовок жирной первой строкой над телом, `updateCounters()` показывает длину уже собранного сообщения, а `headingReserve()` отнимает от лимита части её заголовок (плюс пустую строку), так что разбивка начинается раньше, если заголовок длинный. Сервер считает то же по собранному тексту: `assertPartValid()` меряет `messageOf()` против `TEXT_MAX_LENGTH` и говорит «Заголовок с текстом должен быть от 1 до 4096 символов».
- **Списки читаются позиционно.** `SiteController::publicationTitlesFromRequest()` ставит общее поле на место первой части и добавляет клонированные (`partFieldsFromRequest`) — тем же порядком, каким читаются альбомы, списки сущностей и кнопки, — поэтому N-е заглавие отвечает N-й части. Пустая строка колонки значит, что у этой части заголовка нет.
- **Любая перестройка частей рассаживает заголовки заново.** `setTextParts()` принимает список заголовков и пишет их в поля после клонирования, а места, где часть появляется или исчезает, называют это явно: ручная и автоматическая разбивка и перенос выделения дают новой части пустое поле, слияние убирает поле той части, которой больше нет — у сообщения одна первая строка, и остаётся заголовок той части, в которую слили.
- **Запись на редактирование подставляет свой заголовок**, элемент списка несёт его в атрибуте `data-title`, а `loadText()` отдаёт его первой части; подстановка из форума и загрузка треда заголовка не приносят — у темы форума своё название, и оно в поле публикации не переезжает. Очистка формы после сохранения убирает его вместе с остальными полями.
- **Списки записей показывают собранное сообщение.** `_item_post.php`, `_item_draft.php` и `_item_deleted.php` выводят `headingAndBody()` записи: жирную строку заголовка над текстом без съеденного им номера.

### Ссылка в тексте

Ссылка — одна из шести сущностей и единственная со своим адресом: `text_link` стоит над куском текста, а адрес живёт у самой сущности, поэтому в `text` записи не появляется ничего. Ссылку ставят двумя путями: её набирают через панель редактора и её проставляет сама страница там, где текст приходит в форму извне.

- **Панель спрашивает русским окном, а не системным `prompt()`.** На кнопке ссылки Quill зовёт `prompt()` — окно браузера: его заголовок не перевести, адрес уже стоящей ссылки в поле не подставляется, и то, что пустой ответ ссылку убирает, в нём ничем не сказано. Обработчик `link` переопределён при подключении редактора (`modules.toolbar.handlers.link` → `openLinkDialog`), и страница показывает своё окно Bootstrap (`#publicationLinkModal`, рядом с окном планирования): поле «Адрес ссылки», «Применить», «Отмена» и «Убрать ссылку». Окно работает с выделением, как и прочие кнопки панели: ничего не выделено — flash «Выделите текст, который станет ссылкой.», и адрес не набирается.
- **Одно окно добавляет, правит и убирает.** Курсор, стоящий внутри ссылки, раскрывается до всей ссылки (`enclosingLink` читает список сущностей части, а не документ), её адрес подставляется в поле, а «Убрать ссылку» видна только над уже стоящей ссылкой. Пустое поле значит ровно то же: `formatText(…, 'link', '')` снимает разметку, и текст остаётся обычным. Окно, закрытое «Отменой» или крестиком, выделение не трогает, а `linkTarget` снимается на `hidden.bs.modal`, чтобы запоздалый «Применить» не написал в уже забытую часть.
- **Хост без протокола читается как https, любая другая схема отвергается.** `linkAddressOf` дописывает `https://` адресу, набранному без схемы, и отвечает отказом на всякую прочую — flash «Ссылка принимает адрес http:// или https://.», и окно ждёт лучшего адреса. Причина не в Telegram, а в самом редакторе: `Link.PROTOCOL_WHITELIST` у Quill — `http, https, mailto, tel, sms`, и всё остальное редактор молча превращает в `about:blank`, поэтому на его же проверку полагаться нельзя. Глубокие ссылки Telegram (`tg://`) остаются за кнопкой-ссылкой части: у неё своё поле и своя проверка на сервере.
- **Адрес, пришедший текстом, становится ссылкой сам.** Каждый адрес, над которым ещё нет ссылки, оборачивается ею, а протокол из текста вычитается: в сущность уходит `https://awd.ru`, над текстом остаётся `awd.ru`. `linkifyParts()` вызывается из `setTextParts()` — при открытии записи на редактирование, при подстановке из форума, при загрузке треда и при всякой перестройке частей — и стоит до `applyPartNumbers()`, чтобы нумерация перенесла новые сущности вместе с их текстом. Тот же `linkifyEditor()` одного поля стоит в слушателе `paste` сразу после вставки: адрес, попавший в буфер обмена, человек явно не собирался терять, а курсор возвращается на конец вставки за вычетом снятых протоколов.
- **Адрес опознаётся по схеме.** `findLinks()` берёт всё, что началось с `http://` или `https://` и не прерывается пробелом, угловатой скобкой, кавычкой или `«»`; хост без протокола адресом не считается, поскольку не отличается от слова, в котором стоит. Из конца адреса выбрасываются знаки препинания, которыми его обычно окружают (`. , ; : ! ? » « ' " … ]`), и закрывающая скобка, которой в адресе не открывали, — адрес в скобках и адрес перед точкой берутся целиком. Адрес, хоть немного покрытый уже стоящей над ним ссылкой, пропускается, поэтому повторный проход ничего не удваивает и автоматику можно вызывать вперемешку с перестройками частей.
- **Разметку сдвигает сам редактор, а не счёт.** `linkifyEditor()` правит документ Quill — `deleteText()` протокола и `formatText()` ссылки, оба с источником `api`, чтобы слушатель `text-change` не написал зеркало поверх, — а список сущностей после прохода перечитывается у документа (`entitiesFromOps`), и только тогда в поле пишется значение. Так отрезки разметки соседей уходят на новые места сами, и серверная проверка (`assertFitsText()`) получает тот же список, что рисует экран.
- **Автоматика не трогает то, чего не видит.** Напечатанное в редакторе не проверяется: адрес, который человек набрал сам, остаётся текстом, пока он не выделит его и не нажмёт кнопку панели, — молча переписывать набранное было бы хуже самого текста. Текст, пришедший с форума ссылкой, адреса не содержит вовсе: `ForumPageDomParser::htmlToText()` выбрасывает `href` тега `<a>`, и в форму приходит одна метка. Разбивка адреса между частями практически не случается, поскольку `splitIntoParts()` режет по пробелу, а внутри адреса пробела нет, — и сканер разрезанный пополам адрес не чинит.

### Emoji в тексте

Emoji — обычный текст: форма не хранит про них ничего, а панель и поиск по `:` лишь помогают поставить символ в текст части. Тот же символ, что человек принёс с клавиатуры, попадает в `text` записи, уходит в канал тем же `text` и рисуется в предпросмотре как есть.

- **Таблица лежит в репозитории.** `app/web/ui-kit/assets/vendor/emoji/trvl-emoji.js` — 1921 emoji, порядок и категории которых взяты из UTS #51 `emoji-test.txt` (только последовательности уровня fully-qualified), а русские слова — из аннотаций CLDR для `ru` (имя и производные ключи); обе под Unicode License v3, о чём говорит соседний `.LICENSE.txt`. Подключает файл `PublicationEditorAsset`, перед Quill. Одна строка на emoji, табами: сам символ, номер категории, имя, ключи — ключи объекта над каждой строкой стоили бы дороже, чем занимают сами слова.
- **Ищутся emoji по началу слова.** `emojiSearch(query, list, limit)` ставит имя выше ключей — ключ есть свободная ассоциация, и на «кнопку» ключуется секундомер, — внутри одного ранга порядок остаётся порядком таблицы, то есть Unicode, где частые emoji категории идут раньше редких. `emojiKey()` снимает регистр, `ё` и пробелы между словами, поэтому «ёлка» и «Елка » ищутся одинаково. Пустой запрос не просит ничего; панель кнопки показывает `EMOJI_SEARCH_LIMIT` = 60 ответов, а без запроса — `EMOJI_BROWSE_LIMIT` = 160 emoji выбранной категории.
- **Два пути делят одну панель.** Узел `#publicationEmojiPanel` перенесён в `body` и стоит `position: fixed` с `z-index: 1080` — те же приёмы, что у всплывающего окна переноса выделения, — и выводится теми же `caretPoint()` и `popupPoint()`. Кнопка панели (`.ql-emoji`, иконка `bi-emoji-smile`) добавляется в уже собранную панель после монтирования редактора: Quill собирает свои контролы при конструировании и об этой не знает, а отвечает она на `mousedown`, как и прочие её кнопки, — `click` редактор отменяет, и курсор ушёл бы из поля. Её панель показывает поле поиска и ряд категорий; двоеточие в тексте показывает ту же сетку без них, поскольку слово уже набрано.
- **Двоеточие ищет только там, где могло начаться слово.** `:` в начале текста или после пробела и открывающего знака (`« ( [ {` и кавычки), а за ним буквы, цифры и `-`: поэтому «Время:30», «https://awd.ru» и русское «Время:» панель не зовут. `↓` и `↑` идут по сетке с переходом через край и прокруткой, `Enter` и `Tab` берут подсвеченный, `Esc` убирает панель и больше не показывает её над тем же словом, пока оно не изменится; любой прочий символ, прокрутка, изменение размера окна и всякая перестройка частей закрывают её, а `←` и `→` остаются курсору слова — и в тексте части, и в поле поиска. Пока поле поиска пусто, ничему не подсвечено место, и `Tab` уходит из панели, как из любой прочей.
- **Вставка идёт только через редактор.** `deleteText()` слова-короткода с источником `api` и `insertText()` символа с источником `user` — тот же путь, по которому проходит напечатанная буква, поэтому слушатель `text-change` сам перечитывает список сущностей у документа, сам пишет зеркало textarea, сами обновляются счётчики и самим запускается разбивка. Курсор возвращается за вставленный emoji — но только когда часть ещё стоит на месте: запись зеркала могла разрезать её и переложить все поля, кроме первого. Следствие того же пути: emoji, вставленный в конец жирного слова, попадает в его прогон, как в него попадает буква, — канал на emoji ничего не рисует, и список становится шире ровно на то же, на что его расширил бы любой прочий напечатанный там знак.
- **Emoji стоит двух символов — ровно столько, сколько отсчитывает канал.** Индексы совпадают сами (см. «Форматирование текста»): и `String#length`, и `MessageEntities::utf16Length()` считают кодовые единицы UTF-16, поэтому счётчик поля, лимит сообщения и смещения сущностей переносят его без всякой особой арифметики.
- **Разрез части не рвёт emoji.** `wholeCharacter()` — чистая функция в том же разделе, где остальная арифметика сущностей, — отступает назад, пока позиция разреза стоит внутри последовательности: между двумя половинами парного символа, перед `U+FE0F`, `U+FE0E`, `U+20E3` и оттенком кожи, с любой стороны `U+200D` и между двумя региональными индикаторами флага. Её зовут жёсткий разрез `splitIntoParts()` и тот остаток, куда в `manualCut()` и `middleCut()` не попал ни один мягкий разрез; разрез по пробелу, строке и абзацу в ней не нуждается, поскольку всегда стоит рядом с пробелом. Без неё половина символа ушла бы в одно сообщение, а вторая — в следующее.
- **Чего в этом нет.** Оттенков кожи и ручной сборки последовательностей: панель отдаёт ровно те наборы, какие Unicode считает самостоятельными emoji, а не составляет новые из базы и модификатора. Недавних и избранных: для них нужно хранилище — колонка настроек или localStorage. И никакого обращения к Telegram: у Bot API метода поиска emoji нет (`searchEmojis` и `getEmojiKeywords` живут в TDLib и MTProto и читают локальные данные самого клиента), так что своим столом страница пользуется всегда.

### Кнопка-ссылка

Под сообщением канал рисует одну кнопку с адресом — тем же приёмом канал ведёт читателя на опрос или на анкету. Форма набирает её в двух полях под полем альбома: надпись (`#publicationButtonText`) и адрес (`#publicationButtonUrl`) одной кнопки.

- **Кнопка принадлежит части — как её текст и её альбом.** Полем первой части служит общее поле формы (`publicationButtonText` / `publicationButtonUrl`), а каждая прочая часть получает свою пару в клонированном блоке (`.publication-part-button`, имена `publicationPartButtonText[]` и `publicationPartButtonUrl[]`). У первого блока собственная коробка скрыта и выключена (`d-none` + `disabled`) — невыгружаемое поле не уходит на сервер и не сдвигает части списка, ровно как скрытый альбом первого блока.
- **Чекбокс «Кнопка-ссылка в каждой части»** (`publicationButtonEveryPart`) виден только тогда, когда в форме больше одной части. Включённый он показывает и включает коробки всех прочих частей, подставив в них то, что набрано в общем поле (`syncPartButtons`), — дальше каждую пару правят отдельно. Снятый чекбокс прячет и выключает коробки: их значения остаются в форме, но на сервер не уходят, поэтому такие части уходят в канал без кнопки.
- **Любая перестройка частей рассаживает кнопку заново.** `setTextParts()` после разбивки, слияния, подстановки из форума и открытия записи на редактирование вызывает `syncPartButtons()` и `updateButtonBoxes()` и перебивает `id` клонированных полей (`publicationPartButtonText2`, `…3`, …), поэтому пары не остаются вразнобой с частями, а коробка не переживает ту часть, которой уже нет.
- **Списки читаются позиционно.** `SiteController::publicationButtonsFromRequest()` ставит общее поле на место первой части и добавляет к нему клонированные пары (`buttonFieldsFromRequest`) — тем же порядком, каким `imageGroupsFromRequest()` читает альбомы, а `publicationFormatsFromRequest()` — списки сущностей, так что N-я пара отвечает N-й части. Пары, которой в запросе нет (коробка части оставалась выключенной), соответствует кнопка пустая.
- **Хранится кнопка в той же строке, что и её текст**: jsonb-колонка `button` со `{text, url}`, а читается и пишется через `LinkButton` — `fromStored()` переносит любую форму колонки: объект, строку JSON и `null` строки, записанной до появления колонки.
- **Половинка пары — не кнопка.** `LinkButton::assertValid()` на каждом пути записи (`PublicationsService::saveDraft()`, `schedulePost()`, `saveParts()`, `saveFromForm()`) бросает `InvalidArgumentException`, если заполнен только один из двух полей: flash на страницу, ни одна запись не записана. Надпись ограничена 64 байтами — Telegram считает их байтами, а не буквами, поэтому 33 кириллические буквы уже слишком длинно, — адрес 2048 символами и только схемами `http://`, `https://` и `tg://`.
- **В канал кнопка уходит `reply_markup`.** `NutgramChannelClient::toKeyboard()` собирает `InlineKeyboardMarkup` из одной строки с одной `InlineKeyboardButton(text, url)`; пустая кнопка не даёт `reply_markup` вовсе, поэтому сообщение без неё отправляется ровно тем же запросом, что и раньше. У текста и у одиночного фото клавиатура стоит в том же вызове (`sendMessage`, `sendPhoto`), альбом же клавиатуры не принимает: `sendMediaGroup` не знает `reply_markup`, поэтому кнопка части с картинками достаётся первому фото отдельным `editMessageReplyMarkup` — и только когда кнопка есть.
- **Изменение чинит клавиатуру, а не оставляет старую.** `editMessageText` без `reply_markup` оставляет ту клавиатуру, что висела на сообщении, поэтому `editChannelMessageText` отдаёт `toReplacementKeyboard()`: клавиатуру кнопки — когда она есть, пустой `InlineKeyboardMarkup` — когда записи больше нечего показать. Иначе пост, у которого убрали кнопку, остался бы с ней в канале.
- **Превью рисует кнопку под текстом своей части** (`.telegram-preview-button`) — ненастоящей кнопкой, `<span>`ом с `textContent`: предпросмотр ничего не открывает и не приносит в страницу чужую ссылку. Пара, заполненная наполовину, не показывается ничем — превью рисует ровно то, что примет Telegram.
- **Запись на редактирование подставляет свою кнопку**: элемент списка несёт её в атрибуте `data-button` (`LinkButton::toJson()` в `_item_post.php`, `_item_draft.php`, `_item_deleted.php`), `parseButton()` читает строку, `fillButton()` пишет её в общее поле и рассаживает по коробкам частей; очистка формы после сохранения убирает её вместе с остальными полями.

### Разбивка длинного текста на части

Одно сообщение Telegram вмещает 4096 символов (`ChannelService::TEXT_MAX_LENGTH`), поэтому поле «Текст публикации» не ограничено `maxlength`, а длинный текст разбивается на части. Разбивка выполняется в JS страницы (`splitIntoParts`) в трёх местах: при подстановке текста из форума, при открытии записи на редактирование и при вводе, пока поле в форме одно.

- В форме остаётся первое поле, остальные клонируются из него; каждое со своей меткой («Часть 2», «Часть 3», …) и счётчиком символов. Имена полей — `publicationText[]`, поэтому на сервер уходят все части. Из одного блока клонируется и поле альбома части (`publicationPartImages[]`), и поле её сущностей (`publicationFormatting[]`), и пара полей её кнопки (`publicationPartButtonText[]`, `publicationPartButtonUrl[]`), так что списков в форме всегда столько же, сколько частей.
- Граница режется по пустой строке, затем по переводу строки, затем по пробелу; если ни одного разделения нет, текст режется жёстко. Часть короче половины лимита не допускается — остаток добирается следующим разрезом.
- Кнопка «Разделить» (`publicationSplitPart`, клиентская, на сервер не уходит) разрезает одну часть на две вручную. Граница — курсор в поле: он подтягивается к ближайшему концу предложения (`. ! ? …` перед пробелом, в пределах `__SNAP_RANGE` — настройка «Поиск границы при ручной разбивке», 600 символов по умолчанию), а если предложения рядом нет — к началу слова, и только потом остаётся там же, где стоит. Без курсора (и когда он у самого края поля) текст делится примерно посередине: сначала по пустой строке, затем по переводу строки, затем по границе слова и лишь потом жёстко.
- Курсор берётся из поля, которое держало фокус последним: клик по кнопке уводит `activeElement` на себя, поэтому поле запоминается на событии `focusin`. Смещение курсора отсчитывается от текста без префикса `Часть N`, обе половинки очищаются от пробелов на разрезе, а пустой или почти пустой текст не разрезается вовсе. Фокус переходит ко второй части в начало текста.
- Рядом с «Разделить» стоят три кнопки ручного разбивания всего текста — «По абзацам», «По строкам» и «По предложениям» (`splitWholeText`, атрибут `data-split-whole`). Каждая берёт текст всех полей, склеенных пустой строкой, и режет его по границе своего рода: абзац — блок, отделённый двойным и более чем двойным переносом строки (`\n{2,}`), строка — участок между любыми переносами (`\n+`), предложение — текст до `.`, `!`, `?` или `…` перед пробелом (тем же правилом, что и привязка курсора в `manualCut`). В отличие от автоматической разбивки части не упаковываются до половины лимита: есть граница — начинается и часть, пусть в ней одно слово. Кусок, который не влезает в сообщение, дорезает `splitIntoParts`, поэтому сервер его принимает. Пустые куски (несколько пустых строк подряд, перенос в начале или в конце) в поля не попадают, а если границ своего рода в тексте нет вовсе, текст остаётся одной частью.
- Выделение текста в любом из полей (мышью или `shift` + стрелки) показывает две плавающие кнопки — «Переместить в предыдущую часть» и «Переместить в следующую часть»; они появляются только когда полей два или больше. Кусок встаёт в начало следующей части либо в конец предыдущей, шов склеивается пустой строкой, а пробел, который выделение унесло с собой, остаётся в исходной части, чтобы слова не слиплись.
- Часть, опустевшая после переноса, из формы убирается, а на её краях (первая «назад», последняя «вперёд») текст получает собственную часть. Кнопки живут в `.publication-selection-actions` (`position: fixed`, узел переносится в `body`), позиция считается от конца выделения: редактор сам говорит, где рисуется его текст, — `caretPoint()` берёт `getBounds()` нулевой ширины на этой позиции и складывает с координатами поля. На сервер при этом ничего не уходит: правятся те же поля `publicationText[]` и `publicationFormatting[]`.
- Кнопка «Объединить» (`.publication-merge-row`, клиентская, на сервер не уходит) стоит под полем каждой части, кроме последней, и сливает её с частью ниже: два поля ввода становятся одним, текст склеивается через пустую строку — тем же швом, что у автоматической разбивки и переноса выделения. Курсор встаёт на место стыка; пустая часть при объединении просто исчезает.
- Ряды кнопок пересчитываются при каждой смене состава частей, поэтому последней части кнопки не достается, а нумерация `Часть N` после слияния расставляется заново. Если склеенный текст перестал вмещаться в одно сообщение, он уходит в обычную автоматическую разбивку (`splitIfNeeded()`).
- Альбом едет вместе со своим текстом. Ручная и автоматическая разбивка одной части оставляет весь её альбом первой половинке — вторая начинается без картинок (`splitPartAtCaret`, `alignGroups` + `splice`). Слияние двух частей складывает их альбомы в один (`unionGroups`): порядок тот же, что у частей, а ссылка, которую показывали обе, называется один раз. Перенос выделения отдаёт альбом опустевшей части соседу, который принял её текст, а часть, родившаяся на краю формы, начинается пустой. Разбивка всего текста («По абзацам» и друзья) режет текст заново и уже не угадывает, какой из новых частей принадлежала ссылка, поэтому все альбомы сводятся в первый (`flattenGroups`). Файлы, взятые пикерами, едут при этом рядом со ссылками тех же частей и подчиняются тем же правилам (см. «Файлы альбома»).
- Чекбокс «Нумерация частей» дописывает в начало каждого фрагмента строку `Часть N`. Префикс входит в текст сообщения, поэтому на него резервируются символы лимита; нумерация проставляется только когда частей две или больше и снимается вместе с чекбоксом. Чекбокс клиентский и на сервер не отправляется. Заголовок части урезает её бюджет так же: символов лимита касается не только текст поля, но и первая строка, которую из него составляет страница (`headingReserve()`, `partLimit()` — см. «Заголовок части»).
- Чекбокс «Равномерно распределить изображения между частями» (`publicationDistributeImages`) на сервер не уходит: он существует ровно для одного действия — раздать альбом первой части по полям всех частей (`distributeImages`), после чего снимается сам, потому что дальше форма отправляет то, что в полях записано. Список режется на непрерывные куски, отличающиеся по размеру не больше чем на одну картинку, лишние достаются первым частям (`groupImages` — та же раскладка, что считает предпросмотр); делятся при этом ссылки и файлы одного альбома вместе, чтобы кусок, попавший в часть, не терял ни своей картинки, ни своего файла. Без раздачи весь альбом остаётся первой части, а остальные части уходят без изображений.
- Под полем альбома каждой части стоят две кнопки — «Переместить изображения в предыдущую часть» и «Переместить изображения в следующую часть» (`moveImageGroup`, атрибут `data-move-album`, клиентские, на сервер не уходят). Кнопка переносит весь альбом поля к соседу — и ссылки, и файлы его пикера: принятые ссылки встают после тех, что в поле-приёмнике уже были (там же `unionGroups`, так что ссылка, которую показывали оба поля, называется один раз), а поле, из которого ушли, опустошается. У последней части «следующей» части нет, поэтому её кнопка скрыта (ряды пересчитываются вместе с рядами «Объединить»), а «в предыдущую часть» у части второй ведёт в общее поле `publicationImages`, которое и есть альбом первой части. Пустой альбом никуда не переносится: случайный клик не должен оборачиваться потерей ссылок соседа. Замечания опустевшего поля — о мёртвых ссылках и о принятых файлах — снимаются вместе со списком.
- При сохранении каждая часть становится самостоятельной записью той же таблицы (`PublicationsService::saveParts`): связь с форумом достаётся первой части, а изображения — каждой из них в своём количестве, ровно сколько лежит в её поле (`imageGroupsFromRequest`), и кнопка — каждой из них своя, ровно какая лежит в её паре полей (`publicationButtonsFromRequest`), и заголовок — каждой из них свой, ровно какой лежит в её поле (`publicationTitlesFromRequest`); `published_at` первой части берётся из поля даты, каждая следующая — позже предыдущей на «Интервал между частями публикации» (настройка `partsOffsetMinutes`, по умолчанию 1 минута; меньше частоты задачи `publish-due` она быть не может — см. «Страницы настроек»). Все части одной публикации записываются одним вызовом репозитория в транзакции (`createPosts()` / `createDrafts()`), поэтому сбой на середине не оставляет половину публикации в таблице. Периодическая задача `publishDue()` выбирает ожидающие посты по возрастанию `id`, поэтому части уходят в канал одна за другой, каждая со своим списком `image_urls`, своей кнопкой и своим заголовком.
- Разбитый текст можно сохранить только как новую запись: при открытой на редактирование записи несколько полей вызывают `InvalidArgumentException`. Сервер проверяет лимит каждой части так же, как и прежде, и не пишет ни одной записи, если какая-то часть не прошла проверку.

В блоке предпросмотра текст всегда выводится в обёртке `.event-content` — по одному блоку на каждую часть, даже когда публикация не разбита. Разбитая публикация уходит в канал несколькими сообщениями, поэтому каждая обёртка повторяет будущее сообщение: свои картинки сверху (`.publication-part-images`), текст части подписью под ними; у части без своих картинок остаётся только текст. Текст обёртки раскрашен списком сущностей своей части (`renderFormattedText`): он режется по границам отрезков разметки, а каждый кусок заворачивается во вложенные теги тех сущностей, что над ним стоят. Под полями ввода тот же раздел: общее поле показывает альбом первой части, блок каждой прочей части — свой. У публикации из одной части картинок в обёртке нет — альбом остаётся в превью под карточкой (`#publicationPreviewImages`), а единственная ссылка разворачивается в картинку самой карточки. Порог подписи (`ChannelService::CAPTION_MAX_LENGTH`, 1024 символа) предпросмотр не режет — текст части показывается целиком, а в канал он уйдёт подписью с продолжением отдельным сообщением. Под текстом обёртки встаёт кнопка её части (`.telegram-preview-button`) — если пара её полей заполнена целиком; у публикации без кнопки обёртка выглядит ровно так, как выглядела до появления поля.

### Файлы альбома

У каждого поля альбома стоит второе, дополняющее его, — «Файлы публикации» и «Файлы этой части» (`<input type="file" accept="image/*" multiple>`): картинку в альбом можно взять не только ссылкой, но и файлом с локального компьютера. Отдельного поля в базе у файла нет — он сохраняется на сервере, и в `image_urls` той же части становится одной ссылкой больше, поэтому ни сохранение публикации, ни отправка в канал ничего о загрузке не знают.

- Имена пикеров повторяют имена полей со ссылками: общее поле — `publicationImageFiles[]`, пикер части с номером `N` — `publicationPartImageFiles{N-1}[]` (клонированный блок получает имя на каждой перестройке частей). Скобки в имени обязательны: без них PHP оставил бы в `$_FILES` последний файл множественного выбора. Пикер первого блока формы, как и его поле со ссылками, скрыт и выключен (`d-none` + `disabled`), поэтому на сервер не уходит и части не сдвигает. `SiteController::withUploadedImages()` читает альбомы по именам, а не по порядку пришедших файлов, — пустой пикер одной части не перекладывает файлы соседней.
- Выбранные файлы живут в JS рядом со списком ссылок (`readFileGroups()`, `writeFileGroup()` через `DataTransfer` — другого способа записать `input.files` у скрипта нет) и едут вместе со своим текстом: `moveImageGroup`, `mergeParts`, `splitPartAtCaret`, `splitWholeText`, перенос выделения и раздача `distributeImages` работают с обоими списками, а `albumPictures()` даёт полям превью ссылки и файлы одним списком.
- Проверка мёртвых ссылок до пикеров дела не касается: `probeImage` просит загрузкой только строки, а у файла своей ссылки до сохранения нет.
- Картинка выбранного файла строится через `URL.createObjectURL` и держится в `WeakMap` (`fileUrls`) по одному объекту на файл: превью перерисовывается на каждое нажатие клавиши и не должно каждый раз покупать новый URL.
- Пределы задаёт страница настроек — «Размер загружаемого файла» (`imageUploadMaxMb`) и «Файлов в альбоме части» (`imageUploadLimit`). Форма отсекает лишнее до отправки: крупный файл и всё, что не влезло в лимит альбома, в пикер не попадают и перечисляются в плашке под его полем (`.publication-files-notice`: `Файлы крупнее 10 МБ в альбом не добавлены (N): …`, `Файлов больше 10 в альбоме не будет (N): …`; та же судьба `d-none`, что и у плашки мёртвых ссылок). Сервер перепроверяет то же самое (`validatedUpload`) и бросает `InvalidArgumentException`: flash, ни один файл не сохранён, ни одна запись не записана. Все файлы читаются и проверяются до того, как первый из них покинет временный каталог, поэтому альбом, отвергнувший один файл, не оставляет в хранилище половину своих картинок.
- `storeUpload()` кладёт файл в `@webroot/uploads/publications/ГГГГММ/` под случайным именем (`bin2hex(random_bytes(8))`), а расширение берёт из результата `getimagesize()`, а не из имени, которое придумал браузер: принимаются JPEG, PNG, GIF и WebP (`UPLOAD_IMAGE_TYPES`). Ссылка собирается из `getHostInfo()` и `@web`, то есть картинку отдаёт тот же веб-сервер и на тех же основаниях, что и остальное содержимое `web/`: `docker/nginx/default.conf` уже кэширует её на семь дней и принимает запрос до 32 МБ, `docker/php/php.ini` поднят до `upload_max_filesize=30M`, `post_max_size=32M`, `max_file_uploads=60`, а каталог `app/web/uploads/` в git не попадает.
- Крупный запрос отсекает веб-сервер раньше портала: `client_max_body_size 32m` в `docker/nginx/default.conf` не принимает тело больше 32 МБ и отвечает `413` само, до PHP такой запрос не доходит. Форма на это честна ровно настолько, насколько её слушатель: ответ не JSON, `postForJson` считает его неудачей, и страница показывает «Не удалось обновить списки: HTTP 413». Тело, которое PHP выбрасывает сам как большее `post_max_size`, — случай веб-сервера без своего предела: ни полей, ни файлов портал не получает, и `actionPublicationCreate` смотрит на `CONTENT_LENGTH` при пустом теле, отвечая flash-ом «Запрос больше разрешённого сервером размера…» вместо публикации с пустым текстом.
- Файл крупнее `upload_max_filesize` (30M), но мельче потолка веб-сервера, PHP забирает из запроса сам и помечает `UPLOAD_ERR_INI_SIZE`; `validatedUpload` читает код ошибки первым и отвечает «Файл «…» дошёл до сервера не полностью.» — это единственный способ увидеть предел PHP, потому что предел страницы (`imageUploadMaxMb`, по умолчанию 10M) строже обоих.
- Комментарии в `docker/php/php.ini` — только через `;`. Строка с `#` разбор не отбрасывает, а обрывает его (в сообщении ошибки оказывается скобка из текста комментария), и всё, что написано ниже, до PHP не доходит: пределы остаются системными 2M/8M/20, картинка крупнее 2M не доезжает до портала, а страница настроек между тем позволяет выбрать 10M и не подозревает, что PHP её обещание не выполнит.
- Файл после сохранения от ссылки ничем не отличается: в записи лежит список URL, поэтому повторное открытие публикации показывает загруженную картинку ссылкой на портал.

### Блок «Удаленные»

Блок «Удаленные» на странице публикаций выводит записи из `publications_deleted` по убыванию `updated_at` (самые свежие сверху). Бейдж статуса отражает фазу удаления: **«Удалено»** — сообщение ещё в канале (`deleted_at` пуст, его ждёт задача `telegram/delete-due`), **«Удалено из канала»** — сообщение уже удалено (`deleted_at` заполнен).

У элементов блока три кнопки-иконки, восстанавливающие запись без открытия формы (логика в `PublicationsService`):

- **«Опубликовать»** (`publishDeleted`) — запись удаляется из `publications_deleted` и добавляется в таблицу публикаций: `created_at` сохраняется, `published_at` и `updated_at` — текущее время, старый `telegram_id` сбрасывается (новое сообщение получит свой id после отправки в канал). Ожидающееся удаление из канала отменяется вместе с архивной строкой
- **«Запланировать публикацию»** (`scheduleDeleted`) — запись удаляется из `publications_deleted` и добавляется в таблицу публикаций с датой из модального окна: `created_at` сохраняется, `updated_at` — текущее время, `telegram_id` сбрасывается; задача `publishDue()` отправит пост в канал по наступлении `published_at`
- **«Перенести в черновик»** (`moveDeletedToDraft`) — запись удаляется из `publications_deleted` и добавляется в таблицу черновиков: `created_at` сохраняется, `updated_at` — текущее время (момент перемещения), `telegram_id` сбрасывается

Редактирование удалённой записи (карандаш или двойной клик) открывает форму «Новая публикация» с источником `deleted` и добавляет два сценария к таблице выше: кнопка **«Опубликовать»** восстанавливает запись как запланированный пост с датой из поля формы, кнопка **«Сохранить»** — как черновик; в обоих случаях архивная строка `publications_deleted` удаляется, а ожидающееся удаление из канала отменяется.

### Блок «Форум»

Страница публикаций разбита на два ряда: сверху на всю ширину идут блоки «Фильтры» и «Форум», ниже — два блока на половину ширины (`col-sm-6`), слева превью публикации, справа форма «Новая публикация». Разделение нужно затем, чтобы рост превью не сдвигал форму.

Поле ввода текста формы подстраивает высоту под содержимое (не больше 80% видимой области), но не при каждом нажатии клавиши, а через 5 секунд после последнего изменения: измерение высоты требует `height: auto`, на время которого поле схлопывается до двух строк и утаскивает за собой прокрутку страницы.

Блок «Форум» выводит топики форума awd.ru (таблица `topic`, только `login_required = FALSE`) по убыванию `published_at`; к каждому топику — его посты (таблица `post`, связь по `topic_id`) по убыванию `posted_at`. И то и другое начинается с первой страницы: порция задаётся настройками «Тем форума в блоке» (`forumTopicsPageSize`) и «Ответов в теме» (`forumPostsPageSize`, обе по 10 по умолчанию) — `ForumRepository::latestTopicsWithPosts($topics, $posts)` и `ForumRepository::topicPosts` читают их из `publications_setting`; дальше подключается прокрутка (см. «Бесконечная прогрузка списков»). Счётчик у топика показывает всё обсуждение, а не то, что сейчас видно: `postsTotal` приходит из той же выборки. Топики и посты переключаются по отдельности — см. «Сортировка списков».

У топика выводятся полностью, без обрезок: `source_url` (кликабельная ссылка), `title`, `published_at`, `content_text` (полный текст), `content_html` (полный HTML-исходник в свёрнутом блоке `<details>` — экранирован, поскольку исходный HTML форума содержит рекламные скрипты), `image_urls` (все изображения кликабельны). У постов: `number`, `title`, `published_at` (`posted_at`), `content_html`, `content_text` и `source_url` — тоже полностью. Имена и аватары авторов подтягиваются из таблицы `member` (при отсутствии аватара — иконка-заглушка).

Посты не выводятся, пока парсер их не сохранил: у недавно появившихся топиков постов ещё может не быть, тогда у топика отображается счётчик «0», а коробки прокрутки постов у него нет вовсе — догружать нечего.

#### Тред топика в форму

Рядом с кнопкой «Опубликовать» у топика стоят ещё две — «Тред целиком» и «Тред по частям» (`PublicationsUi::threadButtons`, `.forum-thread-btn`). Обе подставляют в форму текст топика и тексты всех постов его обсуждения; различаются они только тем, что делают с этими текстами, когда те пришли: первая складывает их в один, вторая отдаёт каждой сущности свою часть.

- Посты догружаются с сервера в момент нажатия: кнопка уходит POST на `/forum-thread` с `{topic}`, `SiteController::actionForumThread` читает всё обсуждение через `ForumRepository::topicThread`. Ни страниц, ни фильтров, ни статусов эта выборка не знает — в тред идут все строки `post` топика, включая уже опубликованные в канал. Одно правило блока сохраняет: топик, требующий авторизации, остаётся без треда (`t.login_required = FALSE`)
- Из поста в форму идёт только `content_text` — его `number`, заголовок и даты в ответ не попадают
- Сам топик не запрашивается: его текст, заголовок и альбом лежат в атрибутах кнопки «Опубликовать» этой же строки, куда их кладёт `_item_topic` (`threadEntities` достаёт их через `row.querySelector('.forum-publish-btn')`, поэтому кнопке треда не нужно нести тот же текст второй раз)
- Порядок постов задаёт сессия (`publicationsSort.forumPosts`), а не клиент: перевёрнутый блок отдаёт тред от старого поста к новому, первой частью при этом остаётся топик
- «Тред целиком» (`loadText`) собирает заголовок и текст топика и тексты постов через пустую строку в одно поле; не влезший в сообщение текст дорезает обычная разбивка — см. «Разбивка длинного текста на части»
- «Тред по частям» (`setTextParts`) кладёт топик первой частью, а каждый пост — отдельной. За лимит часть не выходит: каждый текст перед раскладкой проходит через `splitIntoParts`, так что сущность длиннее сообщения занимает несколько частей
- Сущность без текста частью не становится — `saveParts` пустую часть отвергает. Её изображения при этом не теряются: `threadTexts` фильтрует только тексты, `threadImageGroups` смотрит на все сущности треда, и альбом безымянной сущности доезжает до следующей части того же поля
- Каждой части — альбом её сущности: ссылки топика в первую часть (то есть в общее поле `publicationImages`), ссылки поста — в поле той части, куда лёг этот пост (`writeImages(index, …)`). Сущность, разрезанная на несколько частей, отдаёт весь свой альбом первой из них. Одна и та же ссылка топика и поста в одном поле не повторяется (`unionGroups`), а «Тред целиком» складывает все ссылки треда в общее поле первой части
- Альбом проходит тот же `writeImages`, что и любое заполнение формы, поэтому мёртвые ссылки отсекаются и здесь, и называются в замечании под тем полем, из которого их убрали (см. «Открытие на редактирование»)
- Форма, заполненная тредом, — новая запись: `publicationSource` становится `new`, а `forumEntityType` / `forumEntityId` — `topic` и id топика, так что сохранённые части привяжутся к обсуждению. Открытая на редактирование запись при этом закрывается и снимает свой бейдж
- Кнопок нет у топика без постов (`postsTotal = 0`): его тред — это и есть его текст, который уже отдаёт «Опубликовать»
- Пока тред грузится, обе кнопки молчат (`threadInFlight`), иначе второй ответ перезаписал бы поля формы посреди первого. Ответ не пришёл — flash `Не удалось загрузить тред: …`, и кнопки снова работают

#### Статусы топиков и постов

Топик и пост помечаются строкой в таблицах `publications_topic_map` / `publications_post_map`: `telegram_id IS NULL` — элемент отмечен кнопкой «Просмотрено» (`ForumRepository::markTopicViewed` / `markPostViewed`), заполненный `telegram_id` — опубликован в канале. В блоке «Форум» это бейдж «Просмотрено» или «Опубликовано» с дополнением `TG: <telegram_id>`; элемент без строки в таблице-маппинге считается непросмотренным и неопубликованным.

Если у топика ровно один привязанный пост, топик и этот пост — один и тот же элемент: «Просмотрено» и публикация в канал проставляются обоим, в обе стороны (`ForumRepository::mirrorSolePost` / `mirrorTopicOfSolePost`). Тот же `telegram_id` записывается и в вторую строку, но уже имеющийся `telegram_id` не перезаписывается — пост или топик могли быть опубликованы отдельным сообщением раньше. Топики с несколькими постами не зеркалятся: один обработанный пост ничего не говорит об остальных.

#### Фильтры блока «Форум»

Блок «Фильтры» над «Форумом» содержит два переключателя и слайдер: «С изображениями» (`withImages`), «С привязанными постами» (`withPosts`) и «Кол-во изображений» (`imagesCount`, `0` — без ограничения). Фильтры влияют только на выборку «Форума» (топики и их посты), списки публикаций, черновиков и удалённых записей не затрагивают; состояние хранится в нормализованном виде (`SiteController::normalizeForumFilters`).

- «С изображениями» оставляет топики, у которых есть свои изображения или хотя бы один пост с изображениями; списки постов сжимаются до постов с изображениями
- «Кол-во изображений» оставляет топики ровно с `imagesCount` изображений, а среди постов — посты ровно с `imagesCount` изображений
- «С привязанными постами» — правила ниже

Синхронизация фильтра с сессией и URL: состояние живёт в сессии (`forumFilters`) и является единственным источником истины, адресная строка — его зеркало.

- Любое изменение фильтра (переключение тумблера, отпускание слайдера) уходит на `site/forum-filter-save`, сохраняется в сессию и перезапрашивает блоки по ajax
- Ответ сервера содержит `url` — адрес, соответствующий сохранённому состоянию (`SiteController::publicationsUrl`, она же учитывает и порядок списков, см. «Сортировка списков»), и отрендеренный блок «Форум»; JS подставляет адрес в строку браузера через `history.replaceState` (`mirrorUrl`) и подменяет содержимое блока, целиком страницу не перезагружает
- При открытии страницы активный фильтр сессии приоритетен над GET-параметрами: перезагрузка или переход по ссылке не «включают» фильтр обратно. Если в сессии активного фильтра нет, она принимает параметры запроса. Когда URL не совпадает с состоянием сессии, `actionPublications` отвечает 302 на адрес из `publicationsUrl()`; сравнение идёт по нормализованным значениям фильтров и порядков, поэтому цикл редиректов невозможен
- Сессию очищает только кнопка «Очистить» в блоке фильтров (`site/forum-filter-clear`); порядок списков она не трогает — адрес после очистки остаётся с параметрами перевёрнутых блоков

Правила фильтра «С привязанными постами» (`ForumRepository::latestTopicsWithPosts` при `$withPostsOnly = true`):

1. у топика нет привязанных постов в таблице `post` — топик не показывается
2. топик непросмотрен и неопубликован — показываются все его привязанные посты, независимо от того, просмотрены или опубликованы они
3. топик просмотрен или опубликован, но среди его постов есть хотя бы один непросмотренный и неопубликованный — показываются все посты топика
4. топик не показывается, если и он сам, и все его привязанные посты просмотрены или опубликованы

Обработанные посты из правил 2 и 3 приходят в выборку со своими статусами, поэтому у них выводятся бейджи «Просмотрено»/«Опубликовано» и `TG: <telegram_id>`. Лимит «первые N постов» (`forumPostsPageSize`) сохраняется и при активном фильтре. Верх ползунка «Кол-во изображений» и потолок, который принимает сервер, — настройка `imagesCountFilterMax` (100 по умолчанию): значение выше неё `normalizeForumFilters()` снижает до неё же. Топик с единственным постом исчезает из выборки сразу после обработки любой из двух сторон — см. «Статусы топиков и постов».

### Сортировка списков

Блок «Публикации» выводит записи по убыванию `published_at`, блок «Черновики» — по убыванию `updated_at`, блок «Удаленные» — по убыванию `updated_at` (самые свежие сверху). Блок «Форум» сортируется по двум полям сразу: топики — по `topic.published_at`, посты внутри топика — по `post.posted_at`.

В шапке каждого из трёх блоков записей стоит переключатель «Сначала старые» (`.form-check.form-switch`, id `pubSortPosts` / `pubSortDrafts` / `pubSortDeleted`), в шапке «Форума» — два: «Сначала старые топики» (`pubSortForumTopics`) и «Сначала старые посты» (`pubSortForumPosts`). Переключатель разворачивает порядок своего списка: выборка идёт тем же `ORDER BY`, но по возрастанию, и вторичным ключом тоже по возрастанию (`PublicationRepository::order`, `ForumRepository::latestTopicsWithPosts`), поэтому страницы не перекрываются и в обратном порядке. Порядок относится к одному списку — остальные продолжают показывать то, на что читатель смотрел.

- Порядок хранится в сессии (`publicationsSort`, значения — реальные булевы `posts`/`drafts`/`deleted`/`forumTopics`/`forumPosts`), нормализует его `SiteController::normalizePublicationsSort`; всё, что не `true` и не `'1'`, оставляет список по умолчанию. По умолчанию это прямой порядок, а настройка «Порядок записей по умолчанию» (`blockOrderDefault`) переворачивает его у того, кто ещё ничего не переключал; переключатель в сессии важнее настройки
- Переключатель уходит POST на `/publication-sort` с `{block, oldest}`; сервер отвечает блоком, к которому переключатель принадлежит, отрисованным с первой страницы нового порядка, и `applyBlocks` подменяет только его разметку. Имя переключателя и имя блока — не одно и то же: `forumTopics` и `forumPosts` перерисовывают один и тот же блок `forum` (`SiteController::PUBLICATIONS_SORT_BLOCKS`)
- Так как лимит постов топика берётся в том же порядке, перевёрнутый блок «сначала старые посты» отдаёт самые старые посты обсуждения, а не самые свежие в обратном порядке; то же касается топиков
- Записи без даты остаются в конце списка при обоих порядках (`NULLS LAST` у даты топика и поста)
- Прокрутка блока после переключения продолжает уже новый порядок: `actionPublicationPage` читает сессию там же, откуда и первую страницу
- Перерисовка блока после переключения сбрасывает и остановку после сбоя: `resetPaging` снимает `failed`, и блок снова догружается до конца нового списка
- Если запрос о порядке не прошёл, переключатель возвращается в прежнее положение и показывает flash: список-то остался прежнего порядка, и положение тумблера не должно врать
- Порядок переживает перезагрузку страницы (он в сессии) и зеркалится в адресную строку, как фильтры «Форума»: перевёрнутый список даёт параметр `?postsOldest=1` / `?draftsOldest=1` / `?deletedOldest=1` / `?forumTopicsOldest=1` / `?forumPostsOldest=1`, а `publicationsUrl()` собирает из них вместе с фильтрами один адрес — `site/publications?withImages=1&postsOldest=1`
- Ответ `/publication-sort` несёт этот `url`, и JS подставляет его через `history.replaceState`; ответ `/publication-page` адреса не имеет, поэтому прокрутка списков в строку браузера не лезет
- При открытии страницы перевёрнутый список сессии приоритетен над параметрами адреса (перезагрузка не «возвращает» порядок), пустая сессия принимает GET; когда адрес не совпадает с состоянием, `actionPublications` отвечает 302 на `publicationsUrl()`

### Бесконечная прогрузка списков

Блоки «Публикации», «Черновики», «Удаленные» и «Форум» показывают не весь список, а первую страницу: `publicationPageSize` записей (настройка «Записей в блоке», 10 по умолчанию; «Форум» к ней добавляет свои две — см. «Блок «Форум»»). Сколько строк в списке всего, `actionPublications` отдаёт вместе с блоками (`totals`), поэтому браузер знает, есть ли что догружать.

- Прокручивается сам блок (его `.os-viewport` внутри `.scroll350`), а не страница. Когда до нижнего края остаётся не больше `__SCROLL_EDGE` (настройка «Отклик прокрутки», 80px по умолчанию), `loadNextPage` отправляет POST на `/publication-page` с `{block, offset}`
- Сколько прочитано в блоке, считается по строкам его собственного селектора (`__BLOCK_ROWS`): `.activity-log` у трёх списков записей и `.thread` у «Форума». Строка «Форума» содержит вложенные посты, поэтому число строк списка и число показанных элементов — разные величины
- Прокрутка не всплывает, поэтому слушатель на странице один — `scroll` на `document` в фазе перехвата; свой блок находится по `closest('.scroll350')` (`pagedBlockOf`). Прокрутка чужого блока, обсуждения внутри топика или окна страницы запроса не вызывает
- `actionPublicationPage` берёт следующий кусок списка через `PublicationsService::posts()` / `drafts()` / `deleted()` с `LIMIT`/`OFFSET` и возвращает уже отрендеренные строки: элементы живут в отдельных partials `_item_post` / `_item_draft` / `_item_deleted` / `_item_topic` / `_item_reply`, поэтому на клиент приходит разметка, а не записи. Кусок берётся в том порядке, который сейчас показывает блок (см. «Сортировка списков»)
- Ответ приносит новый `offset` и `total`; `offset >= total` — запросов больше нет. Ответ сервера — единственный источник того, сколько прочитано: JS не считает страницы сам
- Ошибка догрузки останавливает блок (`failed`) и показывает flash один раз: читатель стоит на том же нижнем крае, и повторный запрос уходил бы на каждый пиксель прокрутки
- Любое изменение данных (сохранение формы, публикация, перемещение, удаление) перезапрашивает блоки целиком: `applyBlocks` возвращает первую страницу и сбрасывает состояние прокрутки (`resetPaging`) по `totals` того же ответа
- Пустое состояние блок рисует вне списка элементов (`_block_*` выводит либо `<p>`, либо набор `_item_*`), поэтому догрузка не может продублировать «Публикаций пока нет»

#### Два уровня прокрутки в «Форуме»

«Форум» догружается двумя уровнями, и каждый спрашивает только своё:

- Топики идут через тот же `/publication-page` с `{block: 'forum', offset}`: `actionPublicationPage` вызывает `ForumRepository::latestTopicsWithPosts` с `OFFSET`, а `total` приносит `ForumRepository::countTopics()` — сколько топиков оставляют текущие фильтры
- Посты одного топика идут на `/forum-post-page` с `{topic, offset}` и возвращают только посты этого обсуждения (`ForumRepository::topicPosts`). Ответ имени блока не носит, поэтому ответ с чужим `topic` отбрасывается
- Обсуждение живёт в своей `<div class="thread-replies">` с `max-height` и `overflow-y: auto` (`app/web/ui-kit/assets/css/publication-editor.css`, `overscroll-behavior: contain`): первая порция постов (`forumPostsPageSize`) видна, остальные открываются прокруткой коробки. Полоса у неё обычная, браузерная: OverlayScrollbars навешивается только на `.scroll350` и только на document-ready, а коробки приходят после. Правило лежит именно в этом файле, а не в `app/web/css/site.css`: страницу ведёт layout `dashboard`, который подключает `DashboardAsset` и `PublicationEditorAsset`, а `site.css` входит только в `AppAsset` страниц `main` — правило, записанное туда, на портале не применяется
- Положение обсуждения JS не хранит — `data-topic`, `data-offset` и `data-total` лежат в разметке самой коробки, которую принёс сервер. Перерисовка блока фильтром или переключателем порядка возвращает каждое обсуждение на первую страницу нового набора бесплатно, а топик без постов остаётся без коробки
- Слушатель `scroll` сначала смотрит на `closest('.thread-replies')` и только потом ищет блок по `closest('.scroll350')`: коробка постов сидит внутри списка топиков, и без этого порядка её прокрутка читалась бы как нижний край списка — один жест грузил бы и топики, и посты
- Сбой считается раздельно: `failed` коробки глушит только её обсуждение, `failed` блока — только список топиков; `busy` у коробки свой, на DOM-узле (`__busy`), и в `paging`-состояния блоков не попадает
- Прокрутка в середине коробки и прокрутка обсуждения, которое показано целиком, запроса не вызывают: тот же `__SCROLL_EDGE`, что у блоков

Ограничение выборки `LIMIT`/`OFFSET`: если список меняется между догрузками одной страницы (появился новый пост, запись удалили), строка может повториться или оказаться пропущенной. Перезагрузка страницы и любое действие формы сбрасывают чтение на первую страницу. У постов топика то же самое: `topicPosts` нумерует их `ROW_NUMBER()` в порядке, который сейчас показан, поэтому страница не может перескочить или повторить пост, пока порядок и фильтры не менялись.

### Метки времени в списках

Каждый элемент списка показывает все даты, которые есть у его строки в БД (`PublicationsUi::dateMeta`): в «Публикациях» — `published_at` с подписью «Опубликовано», а при ещё не наступившей дате «Запланировано», затем `created_at` («Создано») и `updated_at` («Обновлено»); в «Черновиках» — только `created_at` и `updated_at`, поскольку колонки `published_at` у `publications_draft` нет; в «Удаленных» — все четыре, добавляется `deleted_at` («Удалено»), а дата публикации подписывается по тому же признаку, что и в «Публикациях»: запись могла попасть в архив до отправки в канал.

Пустое значение своей строки не выводит: `deleted_at` пуст, пока сообщение ещё ждёт задачи `telegram/delete-due`, и тогда остаётся только бейдж «Удалено». Значения в разметке остаются в UTC (атрибут `data-utc`), клиент подставляет их в часовом поясе пользователя (`renderUtcTimes`, `.utc-time`) — как и в остальных блоках страницы, и в том формате, который задан настройкой «Формат даты и времени» (см. «Страницы настроек»).

### Страницы настроек

Меню портала (`app/views/layouts/dashboard.php`) ведёт на две страницы настроек: «Настройки публикаций» (`/settings`, `SiteController::actionSettings`, вид `app/views/site/settings.php`) и «Настройки парсера» (`/parser-settings`, вид `parser-settings.php`). Пунктов-заглушек, которые вели в никуда (`href="#!"`), в боковом меню больше нет — ссылкой стало только то, что действительно открывается; в выпадающем меню пользователя такой пункт ещё живёт (см. «Профиль» в шапке).

#### Настройки публикаций

Кроме карточек описания канала и его архива страница несёт форму всех подстраиваемых величин страницы публикаций. Каждая величина описана один раз — в схеме `PublicationSettingsService` (`app/shared/Settings/Service/PublicationSettingsService.php`): подпись поля, тип, границы, единица измерения и подсказка под полем. Из той же схемы миграция `m260925_000001_create_publications_setting` сеет таблицу `publications_setting` (строка `code` → `value` на каждую величину), поэтому дефолты приложения и дефолты базы не могут разойтись.

| Настройка | Код | По умолчанию | Границы |
|---|---|---|---|
| Записей в блоке | `publicationPageSize` | 10 | 1–100 |
| Тем форума в блоке | `forumTopicsPageSize` | 10 | 1–100 |
| Ответов в теме | `forumPostsPageSize` | 10 | 1–200 |
| Отклик прокрутки | `scrollEdgePx` | 80 | 0–400 |
| Шаг минут в выборе времени | `scheduleMinuteStep` | 10 | 1–30 |
| Глубина выбора даты | `scheduleHorizonHours` | 32 | 1–168 |
| Ожидание проверки картинки | `imageProbeTimeoutMs` | 6000 | 500–30000 |
| Превью изображений в форме | `imagesPreviewLimit` | 10 | 1–20 |
| Размер загружаемого файла | `imageUploadMaxMb` | 10 | 1–30 |
| Файлов в альбоме части | `imageUploadLimit` | 10 | 1–20 |
| Картинки в сохранённой записи | `imagesShownLimit` | 4 | 1–20 |
| Поиск границы при ручной разбивке | `splitSnapRangeChars` | 600 | 50–2000 |
| Верх фильтра «Кол-во изображений» | `imagesCountFilterMax` | 100 | 1–1000 |
| Интервал между частями публикации | `partsOffsetMinutes` | 1 | частота `publish-due`–1440 |
| Порядок записей по умолчанию | `blockOrderDefault` | `newest` | `newest` / `oldest` |
| Формат даты и времени | `dateFormat` | `d.m.Y H:i` | три формата из `DATE_FORMATS` |

Первые три и `scrollEdgePx` правят прокруткой списков (см. «Бесконечная прогрузка списков»), `imageProbeTimeoutMs` и `splitSnapRangeChars` — поведением формы (см. «Открытие на редактирование» и «Разбивка длинного текста на части»), `imagesPreviewLimit` — числом превью под полем альбома, `imageUploadMaxMb` и `imageUploadLimit` — файлами, которые альбом берёт с компьютера (см. «Файлы альбома»), `imagesShownLimit` — числом картинок, которые рисует элемент списка (`PublicationsUi`), `scheduleMinuteStep` и `scheduleHorizonHours` — шагом минут и дальностью выбора даты публикации, `imagesCountFilterMax` — ползунком фильтра «Форума», остальные — тем, что следует из их подписей.

- Числа читаются через `all()`, `value()` и `intValue()`: значение, которого в таблице нет или которое вышло за границы, возвращается границей (`normalize()`), а неизвестный вариант выбора — дефолтом, поэтому вызывающему коду не надо проверять то, что он прочитал. Писание наоборот: `save()` отвергает первую же неподходящую величину `InvalidArgumentException`-ом, страница показывает flash и не сохраняет ничего. Один запрос читает таблицу один раз — значения держатся в кэче сервиса.
- «Интервал между частями публикации» упирается в пол, которого у него в схеме нет: части не могут уходить в канал чаще, чем задача, которая раз за разом смотрит в очередь на публикацию. Частота этой задачи живёт в `.env` (`TELEGRAM_PUBLISH_CRON_SCHEDULE`), `cronIntervalMinutes()` вычитает её из расписания (`*/n`, `*`, список минут — с учётом перехода через полночь; нераспознанное расписание даёт 1), а на странице она только показана: карточка «Очередь публикации» печатает расписание как есть, а подсказка поля — нижнюю границу. Тот же пол держит и `saveParts()`, который сдвигает `published_at` частей, и форма, которая его отправляет: записанное ниже границы значение при чтении поднимается до границы, а попытка сохранить его отвергается.
- «Порядок записей по умолчанию» задаёт, как стоят блоки у того, кто ещё ничего не переключал; переключатель в шапке блока, записанный в сессию, важнее настройки (см. «Сортировка списков»).
- «Формат даты и времени» — один формат на весь портал: `DATE_FORMATS` переводит его в токены моментума, которыми говорит выбор даты и клиентская подстановка времени из UTC (`utcToPickerValue`, `renderUtcTimes`), а PHP-виды форматируют даты тем же значением через `asDatetime('php:…')` (смена формата потому не требует правки ни одной страницы).
- Карточка «Лимиты Telegram» перечисляет числа, которые задаёт сам Telegram, а не портал (`telegramLimits()` над константами `ChannelService` и `LinkButton`): 4096 символов текста сообщения, 1024 подписи, 255 описания канала, 10 картинок в альбоме, резерв под строку «Часть N» и пределы кнопки-ссылки — 64 байта надписи и 2048 символов адреса. Они показываются и не редактируются: длиннее лимита текст не примет API, а не это приложение.

#### Настройки парсера

Страница делит `parser_config` на две карточки. «Запрос к форуму» — поведение HTTP: ожидание ответа страницы, число повторов, пауза перед повтором (мкс), бюджет редиректов, коды ответов, на которые запрос повторяется, адрес входа на форум, страниц на одну сущность и часовой пояс источника («Диапазоны источников» — `base_url`, `t_from`, `t_to` и активность каждой строки конфигурации).

- Числовые величины замкнуты в `ParserSettingsService::bounds()` (1–300 секунд, 0–10 повторов, 0–5000000 мкс паузы, 0–20 редиректов, 1–100000 страниц), коды ответов читаются списком через запятую и проверяются на формат статуса HTTP, адреса — на `http(s)`, часовой пояс — по `DateTimeZone::listIdentifiers()`, диапазон сущностей — на неотрицательность и `t_from <= t_to`. Неподходящее значение — `InvalidArgumentException` до первой записи, flash на страницу.
- Восемь «поведенческих» колонок относятся ко всему парсингу сразу, а не к одной строке конфигурации, поэтому форма пишет их во все строки одним `UPDATE`, а сервис читает из первой (`ForumRepository::parserTunables()`). Пока таблица пуста, `tunables()` отдаёт `ParserSettingsService::DEFAULTS` — те же числа, что сеет миграция `m260925_000002_add_parser_tunables_to_parser_config`.
- Отсюда эти числа попадают туда, где раньше были зашиты: `ForumHttpClient` получает таймаут, повторы, паузу, адрес логина, бюджет редиректов и список кодов, парсеры страниц — часовой пояс сайта (`ForumPageDomParser::$siteTimezone`), обходчики постов и альбомов — потолок страниц (`maxPages`). И web- и console-состав (`app/config/web.php`, `app/config/console.php`) собирают их одинаково, а `ParserSettingsService` — синглтон, так что один проход читает таблицу один раз.

#### Секреты и режим отладки

`cookieValidationKey`, `YII_DEBUG` и `YII_ENV` из кода убраны и живут в `.env`: `COOKIE_VALIDATION_KEY` (генерация — `php -r "echo bin2hex(random_bytes(32));"`), `YII_DEBUG`, `YII_ENV`; compose прокидывает их в контейнер, а `app/web/index.php` и `app/yii` читают через `getenv()`. Без этих переменных приложение работает как production, а без ключа Yii не подписывает cookies сессии и CSRF, то есть не принимает ни один запрос, который их несёт. Ни на одной странице настроек эти значения не показываются — страница настроек не место для секретов.

### Стили и скрипты страниц

Ничего не собирается: каждый файл лежит в `app/web/` и подключается bundle-ом Yii — `AppAsset` для старой разметки (`_head.php`: вход, «О программе», «Контакты», страница ошибки), `DashboardAsset` для порталовых страниц (`dashboard.php`), `PublicationEditorAsset` поверх последнего для редактора публикаций. Две раскладки не пересекаются, поэтому на одной странице `AppAsset` и `DashboardAsset` не встречаются.

- **jQuery на странице ровно один, и это копия из ui-kit.** `assetManager.bundles` в `app/config/web.php` переопределяет `yii\web\JqueryAsset`: вместо `@bower/jquery/dist` он публикует `app/web/ui-kit/assets/js/jquery.min.js` (в `publishOptions.only` — один этот файл), а `DashboardAsset` приносит `JqueryAsset` через `$depends`, чтобы его плагины встали в HTML после него. Копии совпадают версией (обе 3.7.1), поэтому двойной jQuery не ломал вёрстку — он молча убивал поведение: любой bundle, просящий jQuery (а это каждый `yii\bootstrap5\Widget`), печатал копию Yii второй, `window.jQuery` становился тем вторым объектом, а плагины, зарегистрированные на первом, исчезали со страницы — пропадали выбор даты и прокрутки списков. На странице публикаций `initAll()` спотыкался о первый же вызов `daterangepicker` — уже после того, как поставил себе `runOnce`, — и форма не инициализировалась вовсе.
- **Иконки — тот файл, что уже несёт ui-kit.** `AppAsset::$css` подключает `ui-kit/assets/fonts/bootstrap/bootstrap-icons.css` (у `DashboardAsset` он в `$css` был и раньше), а `yii\bootstrap5\BootstrapIconAsset` не подключается нигде: он публикует `@vendor/twbs/bootstrap-icons/font`, а этого пакета в зависимостях нет — `twbs/bootstrap-icons` числится лишь необязательной зависимостью `yii2-bootstrap5`, которая прямо предлагает добавить её самому. Пока за иконками просили именно bundle-ом, `InvalidConfigException` получался на каждой странице, собранной через `main.php`.

### Логотип и фавикон

Знак TRVL — «большой круг»: окружность, нарисованная как маршрут (сплошная дуга — пройденное плечо, пунктир — плечо впереди, оранжевое кольцо — точка назначения), и надпись TRVL на хорде этого круга. Два цвета: чернильный `#64739e` и акцентный `#e0713a` — только у точки. Векторные рисунки лежат рядом с остальными картинками веб-документов: `app/web/images/trvl-logo.svg` (словесный знак, 200×57), `app/web/images/trvl-mark.svg` (то же в квадрате 64×64) и `app/web/favicon.svg` (иконка вкладки, 32×32). У всех проставлены `width`/`height` наряду с `viewBox`: без них браузер не знает естественного размера SVG, а шапка ui-kit ограничивает логотип только сверху (`max-height: 46px`), поэтому картинка схлопывается в нуль.

- `app/views/layouts/dashboard.php` берёт их из `@web/images` (`$brandUrl`): в сайдбаре — словесный знак (`.app-brand .logo-full`, 161×46 в боксе 250 px), в мобильной шапке — квадратная марка (`.app-brand-sm .logo`, 46×46). Логотипы ui-kit (`ui-kit/assets/images/logo*.svg`) больше нигде не подключаются.
- Кнопка «закрепить» (`#pin-sidebar`) сужает сайдбар до 70 px, а `.app-brand` просто обрезает всё, что не влезло: от словесного знака оставалось кольцо с огрызком первой буквы. Поэтому в бокс положены обе картинки, и `registerCss` в закреплённом состоянии прячет `.logo-full`, показывая вместо него `.logo-mini` в 46×46.
- Фавикон — не уменьшенный знак, а перерисованный: пунктирное плечо и линейка-хорда на 16 px рассыпаются в грязь, поэтому в кольце остаётся одна буква T.
- Ссылки на иконку отдаёт общий partial `app/views/layouts/_favicon.php`: SVG как `rel="icon"` и прежний `app/web/favicon.ico` как `rel="alternate icon"` для клиентов, которые просят `/favicon.ico` сами. Partial подключён и из `_head.php` (старая разметка логина/ошибок), и из `dashboard.php`, так что правило живёт в одном месте.
- Страницы логина, «О программе», «Контакты» и подвал старой разметки остаются на логотипе Yii (`yii3_full_*` в `app/web/images/`) — там своя, не порталовая вёрстка.
- Лист сравнения десяти вариантов, из которого взят «большой круг», лежит рядом в `trvl-logos/` (`index.html` + папки `01-disc/ … 10-map/`) и в репозиторий не входит: каталог исключён локально в `.git/info/exclude`, так что на другой машине его может не быть.

## Публикации в канал

Подробная документация по функциональности публикаций и интеграции с Telegram каналом вынесена в отдельный файл [PUBLICATIONS.md](PUBLICATIONS.md).

Краткий обзор:

- Публикации хранятся в четырёх таблицах: `publications_post` (основные посты), `publications_draft` (черновики), `publications_edited` (история редактирования), `publications_deleted` (soft-delete архив)
- Отправка в Telegram выполняется исключительно через периодические задачи (`telegram/publish-due`, `telegram/delete-due`, `telegram/edit-due`), а не напрямую из формы
- Управление каналом Telegram (описание, посты, закрепление, удаление) реализовано в `ChannelService`
- Клиент канала ждёт ответа 30 секунд (`NutgramChannelClient::REQUEST_TIMEOUT`): пять секунд, которые Nutgram просит по умолчанию, уходят не на ответ API, а на установку соединения — первый вызов прохода мерился на локальном портале пятнадцатью секундами, а задача, не дождавшаяся ответа, повторяется через пять минут
- Консольные команды доступны через `TelegramController` (`php yii telegram/*`)
- Конфигурация требует `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHANNEL_ID` в `.env`; там же живут `COOKIE_VALIDATION_KEY`, `YII_DEBUG`/`YII_ENV` и `TELEGRAM_PUBLISH_CRON_SCHEDULE`

Для полной информации см. [PUBLICATIONS.md](PUBLICATIONS.md).

## Адреса страниц

Страницы и эндпоинты доступны по коротким путям: `/` — дашборд, `/publications` — страница публикаций, `/settings` — «Настройки публикаций», `/parser-settings` — «Настройки парсера», `/login`, `/contact`, `/about`, `/captcha`, а также POST-эндпоинты `/publication-create`, `/publication-publish`, `/publication-to-draft`, `/publication-schedule`, `/publication-delete`, `/publication-page`, `/forum-post-page`, `/forum-thread`, `/publication-sort`, `/channel-description`, `/forum-viewed`, `/forum-filter-save`, `/forum-filter-clear`, `/settings-save`, `/parser-settings-save`. Плоские имена совпадают с id действий `SiteController`, поэтому перечень правил в `app/config/web.php` (`urlManager`, `enablePrettyUrl` + `showScriptName => false`) и есть список публичных адресов.

Фильтры блока «Форум» в правилах не участвуют и остаются строкой запроса: `/publications?withImages=1&withPosts=1&imagesCount=3`.

Маршрутам вне списка (`site/error`, модули `gii` и `debug`) правила не нужны: при `enableStrictParsing => false`, если ни одно правило не совпало, путь сам становится маршрутом, а `Url::to()` для такого маршрута выдаёт форму `/controller/action`. Вид `?r=` при включённом `enablePrettyUrl` не читается, поэтому сохранённые раньше адреса вроде `/index.php?r=site%2Fpublications` открывают дашборд.

`index.php` из адреса убирает веб-сервер: `app/web/.htaccess` в Apache-варианте и `try_files $uri $uri/ /index.php?$query_string;` в `docker/nginx/default.conf` и в nginx-конфиге Windows-окружения — конфиги менять не потребовалось.

## Релизы

Релизы публикуются автоматически на [GitHub Releases](https://github.com/Resident234/awd/releases) через GitHub Actions (`.github/workflows/release.yml`).

Порядок выпуска релиза:

1. Добавить в `CHANGELOG.md` секцию `## [X.Y.Z] - ГГГГ-ММ-ДД` (формат Keep a Changelog)
2. Закоммитить и запушить изменения в `master`
3. Создать и запушить тег:

```
git tag vX.Y.Z
git push origin vX.Y.Z
```

Workflow срабатывает на пуш тега `v*`: извлекает секцию соответствующей версии из `CHANGELOG.md` (префикс `v` срезается автоматически) и создаёт релиз с именем тега и телом из заметок CHANGELOG. Если такой релиз уже существует, его тело не перезаписывается — при необходимости обновить заметки пересоздайте релиз или отредактируйте его вручную.
