# Changelog

Все значимые изменения проекта TRVL документируются в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии следуют [SemVer](https://semver.org/lang/ru/). Даты указаны в формате ISO 8601 (YYYY-MM-DD).

## [0.1.0] - 2026-09-08

Первая рабочая версия системы парсинга форума forum.awd.ru (исходные данные для канала TRVL). Реализована бывшая TODO 1: парсинг сущностей со всеми необходимыми данными, организация модели данных, периодический запуск с обновлением существующих данных — весь диапазон проходится заново, записи upsert'ятся.

### Добавлено

#### Парсер тем (`forum-parser/scan`, конфиг `awd_forum_topics`)

- Перебор `t` в диапазоне 0–500000 (`viewtopic.php?t=`), полная структура темы: заголовок, дата, автор, текст, изображения, метки времени
- Обход закрытых разделов: темы, требующие авторизацию, сохраняются заглушками `login_required = true`
- HTTP 404 и сетевые ошибки не останавливают проход; счётчики processed / saved / updated / not_found / login_required / failed

#### Парсер постов тем (`forum-post-parser/scan`, конфиг `awd_forum_posts`)

- Постраничный обход топиков (пагинация `start=N`, 50 постов на страницу), извлечение каждого поста: id (`p`-параметр), номер в теме, заголовок, дата, контент (HTML и текст), автор со всеми полями профиля из блока поста
- Дедупликация повторяющегося открывающего поста на первой странице
- Обрабатывает только топики, уже существующие в таблице `topic` (двигается по диапазону вслед за сканером тем)

#### Парсер альбомов галереи (`gallery-parser/scan`, конфиг `awd_gallery_albums`)

- Перебор `album_id` в диапазоне 0–500000 (`gallery/album.php?album_id=`)
- Две таблицы: `gallery_album` (id, ссылка, название, имя пользователя) и `gallery_image` (id из `image_id`, название, ссылка на полноразмерное изображение, ссылка на страницу изображения, привязка к альбому FK)
- Имя пользователя — 4-й элемент навигации личных альбомов (`Список форумов › Галерея › Личные альбомы › <имя> › <альбом>`), у общих альбомов NULL
- Обход пагинации изображений (100 на страницу, `start=N`), страницы мержатся в один upsert

#### Парсер профилей пользователей (`member-parser/scan`, конфиг `awd_forum_members`)

- Перебор `u` в диапазоне 0–500000 (`memberlist.php?mode=viewprofile&u=`)
- Две вкладки профиля: основная (имя, звание, аватар, страна, город, возраст, пол) и статистика `page=7` (Зарегистрирован, Последнее посещение, Всего сообщений, Фотографий)
- Нормализация дат phpBB: «24 дек 2011, 22:42», «Сегодня/Вчера», относительные «N минут назад», «менее минуты назад»
- Данные вкладок мержатся в одну запись `member`; поля, которых нет на страницах профилей (спасибо выдано/получено из блоков постов), не затираются

#### Авторизация на форуме

- Профили и memberlist доступны только авторизованным; `ForumHttpClient` автоматически логинится через `ucp.php?mode=login` под учётной записью из `.env` (`FORUM_LOGIN_USERNAME` / `FORUM_LOGIN_PASSWORD`), держит phpBB-сессию в памяти и повторяет запрос после ответа «вы должны быть авторизованы»
- Cookies собираются через header-function (cURL cookie-jar файл ненадёжен под HTTP/2); успешность входа контролируется по куке `u ≠ 1`
- Без заданных учётных данных клиент работает гостем — остальные парсеры не затронуты

#### Модель данных (PostgreSQL, миграции)

- `m260828_000001`: `parser_config` (конфиги диапазонов и расписаний, advisory-lock ключи, `last_run_at`), `member` (профили пользователей), `topic` (темы) + сид `awd_forum_topics`
- `m260904_000002`: `topic.login_required` для заглушек закрытых разделов
- `m260906_000003`: `post` (посты тем, FK к `topic` и `member`) + сид `awd_forum_posts`
- `m260907_000004`: `gallery_album`, `gallery_image` (FK к альбому) + сид `awd_gallery_albums`
- `m260907_000005`: `member.last_visit_at`, `member.photos_count`, `member.profile_login_required` + сид `awd_forum_members`

#### Периодический запуск

- Cron-контейнер (supercronic), расписание каждого парсера в `.env`: `PARSER_CRON_SCHEDULE`, `FORUM_POST_PARSER_CRON_SCHEDULE`, `GALLERY_PARSER_CRON_SCHEDULE`, `MEMBER_PARSER_CRON_SCHEDULE`
- Защита от параллельного запуска одного парсера: session-level advisory lock по `crc32`-ключу кода конфигурации; упавший процесс не блокирует следующий запуск
- Все четыре парсера работают одновременно по независимым локам; upsert в коротких транзакциях — по одной сущности за транзакцию
- Каждый проход начинает диапазон заново и обновляет существующие записи (upsert) — это ожидаемое поведение до реализации TODO «постоянно живущий парсер с пропуском неизменённых»

#### Инфраструктура

- Слоистая архитектура (Application → Shared → границы через контракты): тонкие console-команды, сервисы сканирования, парсеры DOM/XPath, репозитории с SQL, HTTP-клиент — все детали за интерфейсами, сборка в composition root (`config/console.php`)
- Автоматический вход (login) HTTP-клиента при получении страницы с формой авторизации
- Сборка образов, docker compose (postgres, app/php-fpm, nginx, parser/cron), обновление entrypoint требует пересборки образа parser (`docker compose build parser`)
- Юнит-тесты (Codeception): парсеры всех четырёх типов страниц, сервисы сканирования, нормализация дат, статистика, блокировки — 72 теста
- Статический анализ: phpstan 0 ошибок, phpcs (Yii2 coding standard) 0 ошибок

### Известные ограничения

- Полный диапазон 0–500000 проходится при каждом запуске, включая несуществующие id (404); оптимизация «пропускать неизменённые» — TODO «постоянно живущий парсер»
- Оценка времени полного прохода одного диапазона при расписании `*/10`: порядка нескольких дней непрерывной работы (скорость ~15–20 id/мин по темам с учётом 404 и обновлений)
- Ссылки на изображения галереи ведут на файлы в `images/upload` — при удалении файла с форума ссылка устареет до следующего прохода
- Учётные данные форума в `.env` в открытом виде (для dev-окружения)

### Добавлено

#### Сортировка топиков «Форума» по длине текста

- В шапке блока «Форум», рядом с переключателями порядка и перед счётчиком топиков, стоит пара кнопок «Сначала короткий текст» / «Сначала длинный текст» (`btn-group` из двух `input.btn-check` с `label.btn-outline-primary`, id `pubForumTextAsc` / `pubForumTextDesc`): нажатие одной снимает другую, повторное нажатие уже нажатой убирает сортировку, и список возвращается к порядку по дате. Задевает это только топики — посты каждого обсуждения продолжают идти в своём порядке дат
- Миграция `m261001_000001_add_text_length_to_topic`: у `topic` появляется обычный `integer NOT NULL DEFAULT 0` столбец `text_length`, которым миграция считает уже сохранённые тексты, а дальше его пишет парсер (`ForumRepository::saveTopic()` считает `mb_strlen()` по тому же `content_text`; `char_length()` PostgreSQL даёт то же число). Считать длину на чтении — пройтись по тексту каждого топика до `LIMIT`: на 58 922 топиках прогретая выборка стоит 1,2 с против 0,17 с с готовым числом, поэтому сортировка идёт по сохранённому целому, как и счёт ссылок
- `ForumRepository::latestTopicsWithPosts` принимает `$textOrder`: `'asc'` и `'desc'` дают `ORDER BY t.text_length …, t.id …` тем же направлением, любое иное значение оставляет порядок по датам с `NULLS LAST`. Вторичный ключ повёрнут вместе с сортировкой, поэтому страницы, которые догружает прокрутка блока, не перекрываются, а `countTopics()` не меняется — набор строк тот же
- Состояние пары живёт в сессии ключом `forumTextOrder` (`''` | `'asc'` | `'desc'`, `normalizeForumTextOrder()`); `syncForumTextOrder()` при открытии страницы отдаёт приоритет сессии, которая уже держала порядок, пустая принимает `?forumTextOrder=asc|desc` из адреса, `publicationsUrl()` зеркалит параметр в строку браузера, а несовпадение адреса с сессией уходит 302
- Нажатие кнопки уходит POST на `site/forum-text-order-save` с `{forumTextOrder}` — пустое значение означает снятую сортировку. Ответ приносит перерисованный с первой страницы блок `forum`, `totals` того же состояния и адрес для `mirrorUrl`; целиком страница не перезагружается. Отказ запроса возвращает обе кнопки в положение, которое показывала страница, и показывает flash

#### Переключатель «Первая строка — в заголовок»

- В шапке карточки «Новая публикация», справа от её заголовка, стоит `form-switch` «Первая строка — в заголовок» (`publicationTitleFromFirstLine`) с поповером на всей группе: при подгрузке из блока «Форум» первую строку текста он пишет в поле «Заголовок» той части, куда лёг этот текст, а остальное оставляет в тексте. У тофика первой строкой стоит его название — кнопка ставит его перед текстом, у поста — первая набранная им строка
- Текст разбирает `firstLineAsHeading()` — одна функция на трёх местах подгрузки («Опубликовать» топика, «Опубликовать» поста, «Тред целиком» и «Тред по частям»). Снятая строка из текста исчезает, а не повторяется в двух полях; текст из одной строки не режется — если за первой строкой ничего не осталось, поле заголовка пустое, а текст приходит целиком (пустую часть отвергает `assertPartValid()`). В «Треде по частям» заголовок берёт на себя только первая часть, в которую лёг топик
- Состояние переключателя живёт в сессии ключом `titleFromFirstLine` — там же, где фильтры форума и порядок списков: `actionPublications()` решает его через `syncTitleFromFirstLine()` (сессия, которая уже держала переключатель, не даёт ссылке его повернуть; которая не держала — принимает `?titleFromFirstLine=1` из адреса), `publicationsUrl()` возвращает этот параметр в строку браузера, а `site/title-from-first-line-save` (POST) пишет сессию и отвечает адресом, который страница подставляет через `mirrorUrl`. Ничего на странице ради него не перерисовывается, и в `publication-create` состояние не уходит — очистка формы его не трогает, перезагрузка страницы приносит переключатель в том же положении.

#### Удаление публикаций и черновиков (soft-delete)

- Миграция `m260912_000012`: `publications_deleted.published_at` становится nullable — черновики сохраняют пустое `published_at` при перемещении в архив
- Кнопка «Удалить» в блоках «Публикации» и «Черновики» перемещает запись в `publications_deleted`: `created_at` и `published_at` сохраняют значения, `updated_at` — текущее время, `deleted_at` остаётся пустым

- `PublicationsService::deleteDue()`: записи без `telegram_id` (черновики, запланированные посты) закрываются сразу без обращения к Telegram

#### Периодическое редактирование в канале

- Сценарий `PublicationsService::editDue()`: записи из `publications_edited` с пустым `edited_at` редактируются в канале по `telegram_id` — содержимое сообщения заменяется значением поля `text` (по возрастанию id), после чего в `edited_at` ставится время фактического изменения; каждая запись обрабатывается независимо, сбой логируется и не останавливает остальные, неудачные повторяются на следующем запуске
- Telegram-слой: `editChannelMessageText` в контракте и Nutgram-адаптере (editMessageText Bot API), `ChannelService::editPostText()`
- Репозиторий публикаций: `findPendingChannelEdits()`, `storeEditedAt()`
- Консольная команда `telegram/edit-due`; cron-задача с расписанием `TELEGRAM_EDIT_CRON_SCHEDULE` (по умолчанию `*/5 * * * *`)

#### Периодическое удаление из канала

- Миграция `m260912_000011`: `publications_deleted.deleted_at` становится nullable — пустое значение означает, что soft-deleted запись ещё не удалена из канала
- Сценарий `PublicationsService::deleteDue()`: записи из `publications_deleted` с пустым `deleted_at` удаляются из канала по `telegram_id` (по возрастанию id), после чего в `deleted_at` ставится время фактического удаления; каждая запись обрабатывается независимо, сбой логируется и не останавливает остальные, неудачные повторяются на следующем запуске, кроме отсутствующего в канале сообщения — см. «Отсутствующее в канале сообщение закрывает запись»
- Telegram-слой: `deleteChannelMessage` в контракте и Nutgram-адаптере (deleteMessage Bot API), `ChannelService::deletePost()`
- Репозиторий публикаций: `findPendingChannelDeletion()`, `storeDeletedAt()`
- Консольная команда `telegram/delete-due`; cron-задача с расписанием `TELEGRAM_DELETE_CRON_SCHEDULE` (по умолчанию `*/5 * * * *`)

#### Модель данных публикаций

- Таблица `publications_draft` (миграция `m260910_000008`): текст, изображения (`jsonb`, массив ссылок), дата-время создания, дата-время обновления — черновики до отправки в Telegram

### Изменено

#### Дамп суперглобальных переменных убран из журнала

- У обоих `FileTarget` (`app/config/web.php`, `app/config/console.php`) выставлен `logVars => []`: Yii дописывал к каждой выгрузке дампы `$_GET`, `$_POST`, `$_FILES`, `$_COOKIE`, `$_SESSION` и `$_SERVER`, а в console-процессе `$_SERVER` — это всё окружение контейнера, поэтому в `app/runtime/logs/app.log` лежали `TELEGRAM_BOT_TOKEN`, `DB_PASSWORD` и `FORUM_LOGIN_PASSWORD` (773 таких дампа)
- В веб-конфиге та же настройка закрывает пароль из формы входа и cookies сессии: они попали бы в `$_POST` и `$_COOKIE` при любой ошибке запроса
- Отладочный контекст в дампе не теряется: причины пишутся в текст записи (`{"id":24,"error":"cURL error 7: …"}`, `topic_id`, счётчики статистики), а не в суперглобальные
- Правка не ретроактивна: записанные до неё строки остаются в `app/runtime/logs/app.log` (каталог в git не попадает), а токен бота стоит повернуть через @BotFather

#### Блоки страницы публикаций собраны по разметке kanban-доски

- Карточки «Фильтры» и «Форум» страницы `/publications` объединены в один блок на всю ширину: обе стоят в контейнере `kanban-items ui-sortable`, завёрнутом в белую `card mb-4 p-3`, колонка — `kanban-board`; каждая карточка — `card p-3 border border-danger to-do` с заголовком `icon-box sm … bi-list-task …` и круглым счётчиком справа; разметка взята из доски `ui-kit/tasks.html`
- Превью публикации и форма «Новая публикация» объединены в один блок на всю ширину — раньше они стояли бок о бок в двух `col-sm-6`, и рост превью двигал форму; теперь обе карточки в одном контейнере `kanban-items ui-sortable`, превью над формой, а цвета взяты из колонки «In Progress» той же доски: `card p-3 border border-warning in-progress` с заголовком `icon-box sm … bi-hourglass-split text-warning …` вместо обычного `card-header`; счётчика справа в этих заголовках нет — блоки показывают одну часть, а не список
- Счётчик «Фильтров» показывает, сколько из трёх фильтров включено, счётчик «Форума» — сколько топиков они оставляют; второй обновляется из `totals` того же ajax-ответа, что и список, первый пересчитывается по положению тумблеров и слайдера
- `site/forum-filter-save` и `site/forum-filter-clear` начали отдавать `totals` вместе с блоком — без них переключённый фильтр оставлял счётчик топиков и состояние прокрутки блока от прежней выборки (57847 вместо 9197 при «С изображениями»)
- Подсказка в карточке фильтров переформулирована: «Фильтры применяются к топикам ниже» — блок «Форум» теперь и есть тот же блок
- Класс `preview-card` переехал с внешней белой карточки на жёлтую, поэтому правило `.preview-card > .card-body` продолжает работать как работало
- У `card-body` и `card-footer` внутри жёлтых карточек отступы обнулены (под разделительной чертой подвала остались 0.5rem): содержимое в них отодвигает от цветной рамки только `p-3` самой карточки, как в красных, а не `p-3` плюс собственные 1rem Bootstrap'овского `card-body`
- Переключатели порядка форума («Сначала старые топики», «Сначала старые посты») переехали из отдельного ряда под заголовком в саму строку заголовка: правая часть, перед круглым счётчиком топиков, в одном `d-flex flex-wrap align-items-center gap-3` с ним — на узкой ширине они переносятся на вторую строку заголовка вместо того, чтобы вылезать за карточку; id и поведение остались прежними

#### Отсутствующее в канале сообщение закрывает запись

- `PublicationsService::deleteDue()` больше не повторяет вечно удаление сообщения, которого в канале нет: ответ `message to delete not found` означает, что нужного результата уже достигли, и запись получает `deleted_at` как обычное удаление
- `TelegramApiException::isMessageGone()` — единственный способ это распознать: Telegram несёт в таком ответе только текст описания, регистра он не гарантирует
- Причина разбора: строки архива 6 и 7 (тестовые публикации) падали каждые пять минут с момента появления задачи — у строки 7 `telegram_id` смещён на единицу («test-post» занимает в канале 5608, а не 5609), строка 6 получила `message can't be deleted` при полном наборе прав администратора, её `deleted_at` проставлен вручную, сообщение 5614 в канале осталось

#### Очередь публикаций вынесена из контейнера парсера

- В `docker-compose.yml` появился сервис `telegram`, собранный из того же `docker/php-cli`: в нём живут `telegram/publish-due`, `telegram/delete-due` и `telegram/edit-due`, а сервис `parser` остался один на четыре скана форума и Telegram-переменные больше не читает
- `docker/php-cli/entrypoint.sh` собирает crontab по роли `CRON_ROLE` (`parser` или `telegram`); незнакомая роль завершает контейнер ошибкой вместо тишины
- `TELEGRAM_DELETE_CRON_SCHEDULE` и `TELEGRAM_EDIT_CRON_SCHEDULE` добавлены в `.env.example` — раньше пример знал только расписание публикации
- `FORUM_LOGIN_*` переданы обоим контейнерам: `PublicationsService` получает `ForumHttpClient`, поэтому публикация, собранная из топика, читает форум тем же клиентом и в очереди

#### Название проекта — TRVL

- Прежнее название AWD убрано из пользовательских мест: alt-текст логотипа в шапке и в боковом меню, подпись в меню пользователя, строка авторских прав в подвале, HTTP User-Agent парсера (`TRVL-Parser/1.0`), заголовки `README.md`, `PUBLICATIONS.md`, `TECHNOLOGY_STACK.md`, `CHANGELOG.md`
- Название источника осталось как есть: адреса `forum.awd.ru` в коде, тестах и `PARSER.md` и коды конфигураций сканеров (`awd_forum_topics`, `awd_forum_posts`, `awd_gallery_albums`, `awd_forum_members`) — это имена внешнего форума и значения, уже записанные в `parser_config`, их смена потребовала бы миграции данных и изменила бы ключи advisory lock
