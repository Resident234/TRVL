# Changelog

Все значимые изменения проекта TRVL документируются в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии следуют [SemVer](https://semver.org/lang/ru/). Даты указаны в формате ISO 8601 (YYYY-MM-DD).

## [0.1.0] - 2026-09-08

Первая рабочая версия системы парсинга форума forum.awd.ru (исходные данные для канала TRVL). Реализована бывшая TODO 1: парсинг сущностей со всеми необходимыми данными, организация модели данных, периодический запуск с обновлением существующих данных — весь диапазон проходится заново, записи upsert'ятся.

### Добавлено

#### Парсер тем (`forum-parser/scan`, конфиг `awd_forum_topics`)

- Перебор `t` в диапазоне 0–500000 (`viewtopic.php?t=`), полная структура темы: заголовок, дата, автор, текст, изображения, метки времени
- Обход закрытых разделов: темы, требующие авторизацию, сохраняются заглушками `login_required = true`
- HTTP 404 и сетевые ошибки не останавливают проход; счётчики processed / saved / updated / not_found / login_required / failed

#### Парсер постов тем (`forum-post-parser/scan`, конфиг `awd_forum_posts`)

- Постраничный обход топиков (пагинация `start=N`, 50 постов на страницу), извлечение каждого поста: id (`p`-параметр), номер в теме, заголовок, дата, контент (HTML и текст), автор со всеми полями профиля из блока поста
- Дедупликация повторяющегося открывающего поста на первой странице
- Обрабатывает только топики, уже существующие в таблице `topic` (двигается по диапазону вслед за сканером тем)

#### Парсер альбомов галереи (`gallery-parser/scan`, конфиг `awd_gallery_albums`)

- Перебор `album_id` в диапазоне 0–500000 (`gallery/album.php?album_id=`)
- Две таблицы: `gallery_album` (id, ссылка, название, имя пользователя) и `gallery_image` (id из `image_id`, название, ссылка на полноразмерное изображение, ссылка на страницу изображения, привязка к альбому FK)
- Имя пользователя — 4-й элемент навигации личных альбомов (`Список форумов › Галерея › Личные альбомы › <имя> › <альбом>`), у общих альбомов NULL
- Обход пагинации изображений (100 на страницу, `start=N`), страницы мержатся в один upsert

#### Парсер профилей пользователей (`member-parser/scan`, конфиг `awd_forum_members`)

- Перебор `u` в диапазоне 0–500000 (`memberlist.php?mode=viewprofile&u=`)
- Две вкладки профиля: основная (имя, звание, аватар, страна, город, возраст, пол) и статистика `page=7` (Зарегистрирован, Последнее посещение, Всего сообщений, Фотографий)
- Нормализация дат phpBB: «24 дек 2011, 22:42», «Сегодня/Вчера», относительные «N минут назад», «менее минуты назад»
- Данные вкладок мержатся в одну запись `member`; поля, которых нет на страницах профилей (спасибо выдано/получено из блоков постов), не затираются

#### Авторизация на форуме

- Профили и memberlist доступны только авторизованным; `ForumHttpClient` автоматически логинится через `ucp.php?mode=login` под учётной записью из `.env` (`FORUM_LOGIN_USERNAME` / `FORUM_LOGIN_PASSWORD`), держит phpBB-сессию в памяти и повторяет запрос после ответа «вы должны быть авторизованы»
- Cookies собираются через header-function (cURL cookie-jar файл ненадёжен под HTTP/2); успешность входа контролируется по куке `u ≠ 1`
- Без заданных учётных данных клиент работает гостем — остальные парсеры не затронуты

#### Модель данных (PostgreSQL, миграции)

- `m260828_000001`: `parser_config` (конфиги диапазонов и расписаний, advisory-lock ключи, `last_run_at`), `member` (профили пользователей), `topic` (темы) + сид `awd_forum_topics`
- `m260904_000002`: `topic.login_required` для заглушек закрытых разделов
- `m260906_000003`: `post` (посты тем, FK к `topic` и `member`) + сид `awd_forum_posts`
- `m260907_000004`: `gallery_album`, `gallery_image` (FK к альбому) + сид `awd_gallery_albums`
- `m260907_000005`: `member.last_visit_at`, `member.photos_count`, `member.profile_login_required` + сид `awd_forum_members`

#### Периодический запуск

- Cron-контейнер (supercronic), расписание каждого парсера в `.env`: `PARSER_CRON_SCHEDULE`, `FORUM_POST_PARSER_CRON_SCHEDULE`, `GALLERY_PARSER_CRON_SCHEDULE`, `MEMBER_PARSER_CRON_SCHEDULE`
- Защита от параллельного запуска одного парсера: session-level advisory lock по `crc32`-ключу кода конфигурации; упавший процесс не блокирует следующий запуск
- Все четыре парсера работают одновременно по независимым локам; upsert в коротких транзакциях — по одной сущности за транзакцию
- Каждый проход начинает диапазон заново и обновляет существующие записи (upsert) — это ожидаемое поведение до реализации TODO «постоянно живущий парсер с пропуском неизменённых»

#### Инфраструктура

- Слоистая архитектура (Application → Shared → границы через контракты): тонкие console-команды, сервисы сканирования, парсеры DOM/XPath, репозитории с SQL, HTTP-клиент — все детали за интерфейсами, сборка в composition root (`config/console.php`)
- Автоматический вход (login) HTTP-клиента при получении страницы с формой авторизации
- Сборка образов, docker compose (postgres, app/php-fpm, nginx, parser/cron), обновление entrypoint требует пересборки образа parser (`docker compose build parser`)
- Юнит-тесты (Codeception): парсеры всех четырёх типов страниц, сервисы сканирования, нормализация дат, статистика, блокировки — 72 теста
- Статический анализ: phpstan 0 ошибок, phpcs (Yii2 coding standard) 0 ошибок

### Известные ограничения

- Полный диапазон 0–500000 проходится при каждом запуске, включая несуществующие id (404); оптимизация «пропускать неизменённые» — TODO «постоянно живущий парсер»
- Оценка времени полного прохода одного диапазона при расписании `*/10`: порядка нескольких дней непрерывной работы (скорость ~15–20 id/мин по темам с учётом 404 и обновлений)
- Ссылки на изображения галереи ведут на файлы в `images/upload` — при удалении файла с форума ссылка устареет до следующего прохода
- Учётные данные форума в `.env` в открытом виде (для dev-окружения)

#### Превью альбома — полоса кружков, клик по картинке разворачивает слайдер

- Под полями альбома картинки встали `stacked-images` из `ui-kit/avatars.html`: тема рисует их кружками в 48px, наехавшими друг на друга собственным `margin-right: -15px`, в белой обводке и растущими под курсором (`transform: scale(1.15)` с тенью). От страницы — два правила: `cursor: pointer` (картинка полосы зовёт слайдер, а не просто висит) и `object-fit: cover` (вендорское правило меряет квадратную аватарку, а фото альбома чаще горизонтальное: без подрезки оно сплющилось бы в этот квадрат)
- Полосу называет класс `publication-album-strip` — его носят и общее поле (`#publicationImagesPreview`), и блок каждой прочей части. `renderImagesPreview` у полосы общий с превью под карточкой, поэтому `imagesPreviewLimit` (10) отрезает одно и то же число картинок, и плашка `+N` (`plus bg-danger`) говорит о том же самом
- Прямоугольные превью предпросмотра (`.publication-part-images`, `#publicationPreviewImages`) остались своими 120px с подрезкой: полоса стоит в рамке у полей ввода, а предпросмотр обязан быть как можно ближе к настоящему сообщению канала, поэтому у него свой вид и правится он вместе с тем, что отправляет сервер, а не один
- Клик по картинке полосы разворачивает слайдер этого альбома — `carousel slide` формы `ui-kit/carousel.html` (`carousel-indicators`, `carousel-inner` с `.carousel-item`, стрелки `carousel-control-prev`/`next`). Клик по прочей картинке того же альбома переставляет его на неё, клик по той, на которой он стоит, убирает, а картинка прочего альбома открывает свой слайдер, закрыв тот, что стоял: смотреть можно только на один. Плашка `+N` открывает слайдер на первой из не влезших картинок
- Решение клика (`open` / `slide` / `close`) — чистая функция `stripAction(open, clicked)`, проверенная в `pubjs/test.js` четырьмя проверками; счёт гейта вырос со 125 до 129. В обработчике остаётся расставить узлы
- Узел слайдера стоит в разметке каждой рамки альбома, а не строится на клик, — клон блока части уносит слайдер вместе с собой. Имя (`publicationAlbumCarousel` + счётчик) узел получает в момент открытия, и оно же вписывается в `data-bs-target` его собственных указателей и стрелок: два слайдера одной формы не могут отвечать одному id. Экземпляр перед перестройкой снимается (`dispose()`), иначе переоткрытый узел застал бы старый на уже несуществующих слайдах
- Слайдер держит картинку по высоте, а не по ширине (`max-height: 24rem`, `object-fit: contain`): полоса режет фото в кружок, а смысл слайдера — посмотреть фото, поэтому оно хранит свои пропорции, а не взятое им место остаётся фоном `bg-light-subtle`. У альбома из одной картинки указателей нет, обе стрелки спрятаны (`d-none`) — переставлять нечего, и они только легли бы на фото
- Слайдер следует за формой: `updateImages()` после любой правки альбома зовёт `refreshAlbumSliders()` — список картинок не изменился, слайдер не трогается (его перерисовка — новый экземпляр Bootstrap, и дёргать его на каждое нажатие клавиши не за что); изменился, перерисовывается на той же картинке, а если альбом под ней усох, на последней оставшейся. Альбом без картинок и блок, ушедший из формы вместе со своей частью, закрывают свой слайдер; `clearEditingState()` закрывает их до перестройки блоков, потому что узел слайдера может быть тем, который перестройка уберёт со страницы

#### Высота блока «Форум» — видимая часть страницы за вычетом шапки

- Карточка списка топиков получила `id="pub-forum-block"` и правило `height: calc(100vh - var(--app-header-height, 64px))`: её высота — та часть страницы, что остаётся видимой под приклеенной шапкой `dashboard`, а не те 350px, которыми до сих пор задавала её коробка списка
- Высоту шапки измеряет страница: `syncAppHeaderHeight()` пишет её в `--app-header-height` на корневом элементе при инициализации, на каждом `resize` и ещё раз на `load`. Число зависит от ширины — 64px на десктопе, где шапку держат поле поиска и аватар по 40px, и 70px ниже `lg`, где к ним встаёт логотип-марка в 46px; те же 64px записаны в правило запасным значением на случай неотработавшего JS
- Растёт внутри карточки только коробка списка: `#pub-forum-block > .scroll350` получает `flex: 1 1 0` и `min-height: 0`. Карточка — flex-колонка сама по себе (bootstrap-овский `card`), а flex-элемент без `min-height: 0` не сжимается ниже своего содержимого: список, в котором сотни топиков, растянул бы карточку дальше всякой формулы. Прочие три блока (`.scroll350` «Публикаций», «Черновиков» и «Удалённых») остаются при своих 350px, потому что правило повешено по id карточки
- Строка заголовка блока (два тумблера и пара кнопок сортировки) своей высоты не меняет и на узком окне переносится в несколько рядов, коробке достаётся остаток. Формула задаёт высоту, а не место: над этой карточкой стоит «Фильтры», поэтому её нижний край доезжает до низа окна только когда её верх встал под шапку
- Проверено в настоящем окне `file://` пробой на реальных стилях темы и живом OverlayScrollbars (headless Chrome; `forumheight/build.js` берёт правило и функцию прямо из вида): при 1424×805 шапка 64px, карточка 741px = 805 − 64, коробка списка 659px и `.os-viewport` тех же 659px, прокрутка идёт; при 804×605 шапка 70px, карточка 535px = 605 − 70, строка заголовка свернулась в 102.61px и коробке осталось 382.39px; без JS правило держит запасные 64px
- На живом портале правило приложено к карточке (коробка списка несёт `flex: 1 1 0px` и `min-height: 0px`), страница сама записала `--app-header-height: 70.00px`, консоль чиста. Высоту там измерить нельзя — окно вкладки 0×0, и `100vh` в нём ноль, поэтому за числом проба ходит в headless Chrome

#### Строки поля «Кнопки-ссылки» можно переставлять

- В колонку иконок ряда, рядом с `bi-x-lg`, встали `bi-arrow-up-short` (`.publication-button-up`) и `bi-arrow-down-short` (`.publication-button-down`) — `btn-outline-secondary btn-icon`, тот же вид, что у кнопок переноса альбома; колонка `col-sm-auto` остаётся единой, поэтому и правило «иконок нет, пока ряд в коробке один» (`updateButtonRows()` прячет колонку при `rows.length < 2`) перешло на все три иконки без изменений
- `moveButtonRow(button, step)` переставляет ряд внутри его собственной коробки: ряд встаёт перед тем, кто должен остаться позади него — при подъёме это сам сосед сверху, при спуске ряд за соседом снизу; соседа нет — не происходит ничего. У первой строки «вверх», а у последней «вниз» выключены, а не спрятаны, чтобы колонка не дёргалась от нажатия на краю списка
- После перестановки ряды именует `nameButtonRows()`: `id` пересчитывается по новой позиции, метка коробки остаётся на первой её строке, а `name` не меняется — списки по-прежнему читаются позиционно (`SiteController::publicationButtonsFromRequest`), поэтому порядок, который человек видит на форме, есть порядок предпросмотра и порядок клавиатуры, уходящей в канал
- Перестановка в общем поле задаёт тон всем коробкам: обработчик иконок `takeButtonClick()` вызывает `syncPartButtons()`, как он делает это для добавления и удаления ряда, поэтому поднятая наверху строка поднимается у каждой части; перестановка в коробке части до общего поля не доходит — то же правило, что у правки текста
- Выключенное поле остаётся выключенным целиком: при снятом чекбокс «Кнопки-ссылки в каждой части» `updateButtonRows(box, false)` гасит все три иконки наравне с добавлением и удалением, поэтому колонка не прячется и правый край поля адреса не скачет
- `pubjs/buttons.js` держит правило на подставной коробке, чей `insertBefore` переставляет массив так же, как это делает браузер: подъём через соседа, спуск за соседа, средний ряд уходит в конец, два подъёма подряд поднимают ряд на два места, а движение в никуда не переименует строки
- Проверено в настоящем браузере на `file://` пробной странице (`pubjs/buttonprobe.js`): тот же набор функций страницы, та же разметка ряда и тема `main.min.css` — порядок надписей, `id` rows 0..n после каждого хода, неизменные `name`, выключенные иконки на краях, спрятанная колонка при одном ряде и погашенные иконки при выключенной коробке. Мерка самой колонки: три иконки по 36px и два пробела слова — около 124px против 44px одной иконки удаления
- Проверено и на живом портале (стек поднят после этой записи): три ряда общего поля несут `id` `…-0/1/2` с выключенными иконками на краях, `↑` и `↓` меняют их порядок с ничем на концах, надписи предпросмотра идут за этим порядком в форме 1+2, а разделённый на две части текст с включённым «Кнопки-ссылки в каждой части» копирует ряды в коробку части (`publicationPartButtonText0-0/1/2`): подъём в общем поле поднимает ту же строку у части, спуск в коробке части до общего поля не доходит

#### Состояние переключателя «Ссылки из текста в кнопки-ссылки» живёт в сессии

- Тот же порядок, что у переключателя «Первая строка — в заголовок»: ключ `linksToButtons` (`normalizeLinksToButtons()`), `syncLinksToButtons()` при открытии страницы (сессия, которая уже держала переключатель, не даёт ссылке его повернуть; которая не держала — принимает `?linksToButtons=1` из адреса), `publicationsUrl()` зеркалит параметр в строку браузера, несовпадение адреса с сессией уходит 302, а `site/links-to-buttons-save` (POST) пишет сессию и отвечает адресом для `mirrorUrl`. Ничего на странице ради него не перерисовывается
- Сам тумблер рисуется сервером из этого состояния (`$linksToButtons` в `publications.php`), поэтому свежая загрузка приносит его в запомненном положении. Полем формы он не был и не стал: ряды кнопок, которые он добавляет, уходят с записью, он сам — только в сессию
- Поворот тумблера и отсчёт разборки стали одним действием: вместо отдельного inline-слушателя `change` стоит `watchLinksSwitch(armLinksToButtons)` — сначала взвод таймера в десять секунд по тексту, как он стоит, потом POST; отказ сервера возвращает тумблер в прежнее положение и взводит таймер заново. Функция стоит на верхнем уровне и принимает `arm` параметром ещё и затем, чтобы её можно было прогнать на заглушках вне браузера, как это делается с `watchHeadingSwitch()`
- Очистка формы после сохранённой записи больше не снимает переключатель: он не часть записи, а снятый он оставлял страницу вразрез с сессией, которую та только что записала

#### Сортировка топиков «Форума» по длине текста

- В шапке блока «Форум», рядом с переключателями порядка и перед счётчиком топиков, стоит пара кнопок «Сначала короткий текст» / «Сначала длинный текст» (`btn-group` из двух `input.btn-check` с `label.btn-outline-primary`, id `pubForumTextAsc` / `pubForumTextDesc`): нажатие одной снимает другую, повторное нажатие уже нажатой убирает сортировку, и список возвращается к порядку по дате. Задевает это только топики — посты каждого обсуждения продолжают идти в своём порядке дат
- Миграция `m261001_000001_add_text_length_to_topic`: у `topic` появляется обычный `integer NOT NULL DEFAULT 0` столбец `text_length`, которым миграция считает уже сохранённые тексты, а дальше его пишет парсер (`ForumRepository::saveTopic()` считает `mb_strlen()` по тому же `content_text`; `char_length()` PostgreSQL даёт то же число). Считать длину на чтении — пройтись по тексту каждого топика до `LIMIT`: на 58 922 топиках прогретая выборка стоит 1,2 с против 0,17 с с готовым числом, поэтому сортировка идёт по сохранённому целому, как и счёт ссылок
- `ForumRepository::latestTopicsWithPosts` принимает `$textOrder`: `'asc'` и `'desc'` дают `ORDER BY t.text_length …, t.id …` тем же направлением, любое иное значение оставляет порядок по датам с `NULLS LAST`. Вторичный ключ повёрнут вместе с сортировкой, поэтому страницы, которые догружает прокрутка блока, не перекрываются, а `countTopics()` не меняется — набор строк тот же
- Состояние пары живёт в сессии ключом `forumTextOrder` (`''` | `'asc'` | `'desc'`, `normalizeForumTextOrder()`); `syncForumTextOrder()` при открытии страницы отдаёт приоритет сессии, которая уже держала порядок, пустая принимает `?forumTextOrder=asc|desc` из адреса, `publicationsUrl()` зеркалит параметр в строку браузера, а несовпадение адреса с сессией уходит 302
- Нажатие кнопки уходит POST на `site/forum-text-order-save` с `{forumTextOrder}` — пустое значение означает снятую сортировку. Ответ приносит перерисованный с первой страницы блок `forum`, `totals` того же состояния и адрес для `mirrorUrl`; целиком страница не перезагружается. Отказ запроса возвращает обе кнопки в положение, которое показывала страница, и показывает flash

#### Переключатель «Первая строка — в заголовок»

- В шапке карточки «Новая публикация», справа от её заголовка, стоит `form-switch` «Первая строка — в заголовок» (`publicationTitleFromFirstLine`) с поповером на всей группе: при подгрузке из блока «Форум» первую строку текста он пишет в поле «Заголовок» той части, куда лёг этот текст, а остальное оставляет в тексте. У тофика первой строкой стоит его название — кнопка ставит его перед текстом, у поста — первая набранная им строка
- Текст разбирает `firstLineAsHeading()` — одна функция на трёх местах подгрузки («Опубликовать» топика, «Опубликовать» поста, «Тред целиком» и «Тред по частям»). Снятая строка из текста исчезает, а не повторяется в двух полях; текст из одной строки не режется — если за первой строкой ничего не осталось, поле заголовка пустое, а текст приходит целиком (пустую часть отвергает `assertPartValid()`). В «Треде по частям» заголовок берёт на себя только первая часть, в которую лёг топик
- Состояние переключателя живёт в сессии ключом `titleFromFirstLine` — там же, где фильтры форума и порядок списков: `actionPublications()` решает его через `syncTitleFromFirstLine()` (сессия, которая уже держала переключатель, не даёт ссылке его повернуть; которая не держала — принимает `?titleFromFirstLine=1` из адреса), `publicationsUrl()` возвращает этот параметр в строку браузера, а `site/title-from-first-line-save` (POST) пишет сессию и отвечает адресом, который страница подставляет через `mirrorUrl`. Ничего на странице ради него не перерисовывается, и в `publication-create` состояние не уходит — очистка формы его не трогает, перезагрузка страницы приносит переключатель в том же положении.

### Изменено

#### Часть публикации теперь держится и без текста: альбом выходит без подписи

- `PublicationsService::assertPartValid()` получил четвёртый аргумент — список картинок именно этой части, — и требует от части либо текст, либо свой альбом: пустое поле редактора рядом с заполненным полем альбома записывается и уходит в канал альбомом без подписи. У `saveDraft()`, `schedulePost()` и `saveFromForm()` это `imageUrls` записи, у `saveParts()` — `albums[$index]`, то есть N-е поле альбома, прочитанное позиционно рядом с N-м текстом; первой части принадлежит общее поле `publicationImages`
- Спасает часть только её собственный альбом: заголовок над пустым текстом и набранный набор кнопок-ссылок частью не становятся — flash «Публикации нужны текст или хотя бы одно изображение.», и ни одна запись не пишется. Так же отказывает и разбитая публикация, у которой одна часть осталась без текста и без картинок, пока соседняя их имеет
- Сообщение о длине переформулировано: «…должен быть не длиннее 4096 символов» вместо «…должен быть от 1 до 4096 символов». Нижняя граница перестала быть границей длины — о ней говорит отдельное требование текста либо альбома, а проверка `messageOf()` против `TEXT_MAX_LENGTH` осталась чисто верхней
- `ChannelService::publishPhotos()` больше не отвергает пустой текст, а `NutgramChannelClient::sendPhotoMessage()` и `sendPhotoGroupMessage()` при пустой подписи не ставят в запрос ни `caption`, ни `caption_entities`: пустая строка была бы подписью нулевой длины вместо её отсутствия, а Bot API различает это. Продолжения у такой части нет — против `CAPTION_MAX_LENGTH` резать нечего, и второе сообщение за альбомом не идёт
- Предпросмотр следует за каналом: `partIsShown(text, pictures)` (чистая функция, четыре проверки в `pubjs/test.js`) берёт частью и текст, и альбом, а обёртка без текста не получает строку `.publication-preview-part` и остаётся своими картинками. Placeholder блока теперь появляется только там, где во всей форме нет ни текста, ни альбома
- Миграции не потребовалось: колонка `text` — `notNull()` без CHECK, а `SiteController::publicationTextsFromRequest()` сохраняет пустые поля списком, поэтому позиция «N-й текст — N-й альбом» не съезжает. «Нумерация частей» при этом пустых частей не оставляет: чекбокс дописывает в начало поля строку `Часть N`, и она уходит на сервер вместе с текстом
- Тесты: новый `PublicationsServiceEmptyTextTest` (5 тестов — пустой текст с альбомом записывается, без альбома отвергается, заголовок над пустым текстом часть не спасает, часть разбитой публикации держится своего альбома, часть без текста и без своего альбома отвергается) и `ChannelServicePublishPhotosTest`, где `testEmptyTextThrows` заменён тремя проверками: одиночное фото без подписи, альбом без подписи и пустой список картинок. Каждый тест сначала падал
- Проверено на живой странице (`/publications`, стек поднят): публикация без текста с альбором из ссылок уходит черновиком и в предпросмотре остаётся картинками без текстовой строки, то же с файлами пикера, разбитая публикация с пустой второй частью, у которой свой альбом, даёт две обёртки — первую с текстом, вторую одними картинками; публикация без текста и без картинок по-прежнему отвергается flash-ом, консоль чиста. Три пробных черновика (id 19, 20, 21) оставлены на странице

#### Панель emoji одета в rich popover

- Узел `#publicationEmojiPanel` носит разметку поповера из `ui-kit/popovers.html`: `popover popover-rich bs-popover-auto` с `popover-arrow`, `popover-header` («Emoji» с иконкой `bi-emoji-smile`) и `popover-body > .p-1`, внутри которого стоят те же поле поиска, ряд категорий и сетка, что и раньше — функционал панели не изменился
- Картинку рисует тема: скругление, тень, фон шапки и границы ширины (350–380px из `min-width`/`max-width` правила `.popover-rich`) приходят из `main.min.css`, поэтому своих `border`, `border-radius`, `background` и `padding` у панели больше нет; своя у панели только ширина — `width: 380px`, то есть `max-width` того же `.popover-rich`, записанная страницей, потому что на произволе содержимого карточка встаёт на `min-width` в 350px, а восемь столбцов emoji большего не просят. Вместе с `position: fixed` и `z-index: 1080` она стоит составным селектором `.popover.publication-emoji-panel`, чтобы порядок подключения стилей не решил эти три заново
- Ряд сетки — восемь столбцов по `minmax(0, 1fr)` без горизонтальной прокрутки: трек не должен расти от стоящего в нём, потому что самый широкий ответ, который список оставляет (семья из четырёх человек), не дотягивает до целого столбца двух пикселей, а выросший ряд подвесил бы под панелью второй скроллбар. Ячейка столбца — квадрат: `aspect-ratio: 1` берёт ей высоту самого столбца, а фигуру держит по центру сеточная коробка кнопки, потому что строка фиксированной высоты не поспевает за стороной, которую задала ширина карточки. Поле списка поднято до `12.7rem` — ровно пять таких рядов
- Стрелку и её сторону ставит сама страница: Popper, который обычно владеет стрелкой поповера, здесь не при чём, поэтому `placeEmojiPanel()` пишет панели `data-popper-placement` (`top`, когда панель встала над якорем, `bottom` — когда под ним) и уводит `.popover-arrow` к якорю через `translate()`, не подпуская её ближе чем на 1rem к углу карточки
- Якорь панель берёт от того, чем её открыли: `emojiAnchor()` для панели кнопки становится на прямоугольник `.ql-emoji` (`buttonPoint()` даёт её середину и обе границы), а для панели двоеточия — на курсор, поэтому карточка сдвигается по горизонтали так, чтобы стрелка попала ровно на тот смайл, который нажали, а сторону выбирает прокрутка: кнопка у верхнего края окна — панель висит под ней со стрелкой на верхнем крае, кнопка низко — панель встаёт над ней
- `popupPoint()` отсчитывает панель от двух границ якоря (`y` и `bottom`), а не от одной линии: у курсора обе границы — одна и та же линия, поэтому окно переноса выделения считается ровно так же, как считалось
- Двоеточие в тексте по-прежнему показывает ту же сетку без поля поиска и категорий — `.publication-emoji-inline` прячет `.publication-emoji-head`, — а шапка поповера остаётся: панель без строки поиска всё равно должна говорить, чем она является

#### Панель emoji не показывает то, чего шрифт машины не рисует

- `emojiSupported(list, measure, single, missing)` отсекает из таблицы две разные неудачи шрифта. Первой держался и прежний список: строка с джойнером `U+200D` сравнивается с шириной одного emoji, и всё, что вышло за полторы, уходит — на Segoe UI Emoji Windows 10 (сборка 19045) это 70 строк из 248 с джойнером, «лицо в тумане», «сердце в огне», «бородатый человек — женщина», по 45–55px против 27.5px у одиночного символа. Порог не выбран наугад: самая широкая фигура, которую этот шрифт действительно рисует одна, — семья из четырёх при 1.41 одиночного, а распавшиеся на части наборы начинаются с 1.64, так что между ними остаётся зазор
- Второй вопрос добавлен потому, что ширины тут бывает не видно: символа, фигуры которому шрифт не знает, шрифт замещает квадратиком последнего средства — ровно той же ширины, что и сам emoji, поэтому он проходил прежний отбор и вставал в панели квадратиком. Теперь краска спрашивается отдельно, четвёртым аргументом: `emojiMissing()` рисует символ на canvas и сравнивает его пиксели с пикселями кодовой точки `U+10FFFF`, которой нет ни в одном шрифте на любой машине. На этой машине у вопроса остаются за бортом 134 строки без джойнера — всё, что Unicode выпустил после Emoji 12.1, («плавящееся лицо», «лицо со слезой», «трещина», зевота), а всего таблица из 1921 строки теряет 204 и отдаёт панели 1717
- Проверка сделана по кубику, а не по цвету и не по разбросу краски, потому что в таблице стоят монохромные по замыслу «чёрный квадрат», «белый квадрат», «чёрный круг», «белое сердце», «чёрная кнопка-квадрат» и «чёрный флаг» — у всех них разброс нулевой, а фигуры у них свои, и по цвету они ушли бы вместе с квадратиками
- Вопрос идёт шрифту, а не заводится список исключений: там, где составные emoji рисуются и где шрифт новее, — более новый шрифт, другая платформа, — они в панели остаются; так же держатся в ней и те 178 наборов с джойнером, с которыми этот шрифт справился. Машину, которая не рисует вообще ничего (где и `U+1F600` выходит квадратиком), спрашивать нечего: там вопрос о краске снимается целиком, и панель показывает всё, что проходит вопрос ширины, иначе она осталась бы пустой
- Спрашивается шрифт не по всей таблице при сборке страницы, а по тому, что панель выводит: `emojiListOf()` зовёт отбор на категории целиком до обрезка до `EMOJI_BROWSE_LIMIT` (иначе откачанные шрифтом строки оставили бы в панели пустые места, а на этой машине их 16 в «смайлах», 23 в «природе» и 15 в «еде») и на ответе поиска — уже после обрезка до `EMOJI_SEARCH_LIMIT`, потому что хвост ранжированных ответов не то, что человек ищет. Ответ держится в памяти самой функции, поэтому вторая открытая категория стоит десятые доли миллисекунды. Таблица целиком при инициализации не меряется вовсе: первое знакомство Chrome с символом стоит десятых долей миллисекунды, и 1921 строка сложились бы в полсекунды занятого потока до первого ответа страницы на любой прочий клик
- Список один для панели кнопки, для поиска и для двоеточия, поэтому «огонь» больше не выдаёт «сердце в огне», а «туман» — «лицо в тумане», при том что и сам огонь, и туман, и «пожарный» остаются; в тексте наборам никто не препятствует — принятый с клавиатуры emoji уходит в канал как есть
- `pubjs/test.js` держит правило на подставных ширинах и подставной краске: без джойнера строка не меряется вовсе, 1.41 остаётся, ровно 1.5 остаётся, 1.5 плюс сотая уходит, квадратик уходит, а монохромный «чёрный квадрат» остаётся, и из настоящей таблицы при тех же ответах исчезают «лицо в тумане», «сердце в огне» и «бородатый человек — женщина», но остаётся семья из четырёх; 125 проверок всего. `pubjs/emoji.js` держит порядок обрезка и вопроса: категория с двумя отказанными строками отдаёт панель полную (шесть ячеек из восьми, а не четыре из шести), а одно слово спрашивается не дальше, чем показывает

Вопрос о краске проверен `emojifont/build.js`, который вставляет в пробную страницу сами эти функции из вида, — в настоящем Chrome (вкладка Qoder) и в headless: ни одного квадратика в девяти категориях, страница каждой категории полна настолько, насколько шрифт даёт (148, 160, 133, 115, 160, 79, 160, 160, 160 ячеек), «плавящееся лицо» и «лицо со слезой» ушли, а `⬛ ⚫ ⚪ 🖤 🤍 🔲 🏴 🇷🇺` и семья из четырёх остались, холодная категория 31–168 мс и тёплая 0.0–0.8 мс, до 285 мс без GPU. #### Клавиатура канала собирается в два ряда

- `LinkButtons::MAX_ROWS` (2) и `LinkButtons::rows()`: набор делится не больше чем на два ряда, поровну между ними, а лишняя кнопка достаётся нижнему ряду; `NutgramChannelClient::toKeyboard()` даёт один `addRow()` на ряд вместо `addRow()` на кнопку, поэтому десять кнопок становятся двумя рядами по пять, а не десятью рядами по одной
- Превью повторяет ту же разбивку: `renderPreviewKeyboard()` считает ряды по `__KEYBOARD_MAX_ROWS` — числу, вынесенному страницей из той же константы, — ряды стоят в `div.telegram-preview-keyboard-row` (`display: flex`, `gap: .5rem`), а каждой кнопке достаётся равная доля ширины (`flex: 1 1 0`) вместо прежнего `display: block` во всю ширину
- Раскладку подсказала выгрузка переписки с ботом, чьим видом клавиатур мы сверялись (3327 сообщений с клавиатурой, лежит вне репозитория): все 1383 набора из двух кнопок стоят в ней столбиком, набора же из двух кнопок в единственном ряду нет ни одного, а три кнопки дают 1+2 — нижний ряд шире верхнего
- Подсказка поля «Кнопки-ссылки» говорит про два ряда и про то, что две кнопки стоят одна под другой, а не про «каждая кнопка своей строкой»; у границы `MAX_BUTTONS` та же причина, но без прежней ссылки на ширину строки
- Правило, из-за которого правка одна, а не две: блок «Предпросмотр публикации» обязан выглядеть как настоящее сообщение канала, поэтому раскладку кнопок меняли одновременно на отправке и в превью — одно без другого показывало бы читателю формы картинку, которой в канале нет
- Уже опубликованные сообщения сами не перевешиваются: старая клавиатура остаётся на них до следующего `editChannelMessageText`, который заменит её новой
- `LinkButtonsTest::testTheKeyboardPacksItsButtonsIntoTwoRowsAtMost` держит форму рядов на всём диапазоне (1, 1+1, 1+2, 2+2, 2+3, 5+5), пустой список без рядов, то, что ряды не выходят за границу, ни один ряд не пуст и ни одна кнопка не теряется, и что порядок набора при разбивке не меняется

#### Дамп суперглобальных переменных убран из журнала

- У обоих `FileTarget` (`app/config/web.php`, `app/config/console.php`) выставлен `logVars => []`: Yii дописывал к каждой выгрузке дампы `$_GET`, `$_POST`, `$_FILES`, `$_COOKIE`, `$_SESSION` и `$_SERVER`, а в console-процессе `$_SERVER` — это всё окружение контейнера, поэтому в `app/runtime/logs/app.log` лежали `TELEGRAM_BOT_TOKEN`, `DB_PASSWORD` и `FORUM_LOGIN_PASSWORD` (773 таких дампа)
- В веб-конфиге та же настройка закрывает пароль из формы входа и cookies сессии: они попали бы в `$_POST` и `$_COOKIE` при любой ошибке запроса
- Отладочный контекст в дампе не теряется: причины пишутся в текст записи (`{"id":24,"error":"cURL error 7: …"}`, `topic_id`, счётчики статистики), а не в суперглобальные
- Правка не ретроактивна: записанные до неё строки остаются в `app/runtime/logs/app.log` (каталог в git не попадает), а токен бота стоит повернуть через @BotFather

- Переключатели порядка форума («Сначала старые топики», «Сначала старые посты») переехали из отдельного ряда под заголовком в саму строку заголовка: правая часть, перед круглым счётчиком топиков, в одном `d-flex flex-wrap align-items-center gap-3` с ним — на узкой ширине они переносятся на вторую строку заголовка вместо того, чтобы вылезать за карточку; id и поведение остались прежними

#### Отсутствующее в канале сообщение закрывает запись

- `PublicationsService::deleteDue()` больше не повторяет вечно удаление сообщения, которого в канале нет: ответ `message to delete not found` означает, что нужного результата уже достигли, и запись получает `deleted_at` как обычное удаление
- `TelegramApiException::isMessageGone()` — единственный способ это распознать: Telegram несёт в таком ответе только текст описания, регистра он не гарантирует
- Причина разбора: строки архива 6 и 7 (тестовые публикации) падали каждые пять минут с момента появления задачи — у строки 7 `telegram_id` смещён на единицу («test-post» занимает в канале 5608, а не 5609), строка 6 получила `message can't be deleted` при полном наборе прав администратора, её `deleted_at` проставлен вручную, сообщение 5614 в канале осталось

#### Очередь публикаций вынесена из контейнера парсера

- В `docker-compose.yml` появился сервис `telegram`, собранный из того же `docker/php-cli`: в нём живут `telegram/publish-due`, `telegram/delete-due` и `telegram/edit-due`, а сервис `parser` остался один на четыре скана форума и Telegram-переменные больше не читает
- `docker/php-cli/entrypoint.sh` собирает crontab по роли `CRON_ROLE` (`parser` или `telegram`); незнакомая роль завершает контейнер ошибкой вместо тишины
- `TELEGRAM_DELETE_CRON_SCHEDULE` и `TELEGRAM_EDIT_CRON_SCHEDULE` добавлены в `.env.example` — раньше пример знал только расписание публикации
- `FORUM_LOGIN_*` переданы обоим контейнерам: `PublicationsService` получает `ForumHttpClient`, поэтому публикация, собранная из топика, читает форум тем же клиентом и в очереди
