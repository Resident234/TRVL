# Publications and Telegram Posting

## Overview

This document provides a comprehensive description of the **publications** feature of the TRVL project, covering:

- How publications are stored and managed (drafts, scheduled posts, published posts, soft-deleted posts).
- The workflow for creating, editing, deleting and publishing content.
- Integration with the **Telegram** channel (TRVL) - updating channel description, sending text or photo posts, editing and deleting messages. A pin command is available for test posts; scheduled publication pinning is not part of the publications UI.
- Console commands and cron schedules that automate publishing tasks.
- Configuration requirements.
- Detailed database schema and table relationships.
- Error handling and validation rules.

Domain rules and persistence adapters are implemented in the **Shared layer** (see the root `README.md` for the architecture and setup). The web UI, controllers, configuration and console entry points are in the Application layer. Shared classes are under `app/shared/Publications`, `app/shared/Settings` and `app/shared/Telegram`.

## Architecture

| Layer | Responsibility |
|------|-----------------|
| **Framework / infrastructure** | Yii and Composer dependencies; the project has no separate Core layer. |

## Domain Model

### Database Schema

The publications feature uses four tables to manage the lifecycle of content, plus one table to hold its tunables:

| Table | Purpose | Status Indicators |
|-------|---------|-------------------|
| `publications_post` | Main publications table | - `telegram_id IS NULL` = Scheduled (future `published_at`)<br>- `telegram_id IS NOT NULL` = Published<br>- `published_at` in past = Due for publishing |
| `publications_draft` | Draft publications | - Ready for editing/scheduling |
| `publications_edited` | Edit history of published posts | - `edited_at IS NULL` = Needs update in Telegram<br>- `edited_at IS NOT NULL` = Already updated in Telegram |
| `publications_deleted` | Soft-delete archive | - `deleted_at IS NULL` = Pending deletion from Telegram<br>- `deleted_at IS NOT NULL` = The channel no longer holds the message (deleted there, or already gone when `deleteDue()` asked for it) |
| `publications_setting` | Tunables of the publications page | - one row per code (`code` → `value`, `updated_at`)<br>- seeded from `PublicationSettingsService::defaults()` by `m260925_000001_create_publications_setting` |

A publication whose text goes past the 4096-character limit of one Telegram message is stored as several `publications_post` (or `publications_draft`) rows, one per part: the rows are written by a single `createPosts()`/`createDrafts()` call inside a transaction, `published_at` puts each part the configured gap after the previous one (`partsOffsetMinutes`, one minute by default, never shorter than the `publish-due` schedule), and there is no group column — the parts are ordinary records, ordered by `id`. The form keeps that shift out of its own arithmetic: the preview shows it instead, each part's card carrying in the corner of its bubble the field of the slot moved on by one `partsOffsetMinutes` for every part field that stands before it — the same expression `saveParts()` writes into `published_at`, so what the card promises is what the row stores. See «Время части в углу предпросмотра» in [README.md](README.md). Each part has its own `title`; the channel adds that heading (including the «Часть N» marker when numbering is enabled) to the message at send time, while the stored `text` remains the editor's text. Each row keeps its own `image_urls`, so a part is sent to the channel with the photos it holds: the form gives every part a field of its own (`publicationPartImages[]`, the album of the first part being the shared `publicationImages` field), and what a field holds on submit is what that row gets — an album that belongs to no part of its own stays with the first one. Beside the caret split the form offers three manual modes for the text as a whole — by paragraphs, by lines, by sentences (`splitWholeText`, the buttons carrying `data-split-whole`): one part per boundary of the chosen kind, however short it comes out, with a piece too long for one message still cut down by `splitIntoParts`. Two buttons under each part's album field move the whole list to the neighbouring part (`moveImageGroup`, `data-move-album`): the received pictures come in behind the ones the receiving album already held — `unionPictures`, so a link both fields showed is named once — and the field they left stands empty, while the last part has no «next» button and moving an empty list is refused so a stray click cannot empty the neighbour's field. The order the receiving album comes out with is written into its own mask field, so a link and a file that were interleaved before the move stay interleaved after it. See «Строки альбома и их порядок» in [README.md](README.md). See «Разбивка длинного текста на части» in [README.md](README.md). Every album field also carries a file picker of its own — «Файлы публикации» / «Файлы этой части» (`publicationImageFiles[]` for the shared field, `publicationPartImageFiles{N-1}[]` for part *N*, the first block's picker hidden and disabled exactly like its links field): a file chosen there is stored under the web root and becomes one more link of that same album, so `image_urls` stays a list of links and neither the record nor the channel has to know anything about the upload. See «Файлы альбома» in [README.md](README.md).

Every one of the four tables also carries a `formatting jsonb NOT NULL DEFAULT '[]'` column (`m260926_000001_add_formatting_to_publications`) — the highlighting of that row's `text`, kept as a list of Telegram message entities: `['type' => …, 'offset' => …, 'length' => …]`, plus `url` for a `text_link`, with offsets and lengths counted in UTF-16 code units, which is what the Bot API asks for. The text itself stays plain — no markup characters in it — and `parse_mode` is never sent, so the list is always read against the text it decorates, and an empty list (the column default, and therefore every row written before the editor existed) simply means plain text. A long publication is stored one row per part, so each row holds the entities of its own text. See «Форматирование текста» in [README.md](README.md).

Every one of the four tables carries a `button jsonb NOT NULL DEFAULT '{}'` column beside it (`m260927_000001_add_button_to_publications`) — the keyboard of that row as a list of pairs `[['text' => …, 'url' => …], …]`, one button per row Telegram draws under the message. The column needed no migration to hold a list: `LinkButtons::fromStored()` reads the list a new row writes, the single object a row written before the list holds, the empty object and `[]` of a message without buttons and the `null` of a row written before the column existed, so the default `{}` still means «no keyboard». A part of a long publication gets the buttons of its own row exactly as it gets the album and the entities of its own row. See «Кнопки-ссылки» in [README.md](README.md).

Every one of the four tables carries a `text` column `title` beside it (`m260928_000001_add_title_to_publications`, `NOT NULL DEFAULT ''`) — the heading of that row: the bold first line the channel puts over its text. It is stored apart from `text` and never inside it, so the message the channel gets is composed at send time (`PublicationData::messageText()` and `messageEntities()`), and an empty string — what every row written before the column holds — is a message that starts with its text. A part of a long publication gets the heading of its own row exactly as it gets the album, the entities and the button of its own row; when it has one, the «Часть N» line moves out of the text and to the end of that heading, so the part opens with «Заголовок. Часть 2» while the row keeps the text it was typed with. See «Заголовок части» in [README.md](README.md).

Publications created from forum elements are additionally tracked in two link tables, one row per forum element:

| Table | Purpose | Status Indicators |
|-------|---------|-------------------|
| `publications_topic_map` | Links `topic.id` to a Telegram message | - no row = topic not seen<br>- `telegram_id IS NULL` = marked viewed («Просмотрено»)<br>- `telegram_id` set = published to the channel |
| `publications_post_map` | Links `post.id` to a Telegram message | - no row = post not seen<br>- `telegram_id IS NULL` = marked viewed («Просмотрено»)<br>- `telegram_id` set = published to the channel |

Both tables are written only through `ForumPublicationMapGatewayInterface` (see below). A topic that has exactly one post and that post count as a single element: marking or publishing either one writes the same state into the map row of the other, and a `telegram_id` the twin already has is never overwritten. Topics with several posts are not mirrored — one processed post says nothing about the rest.

The forum block filters («С изображениями», «С привязанными постами», «С ссылками», «Кол-во изображений», «Кол-во ссылок») and their session/URL sync are documented in [README.md](README.md), section «Фильтры блока «Форум»».

### Data Contracts and Interfaces

- **`PublicationData` (DTO)** - Represents a publication record with fields:
  - `id` (int): Primary key
  - `title` (string): The heading of the record — the bold first line the channel puts over its text; empty when the message starts with its text
  - `text` (string): Publication content (1-4096 characters, one record per part of a long publication)
  - `imageUrls` (string[]): Array of image URLs
  - `formatting` (MessageEntities): The inline highlighting of `text` — the entity list of that row; empty for plain text
  - `buttons` (LinkButtons): The keyboard of `text` — the list of link buttons Telegram draws under the message, empty when the record goes out without one
  - `publishedAt` (string|null): Publication timestamp in UTC (`YYYY-MM-DD HH:MM:SS`), null for a draft
  - `createdAt` (string): Creation timestamp
  - `updatedAt` (string): Last update timestamp
  - `telegramId` (int|null): Telegram message ID (null until published)
  - `deletedAt` (string|null): Only for `publications_deleted` rows; null while the message still waits for removal from the channel
  - `messageText(): string` / `messageEntities(): MessageEntities` - The message the channel is given, composed out of `title` and `text`: the heading line — with the «Часть N» the text opens with moved to its end — over the rest of the text, and that text's entities moved behind it with the whole heading line bold over it. `headingAndBody(): array` is the same cut for a list that shows the record instead of sending it

- **`MessageEntities` (DTO, `app/shared/Telegram/Dto`)** - The inline formatting of one message text as the list the Bot API takes it in:
  - `TYPES` - The six formats carried: `bold`, `italic`, `underline`, `strikethrough`, `code`, `text_link`
  - `fromArray(array $raw): self` / `fromStored(mixed $raw): self` - Read a list, dropping entries of a type Telegram does not render and accepting the jsonb column value in every shape it arrives in (a JSON string, an already decoded list, null on a row written before the column)
  - `slice(int $start, ?int $length = null): self` - The entities of a substring re-based on its beginning, spans clipped to it and spans outside it dropped — this is what cuts a caption out of a text and a continuation out of its tail
  - `underHeading(string $heading, string $gap = "\n\n", int $moved = 0): self` - The list as it stands under a bold heading line: the whole heading becomes one `bold` span at zero and every span of the list moves behind the heading and the gap after it — less `$moved`, the length of the number line the heading took out of the head of the text, since the list was counted over a text that still began with it
  - `assertFitsText(string $text): void` - Refuses a list that does not describe real spans of the text: an empty span, a span reaching past the end, an entry out of the offset order, a link with no http(s) address
  - `utf16Length(string $text): int` / `toArray()` / `toJson()` / `isEmpty()` - Counting in the units Telegram counts in, and the shapes the list takes on its way through the column, the form and the API

- **`LinkButton` (DTO, `app/shared/Telegram/Dto`)** - One link button of a message — the label and the address of one of the buttons Telegram draws under the text, the photo or the album:
  - `TEXT_MAX_LENGTH` (64) / `URL_MAX_LENGTH` (2048) - What Telegram accepts of a label and of an address; the label is counted in **bytes**, so 33 Cyrillic letters are already too long
  - `fromArray(array $raw): self` - Read a pair, trimming both halves
  - `fromStored(mixed $raw): self` - Read one stored pair — a JSON object string, an already decoded pair, the empty object, null on a row written before the column; the jsonb column as a whole is read through `LinkButtons::fromStored()`
  - `assertValid(): void` - Refuses a half-filled pair — a label with no address, an address with no label — a label over the byte limit, an address over the character limit, and an address that is not `http://`, `https://` or `tg://`
  - `isEmpty()` / `toArray()` / `toJson()` - Whether the pair is nothing at all, and the shapes it takes on its way through the column, the form and the API

- **`LinkButtons` (DTO, `app/shared/Telegram/Dto`)** - The keyboard of one message as the list the Bot API takes it in — packed into `MAX_ROWS` rows at most, the list shared between them evenly and widening downwards:
  - `MAX_BUTTONS` (10) - How many buttons one message may carry: a bound the portal gives a publication, not one the API imposes — past this point the buttons stop being an accent and become a menu
  - `MAX_ROWS` (2) - How many rows the keyboard is given: a client spreads the buttons of a row over the whole width of the message, so it is the rows, not the buttons, that turn an accent under the text into a block of their own. The preview of the form packs the list by the same bound
  - `fromPairs(array $texts, array $urls): self` - Pair the two lists of one part of the form by position, trimming each half and dropping the rows that hold nothing in either field; a half-filled row stays, so that `assertValid()` is the one that refuses it
  - `fromArray(array $raw): self` / `fromStored(mixed $raw): self` - Read the column value in every shape it arrives in: the JSON list a new row holds, the single JSON object a row written before the list holds, the empty object, `[]`, broken JSON, null on a row written before the column
  - `assertValid(): void` - Refuses more buttons than the message is given, then hands every button to `LinkButton::assertValid()`; an empty list needs nothing and passes, because no keyboard is a valid answer
  - `empty(): self` / `all()` / `count()` / `isEmpty()` / `toArray()` / `toJson()` - The list and the shapes it takes on its way through the column, the form and the API
  - `rows(): array` - The list cut into `MAX_ROWS` rows at most and shared between them evenly, the row the odd button falls to being the last one: two buttons stand one under another, three put a lone button over a pair, ten fill two rows of five. The shape follows a working bot's keyboards — in an export of 3327 of its messages with a keyboard (kept outside the repository) all 1383 keyboards of exactly two buttons are columns, and no keyboard is two buttons in a single row. What the adapter turns into the `inline_keyboard` of the message and what the preview of the form lays out under every part; an empty list gives no rows at all

- **`PublicationRepositoryInterface`** - Abstract repository used by the service to persist publications (implemented by `PublicationRepository`, which keeps all the SQL):
  - `createDraft(string $text, array $imageUrls, string $now, MessageEntities $formatting, LinkButtons $buttons, string $title): int` - Creates a draft with the highlighting of its text, its keyboard of link buttons and its heading, returns its id
  - `createPost(string $text, array $imageUrls, string $publishedAt, string $now, MessageEntities $formatting, LinkButtons $buttons, string $title): int` - Creates a scheduled post with its buttons and its heading, returns its id
  - `createPosts(array $parts, string $now): int` - Inserts the parts of one long publication as separate posts **in a single transaction** (all rows or none); `$parts` is a list of `['text' => …, 'imageUrls' => …, 'formatting' => …, 'buttons' => …, 'title' => …]` rows, so every part carries its own album, its own highlighting, its own buttons and its own heading. Returns the id of the first part
  - `createDrafts(array $parts, string $now): int` - Same, for drafts
  - `updateDraft(int $id, string $text, array $imageUrls, string $now, MessageEntities $formatting, LinkButtons $buttons, string $title): void` - Updates a draft, `created_at` untouched
  - `updatePost(int $id, string $text, array $imageUrls, string $publishedAt, string $now, MessageEntities $formatting, LinkButtons $buttons, string $title): void` - Updates a post, `created_at` untouched
  - `deletePost(int $id): PublicationData` / `deleteDraft(int $id): PublicationData` / `deleteDeleted(int $id): PublicationData` - Removes a row and returns it as it was before deletion
  - `findPost(int $id): PublicationData|null` - Finds a post by ID
  - `findDraft(int $id): PublicationData|null` - Finds a draft by ID
  - `findDeleted(int $id): PublicationData|null` - Finds a deleted record by ID
  - `allPosts(int $limit = 0, int $offset = 0, bool $oldestFirst = false): PublicationData[]` - Gets posts (scheduled and published), newest `published_at` first; `$limit` takes that many rows starting at `$offset`, `0` means the whole list, `$oldestFirst` reverses the order
  - `allDrafts(int $limit = 0, int $offset = 0, bool $oldestFirst = false): PublicationData[]` - Gets drafts by `updated_at`, paged and ordered the same way
  - `allDeleted(int $limit = 0, int $offset = 0, bool $oldestFirst = false): PublicationData[]` - Gets soft-deleted records by `updated_at`, paged and ordered the same way
  - `countPosts(): int` / `countDrafts(): int` / `countDeleted(): int` - How many rows each list holds without paging, so a paged reader knows when it has reached the end
  - `findDueForPublishing(string $now): PublicationData[]` - Posts with an empty `telegram_id` and `published_at <= now`, `id` ascending
  - `storeTelegramId(int $id, int $telegramId, string $publishedAt, string $now): void` - Stores the channel message id and corrects `published_at` to the send time
  - `insertPostWithHistory(PublicationData $post, string $now): int` / `insertDraftWithHistory(PublicationData $draft, string $now): int` / `insertDeletedWithHistory(PublicationData $record, string $now): int` - Insert a moved row preserving its original `created_at` (and `published_at` for archived records)
  - `archiveEdited(PublicationData $post, string $now): void` - Copies a published post into `publications_edited`
  - `findPendingChannelDeletion(): PublicationData[]` - Soft-deleted records still awaiting removal from the channel
  - `storeDeletedAt(int $id, string $deletedAt): void` - Stamps the time a record left the channel
  - `findPendingChannelEdits(): PublicationData[]` - Archived edits still awaiting the channel update
  - `storeEditedAt(int $id, string $editedAt): void` - Stamps the time a message was replaced in the channel

- **`ForumPublicationRef`** - Reference to the forum entity a publication was created from:
  - `type` (string): Either `'topic'` or `'post'`, `isTopic()` / `isPost()` test it
  - `id` (int): ID of the forum topic or post

- **`PublicationForumLinkStoreInterface`** - Temporary store that remembers the relation between a newly created draft/post and a forum entity until the publication is finally published:
  - `remember(int $publicationId, ForumPublicationRef $ref): void` - Stores the link
  - `find(int $publicationId): ForumPublicationRef|null` - Recalls the link
  - `move(int $fromPublicationId, int $toPublicationId): void` - Moves link between publication IDs
  - `forget(int $publicationId): void` - Removes the link

- **`ForumPublicationMapGatewayInterface`** - Permanent bridge tables storing the link between a forum entity and a Telegram message (implemented by `ForumRepository`):
  - `storeTopicMapTelegramId(int $topicId, ?int $telegramId): void` - Creates the `publications_topic_map` row with an empty `telegram_id`, or stamps an existing row with the channel message id
  - `storePostMapTelegramId(int $postId, ?int $telegramId): void` - Same for `publications_post_map`
  - Both mirror the state onto the twin entity when a topic has exactly one post — see the note under the link tables above

The concrete implementations live in the **Infrastructure** sub-namespace of each module and are wired via Yii DI container.

## Service API – `PublicationsService`

The service lives in `app/shared/Publications/Service/PublicationsService.php` and implements the following public use-cases:

| Method | Description |
|--------|-------------|
| `posts(int $limit = 0, int $offset = 0, bool $oldestFirst = false): array` | Returns *published* posts (including scheduled ones that are already due), newest `published_at` first. `$limit`/`$offset` read the list a page at a time, `0` returns all of it, `$oldestFirst` flips the order. |
| `drafts(int $limit = 0, int $offset = 0, bool $oldestFirst = false): array` | Returns drafts by `updated_at`, paged and ordered the same way. |
| `deleted(int $limit = 0, int $offset = 0, bool $oldestFirst = false): array` | Returns soft-deleted records by `updated_at`, paged and ordered the same way. |
| `listTotals(): array` | `{posts, drafts, deleted}` — how many rows each of the three lists holds, so the browser knows how much further a block can scroll. |
| `saveDraft(string $text, array $imageUrls, MessageEntities $formatting, LinkButtons $buttons, string $title, ?ForumPublicationRef $forumRef = null): void` | Validates that the record carries either text or at least one of its `imageUrls`, that the message it composes out of its heading and its text is no longer than 4096 chars, that the formatting describes spans of that text and that every button of its keyboard is either whole or absent, then stores the record as a **draft**. If a forum reference is supplied, a temporary link is stored. |
| `schedulePost(string $text, array $imageUrls, MessageEntities $formatting, LinkButtons $buttons, string $title, string $publishedAt, ?ForumPublicationRef $forumRef = null, ?string $userTimezone = null): void` | Validates the composed message and its buttons, normalises the supplied date (several common formats are supported), creates a **scheduled** post (`published_at` set) and stores an optional forum link. |
| `saveParts(array $texts, array $imageGroups, array $formats, array $buttons, array $titles, string $publishedAt, string $action, ?ForumPublicationRef $forumRef = null, ?string $userTimezone = null): void` | Entry point of the publication form for a **new** record, which sends one text field, one album field, one formatting field, one box of button rows and one heading field per part of a long publication. Every part goes through the text validation before anything is written — and a part passes it on its own album alone, with an empty text field. A single field is saved exactly as `saveDraft()`/`schedulePost()` would. Several fields become one record each through a single repository call (`createPosts()`/`createDrafts()`), so a failure halfway leaves none of the parts behind; `$action` (`'draft'` or `'publish'`) picks the table, the forum link belongs to the first record, and its `published_at` is the form date with each following part shifted by the configured parts gap (`partsOffsetMinutes`, read through `PublicationSettingsService::intValue()` and floored by the `publish-due` cron interval), so `publishDue()` drains the parts in order. `$imageGroups` is read positionally against `$texts` — the album of part *n* is the list the form held in field *n* — and a part whose field stands empty is saved without images. `$formats` is read the same way, and the `trim()` of a part takes its formatting through the same cut (`trimFormatting()`), so a span never outlives the text it was counted over. `$buttons` is read the same way once more — the rows of that part, the shared «Кнопки-ссылки» box standing for the first one — and a part whose box stayed switched off arrives with an empty keyboard and is saved without buttons. `$titles` is read the same way a fourth time — the heading field of that part, the shared «Заголовок» field standing for the first one — and a part whose field stands empty (or holds nothing but spaces) is saved without a heading and goes out as the text it was typed with. |
| `saveFromForm(string $text, array $imageUrls, MessageEntities $formatting, LinkButtons $buttons, string $title, string $publishedAt, string $source, ?int $sourceId, string $action, ?string $userTimezone = null): void` | The eight scenarios of the form when it holds a record opened for editing (`$source` is `post`, `draft` or `deleted`, `$action` is `'draft'` or `'publish'`): update in place, or move between the posts, drafts, edited and deleted tables. `created_at` is always preserved, `updated_at` is the moment of the change, nothing is sent to Telegram from the form. See «Сценарии сохранения» in [README.md](README.md). |
| `publishDue(): array` | Drains the publishing queue: every post with an empty `telegram_id` whose `published_at` has come, read by `findDueForPublishing()` in ascending `id` order. A record that reaches the channel gets the message id Telegram returned into `telegram_id`, and its `published_at` moves to the actual send time (`storeTelegramId()`); the forum map row of a record that came from a topic or a post is stamped with the same id. A record the channel refuses is asked again while the attempt budget of this one run lasts — three attempts by default (`$publishAttempts`), the wait in front of a retry growing with the attempt (`$publishRetryMicroseconds × attempt`) or taken from the `retry_after` the API asked for, whichever is longer and neither past `RETRY_WAIT_MAX_MICROSECONDS`, so a record cannot push the pass beyond the interval the task is scheduled on. A record the budget ran out on is logged once with its attempt count, skipped and left with an empty `telegram_id`, which is what makes the next run of the task take it up again; the records behind it are sent by the same pass. There is no terminal state: nothing gives a record up for good. Returns a stats array `{processed, published, failed}`, counted per record and not per attempt. |
| `deleteDue(): array` | Processes rows in `publications_deleted` with an empty `deleted_at`, removes the message from Telegram by `telegram_id` (if present), then sets `deleted_at` to current time. Returns a stats array `{processed, deleted, failed}`. Records without `telegram_id` are marked as deleted immediately (no message existed in Telegram). A delete that Telegram answers with `message to delete not found` counts as done and is stamped too: the channel already does not hold the message, so a retry could only repeat the same answer for ever. Any other failure keeps `deleted_at` empty and is retried on the next run. |
| `editDue(): array` | Processes rows in `publications_edited` with an empty `edited_at`, updates the Telegram message text by `telegram_id`, then sets `edited_at` to current time. Returns a stats array `{processed, edited, failed}`. |
| `publishDraft(int $id): void` | The «Опубликовать» button on a draft: the record moves to the posts table with `published_at` and `updated_at` set to the current time, so the periodic `publishDue()` task sends it to Telegram at once. `created_at` is preserved. |
| `scheduleDraft(int $id, string $publishedAt, ?string $userTimezone = null): void` | The «Запланировать публикацию» modal: the draft moves to the posts table with the publication time from the modal. `created_at` is preserved, `updated_at` is the current time. |
| `publishPostNow(int $id): void` | The «Опубликовать» button on a scheduled post: the post stops being scheduled — `published_at` and `updated_at` become the current time, `created_at` is untouched. |
| `movePostToDraft(int $id): void` | The «Переместить в черновик» button: the post row is deleted from the posts table and inserted into the drafts table; `created_at` is preserved, `updated_at` is the moment of the move. |
| `publishDeleted(int $id): void` | Restores a soft-deleted publication to the posts table with current timestamp as `published_at`, clears `telegram_id` (new message will be sent), and removes the deleted record. Used for republishing deleted content. |
| `scheduleDeleted(int $id, string $publishedAt, ?string $userTimezone = null): void` | Restores a soft-deleted publication to the posts table with the specified `publishedAt`, clears `telegram_id`, and removes the deleted record. Used for rescheduling deleted content. |
| `moveDeletedToDraft(int $id): void` | Moves a soft-deleted publication to the drafts table, clearing `telegram_id` and setting `updated_at` to current time. Used for recovering deleted content as a draft. |
| `deleteDraft(int $id): void` | Moves a draft into `publications_deleted` so the pending removal is dropped and the record stays restorable. |
| `deletePost(int $id): void` | Soft-deletes a published/scheduled post by moving it to `publications_deleted` table, preserving `created_at` and `published_at`, setting `updated_at` to current time, and clearing `telegram_id` (the periodic task will handle Telegram deletion). |

### Validation Rules
- A part needs either text or its own album: `assertPartValid()` refuses a part whose text is empty and whose picture list is empty with «Публикации нужны текст или хотя бы одно изображение.», while a part that brings pictures may keep its editor empty and goes out as an album with no caption (see «Альбом вместо текста» in [README.md](README.md)). A heading and a keyboard do not rescue such a part. Length is the other, separate rule: the message must not exceed 4096 characters. The limit is per record, and a long publication is split into parts by the form before saving, so each stored part stays inside it (see `saveParts()` and «Разбивка длинного текста на части» in [README.md](README.md))
- The limit falls on the message the channel is given, not on the text column alone: `assertPartValid()` measures `PublicationData::messageText()`, so a heading counts against the 4096 of its part, and a part with one is refused with «Заголовок с текстом должен быть не длиннее 4096 символов». A heading of nothing but spaces is no heading and the part is measured as its text alone
- A formatting list must describe real spans of its text (`MessageEntities::assertFitsText()`, reached from `assertPartValid()` on every write path): no empty span, nothing past the end, offsets in non-decreasing order, an http(s) address behind every `text_link`. An entry of a type Telegram does not render is dropped on read, not refused
- Every link button of a record is either a full pair or nothing (`LinkButtons::assertValid()`, called on every write path beside `assertPartValid()`): a label with no address or an address with no label, a label over 64 bytes, an address over 2048 characters and an address outside `http://`, `https://` or `tg://` all raise `InvalidArgumentException` — a flash, and no record written. The same check refuses a keyboard of more than `LinkButtons::MAX_BUTTONS` (**10**) buttons — a bound of the portal, not of the API, so the form never offers an eleventh row
- Image URLs array can be empty but must contain valid URLs when provided
- Dates must be parseable by multiple common formats (see `normalizeDate()` method)
- Forum references are optional but when provided must contain valid source ('topic' or 'post') and positive sourceId

### Error Handling
- `InvalidArgumentException` is thrown for validation failures (text length, date format, missing IDs, etc.)
- `TelegramApiException` is thrown when Telegram API calls fail (network issues, invalid bot token, rate limiting, etc.). It carries the HTTP `errorCode` and the `retryAfter` of a flood wait, and answers `isMessageGone()` for the one failure that is really a success: a delete of a message the channel no longer has. `isMessageUnchanged()` is its sibling for the other such answer, `message is not modified`: an edit that asks a message for what that message already is.
- `RuntimeException` is thrown when Telegram bot is not configured (missing TELEGRAM_BOT_TOKEN)

## Telegram Integration – `ChannelService`

Located at `app/shared/Telegram/Service/ChannelService.php`. The service is a thin wrapper around the low-level `TelegramChannelClientInterface` and adds business-level validation.

| Method | Purpose |
|--------|---------|
| `isConfigured(): bool` | Returns **true** if a bot client instance is provided. |
| `channelInfo(): ChannelInfo` | Retrieves basic channel information (id, title, username, description). |
| `updateDescription(string $description): void` | Validates that the description does not exceed **255** characters and updates the channel description via the Telegram API. The new description is archived in the `publishedDescriptions` repository. |
| `publishedDescriptions(): array` | Returns archived channel descriptions (newest first). |
| `publishText(string $text, MessageEntities $entities = new MessageEntities(), LinkButtons $buttons = new LinkButtons()): int` | Sends a plain-text message (1–4096 chars) with its entities and, when the record has any, its link buttons as the keyboard of the message. Returns the Telegram `message_id`. |
| `publishPhotos(string $text, array $photoUrls, MessageEntities $entities = new MessageEntities(), LinkButtons $buttons = new LinkButtons()): int` | Sends one or many photos (up to 10 per API call). The first photo receives a caption (max 1024 chars), cut at the last line break that still fits so a line is never split. An empty text is not a refusal any more: the photos then go out with no caption at all, which is the album Telegram makes of pictures alone, and there is nothing left to send as a continuation. What does not fit into the caption is sent once as a continuation text message after the photos, never as a repeat of the whole text. The formatting follows the same cut: `MessageEntities::slice()` keeps the spans of the caption in the caption and re-bases the rest onto the continuation. Only the album that carries the caption is given the keyboard, so a text cut into several albums leaves its buttons on the first of them. Returns the `message_id` of the first photo. |
| `pinPost(int $messageId): void` | Pins the given message in the channel. |
| `deletePost(int $messageId): void` | Deletes a message from the channel. |
| `editPostText(int $messageId, string $text, MessageEntities $entities = new MessageEntities(), LinkButtons $buttons = new LinkButtons()): void` | Edits the text of an existing message (same validation as `publishText`) — entities, keyboard and all. |

Entities are the only way formatting reaches the channel: `parse_mode` is never sent, the text goes out as plain characters, and the spans go with it as `entities` of a text message or `caption_entities` of a photo — an empty list sends neither (`NutgramChannelClient::toMessageEntities()`). The other side is sent the same way: `sendPhotoMessage()` and `sendPhotoGroupMessage()` leave out both `caption` and `caption_entities` when the caption is empty, because an empty string would be a caption of zero length rather than its absence.

A link button reaches the channel as `reply_markup`: `NutgramChannelClient::toKeyboard()` builds an `InlineKeyboardMarkup` with one `addRow()` per `LinkButtons::rows()` entry — `MAX_ROWS` rows at most, the list shared between them evenly, the wide row last — out of `InlineKeyboardButton(text, url)` objects, and an empty keyboard builds nothing at all — a publication without buttons sends the very same request it sent before. `sendMediaGroup` takes no `reply_markup`, so the keyboard of a part with an album is attached to its first photo by a following `editMessageReplyMarkup`, and only when there are buttons to attach. The first photo of an album the queue has already sent can be standing in the channel wearing that very keyboard while its record is still queued, and the edit of such a message answers 400 `message is not modified` — the refusal of a change that needed no change. `sendPhotoGroupMessage()` reads that answer as the send it describes: the album is there, its button is on it, and the message id goes back to the queue, which stamps the record instead of asking the channel for the same album on the next run. Any other refusal of the edit is the failure it has always been. `editMessageText` keeps the keyboard that hung on the message when the parameter is omitted, which is why every edit answers with one: the buttons' markup, or an empty `InlineKeyboardMarkup` that drops it (`toReplacementKeyboard()`).

The channel never sees the columns as they stand: `publishToTelegram()` and `editInTelegram()` send `PublicationData::messageText()` with `messageEntities()`, so what goes out is the record's text with its heading composed in front of it — the heading line bold, the «Часть N» the text opened with moved to the end of that line, and the spans of the text behind it. A record without a heading composes into its own text byte for byte, which is every record written before the column existed. See «Заголовок части» in [README.md](README.md).

An album goes out as files rather than as links: `publishToTelegram()` hands the pictures of a record to `prepareImageUrlsForTelegram()`, which fetches every one of them through the injected `ForumHttpClientInterface` — the same client the parsers read the forum with, and the only HTTP client the queue is wired with — writes the answer into `publication_img_*` in the temp directory, and gives the channel that path. Which host a picture stands on decides nothing: `forum.awd.ru` answers only a client holding its session, while hosts like `foto.awd.ru` serve the portal a JPEG and answer the channel's own fetcher with `wrong type of the web page content`, and bytes that already arrived here cannot be refused a second time over there. A picture this side could not fetch keeps its address in the album, so the channel gets its own attempt at it and the record is not refused over one broken file; `NutgramChannelClient::isLocalFile()` tells the two cases apart by `file_exists()` — a path is uploaded as `InputFile`, an address is passed to the API as media. The name a download takes comes from the bytes it answered with, unless its address ends in one of the picture extensions listed in `PublicationsService::IMAGE_EXTENSIONS`.

A download is not removed on the spot: the file has done its work once the message carrying it is sent, and nothing comes back for it later — an edit replaces the text of a message, and a re-send reads the album again from its addresses. `TempImageCleanup` (`app/shared/Publications/Infrastructure/TempImageCleanup.php`, run by `telegram/clean-temp` once a day by default) takes the files older than `MAX_AGE_SECONDS` (an hour): a younger one can still belong to an album being sent by a queue pass running at the same moment, since the client reads the file while the request goes out. The sweep looks at that one name and at nothing else — the container's temp directory also holds the crontab `entrypoint.sh` writes for supercronic and the mounted composer cache, and neither is the queue's to remove. The name itself is written in one place, `TempImageCleanup::PREFIX`, which is what `downloadImage()` builds its path from.

Because this same client also visits hosts that have nothing to do with the forum, its cookie jar is kept per host: the phpBB session is sent to `forum.awd.ru` alone, and a cookie another host handed out is never offered to the forum. See «Настройки парсера» in [PARSER.md](PARSER.md).

All methods may throw `TelegramApiException` (API failure) and `RuntimeException` when the bot token is missing.

The client waits 30 seconds for an answer (`NutgramChannelClient::REQUEST_TIMEOUT`, given to Nutgram through `Configuration::fromArray(['timeout' => …])`). The five seconds Nutgram asks for by default are not the time the API takes to answer but the time the connection to it takes — the first call of a run spends most of it negotiating the route, measured on the local portal at about fifteen seconds — and a task that never gets past that is a task that fails again every five minutes.

The limits Telegram itself imposes are public constants of the class — `TEXT_MAX_LENGTH` (4096), `CAPTION_MAX_LENGTH` (1024), `DESCRIPTION_MAX_LENGTH` (255), `ALBUM_MAX_PHOTOS` (10) and `PARTS_NUMBERING_RESERVE` (16 characters the «Часть N» heading keeps out of the text budget) — and of `LinkButton`, which holds `TEXT_MAX_LENGTH` (64 bytes of a button label) and `URL_MAX_LENGTH` (2048 characters of its address) — because the publications form reads the first two to decide where a long text has to be split, and the settings page lists all of them through `PublicationSettingsService::telegramLimits()`. None of them is editable from the portal. `LinkButtons::MAX_BUTTONS` (10 buttons under one message) belongs to the same kind of check but is not in that list: the Bot API would accept a larger keyboard, and it is the portal that stops the form from asking.

The console controller exposes the above functionality to the command line and is intended to be used by cron jobs or developers.

| Command | Description |

| `php yii telegram/index` | Shows current channel information (id, title, username, description). |
| `php yii telegram/set-description "<desc>"` | Updates the channel description. Returns an error code if validation fails or the bot is not configured. |

These commands are typically scheduled by **supercronic** in the `telegram` Docker Compose service, using the environment variables defined in `.env` (see below). They can also be run manually from the `app` container.

## Cron Scheduling (environment variables)

| Variable | Default | Description |
|----------|---------|-------------|
| `TELEGRAM_PUBLISH_CRON_SCHEDULE` | `*/5 * * * *` | How often `telegram/publish-due` should run. |
| `TELEGRAM_DELETE_CRON_SCHEDULE` | `*/5 * * * *` | How often `telegram/delete-due` should run. |
| `TELEGRAM_EDIT_CRON_SCHEDULE` | `*/5 * * * *` | How often `telegram/edit-due` should run. |
| `TELEGRAM_TEMP_CLEAN_CRON_SCHEDULE` | `0 4 * * *` | How often `telegram/clean-temp` should sweep the downloaded album pictures out of the temp directory. |

These variables are read by the **docker-compose** entrypoint (or by a host scheduler) and passed to the container. Adjust them according to your desired frequency.

The four jobs run in the `telegram` container, not in the `parser` one: `docker/php-cli/entrypoint.sh` builds the crontab from `CRON_ROLE`, and only the role `telegram` writes these four lines. The container is built from the same image as the parsers, so nothing about the commands changes — where they run is a matter of which schedule lines the crontab gets. The `parser` container holds the four forum scans and has no bot token at all.

`TELEGRAM_PUBLISH_CRON_SCHEDULE` is also passed to the `app` container, because the settings page needs it: `PublicationSettingsService::cronIntervalMinutes()` turns the schedule into a number of minutes, and that number is the lower bound of the gap between the parts of one publication. The portal shows the schedule read-only and never edits it — the cron of the container is not something a page can change.

## Configuration (`.env`)

The Telegram integration requires two variables:

```
TELEGRAM_BOT_TOKEN=xxxx:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
TELEGRAM_CHANNEL_ID=@your_channel_username   # or numeric channel ID
```

If the token is missing the service will throw a `RuntimeException` and all Telegram-related commands will exit with the `CONFIG` exit code.

Three more variables left the source code and are read from the environment:

```
# Signs the session and CSRF cookies (app/config/web.php); empty key = no request
# carrying one of them is accepted. Generate: php -r "echo bin2hex(random_bytes(32));"
COOKIE_VALIDATION_KEY=
# Both are read by app/web/index.php and app/yii; without them the app is production
YII_ENV=dev
YII_DEBUG=1
```

None of the three is displayed on a settings page: a page that lists tunables is not where a secret belongs.

Insertion goes through the editor and nowhere else (`deleteText()` of the shortcode as `api`, `insertText()` of the emoji as `user`), so the change the page already listens to reads the entity list back from the document, writes the textarea mirror, updates the counters and runs the split on its own: an emoji is the keystroke it imitates, and one put at the end of a bold word joins that word exactly as a letter there would. It counts as the two UTF-16 units it is, which is how the channel counts it, so the counters, the limit of a message and the offsets of the entities need no arithmetic of their own. `wholeCharacter()` keeps a cut out of the middle of one: the hard cut of `splitIntoParts()` and the caret and middle cuts of `manualCut()`/`middleCut()` step back over a divided surrogate pair, a variation selector, a keycap sign, a skin tone, a joiner standing on either side and the two regional indicators of a flag, so no part begins or ends with half a character. See «Emoji в тексте» in [README.md](README.md). The buttons of a part travel the same way: the shared «Кнопки-ссылки» box (`#publicationButtonBox`) holds the keyboard of the first part and `.publication-part-button` holds a box of exactly the same shape per part after it — rows named after the part they belong to (`publicationPartButtonText0[]`, `publicationPartButtonUrl0[]`, `publicationPartButtonText1[]` and so on, the first part being served by the shared field) and read positionally by `SiteController::publicationButtonsFromRequest`. A `bi-plus-lg` icon adds a row to its own box, a `bi-x-lg` one takes a row away, and `LinkButtons::MAX_BUTTONS` (10) is where adding stops. Two more icons of the same column — `bi-arrow-up-short` (`.publication-button-up`) and `bi-arrow-down-short` (`.publication-button-down`) — move the row they stand in one place up or down inside that same box: the row is inserted before whatever has to stay behind it, a row with no neighbour moves nowhere, which is why the first row's up icon and the last row's down icon are disabled rather than hidden and the column never shifts. `nameButtonRows()` renumbers the `id` of the rows after a move (the box's label keeps pointing at its first row) while the `name` stays the same list, so the submitted order, the preview order and the order of the channel keyboard are the order the person sees; a move made in the shared box reaches every part box through the `syncPartButtons()` the icon handler already calls, while a move inside a part's own box stays in that part. See «Кнопки-ссылки» in [README.md](README.md). The checkbox «Кнопки-ссылки в каждой части» — visible only while the form holds more than one part — opens those boxes prefilled from the shared field and keeps them in step with it while it stays switched on; a box left switched off is disabled, so it is not submitted and that part goes out with no buttons. The switch «Ссылки из текста в кнопки-ссылки» (`publicationLinksToButtons`, a `form-switch` standing at the top left of the button frame in the shape the vendored sheet draws it, explaining itself in the popover of that same group rather than in a line under it — see «Подсказка элемента» in [README.md](README.md), its state kept in the session under `linksToButtons` exactly as the forum filters and the heading switch of the header are kept there — `syncLinksToButtons()` resolves it when the page opens (a session that has already held the switch keeps it, an untouched one takes `?linksToButtons=1` from the address), `publicationsUrl()` mirrors it back into the bar, and `site/links-to-buttons-save` stores what the switch was set to and answers with that address, nothing of the page being redrawn for it — and submitted neither as a field of the form nor as anything of the record) keeps the boxes filled from the texts they belong to: a turn of it is one action with the waiting it starts, `watchLinksSwitch(armLinksToButtons)` arming before it posts and arming again when the server refuses, and the clear of the form after a saved record leaves the switch alone, the state it shows being the session's. While it is on, every change of a part's text puts off a ten-second timer (`armLinksToButtons()`, `__LINKS_TO_BUTTONS_IDLE`) and `fillButtonsFromText()` then appends that part's own addresses to that part's own rows — the bare ones `findLinks()` reads and the `text_link` spans alike (`addressesInText()`), minus the links that point at a picture (`IMAGE_ADDRESS`, the same suffixes the album of a part takes and the forum parser cuts out of a post, since such a link already leaves as one of its photos). A row the person typed is left alone and an address a box already carries is not added twice (the rows are matched through `linkAddressOf()`, so a hand-typed `awd.ru/x` counts as `https://awd.ru/x`), the set stops at `LinkButtons::MAX_BUTTONS`, and each new button is labelled with its host and the first piece of its path cut to `LinkButton::TEXT_MAX_LENGTH` bytes (`buttonLabelOf()`), so the fill never writes a label `assertValid()` would refuse. Where the form holds parts, the switch checks «Кнопки-ссылки в каждой части» first — a hidden box is disabled and submits nothing — which means a later edit of the shared box replaces the parts' rows with the shared ones through `syncPartButtons()`, and the addresses come back on the next change of a text. See «Кнопки-ссылки» in [README.md](README.md). The heading of a part travels the same way: the shared «Заголовок» field (`publicationTitle`) is the heading of the first part and `.publication-title-field` holds one per part after it (`publicationPartTitle[]`, read positionally by `SiteController::publicationTitlesFromRequest`); it is optional, and while the text column keeps what was typed into the editor, the message the channel gets is composed at send time with that heading as a bold first line — «Заголовок. Часть 2» for a part of a long publication, since its own number line moves to the end of the heading. `composedMessage()` of the page makes the same cut, so the preview, the counters and the budget of a part all stand over the message that will be sent. See «Заголовок части» in [README.md](README.md). A switch in the header of the form — «Первая строка — в заголовок» (`publicationTitleFromFirstLine`, a `form-switch` standing on the right of that header, explaining itself in the popover of its own group, its state kept in the session under `titleFromFirstLine` exactly as the forum filters and the reading order of the lists are kept there — `syncTitleFromFirstLine()` resolves it when the page opens (a session that has already held the switch keeps it, an untouched one takes `?titleFromFirstLine=1` from the address), `publicationsUrl()` mirrors it back into the bar, and `site/title-from-first-line-save` stores what the switch was set to and answers with that address, nothing of the page being redrawn for it — and submitted neither as a field of the form nor as anything of the record) — decides whether a fill from the forum block starts its publication with a heading: with it on, `firstLineAsHeading()` takes the first line off the text that «Опубликовать» of a topic or a post brings, and off the text of both thread buttons, and writes it into the heading field of the part that text lands in — which for a topic is its own name, the button already standing it in front of its text, and for a post is the line its author opened with. The line leaves the text rather than being copied into it, only the first part of a «Тред по частям» takes one, and a text with nothing behind its first line is handed over whole with an empty heading, since a part without text and without its own album is what `saveParts()` refuses. See «Заголовок части» in [README.md](README.md). Each part of a split publication stands in a frame of its own: `.publication-text-block:not(:only-child)` carries `border: 1px dashed #ff7d5c`, `padding: 1rem` and the radius of a board card — the three numbers under which `kanban-items .kanban-item:hover` dresses a card of the board, taken without the `cursor: move` of a draggable item, since a part of this form travels nowhere. The frame is drawn permanently rather than on hover, because it is a reading aid and not a promise of an action: the boundary between two parts used to be guessable only from the «Часть N» line. The rule is written against the template block, so every clone carries it, and the album frame of a part keeps its own solid `#dfe5ea` border inside it. Only a box holding more than one block is framed: `:not(:only-child)` reads that off `#publicationTextParts` itself, which holds nothing but these blocks, so a monolithic publication with its single «Текст публикации» field stays a plain card, and every split, merge, move and rebuild of the parts restates the frame with the number of children of the box rather than with a class someone might forget to refresh. Each card of the «Предпросмотр публикации» block carries the moment its own part goes out at, in the bottom-right corner of its bubble: the field of the slot shifted by the sender's own `partsOffsetMinutes` per part field, the day named beside the time only where a part has left the day the field names, and no corner at all where the field names no readable moment. The footer badge that repeated that field once for the whole publication (`#previewPublicationAt`) is gone — the field now redraws the preview (`applyPublicationSlot()` → `update()`), the corner and the calendar being two views of the same value — and an album with no caption keeps its full-bleed shape only while nothing stands under it, the hour or a keyboard being enough to take it away. See «Время части в углу предпросмотра» in [README.md](README.md). The three record lists start at one page of `publicationPageSize` rows and ask `publication-page` (`posts()`/`drafts()`/`deleted()` with a page and an offset, rendered through the `_item_*` partials) for the next page whenever a block is scrolled to its bottom. The forum block pages on two levels of its own: its topics come from the same `publication-page` endpoint (`ForumRepository::latestTopicsWithPosts` with an offset, `countTopics` for the total), while the posts of one topic sit in a scrollable box of their own (`_item_topic`, `.thread-replies`) and are loaded by `forum-post-page` (`ForumRepository::topicPosts`) as that box is scrolled — see «Бесконечная прогрузка списков» in [README.md](README.md). The card of that list is as tall as the page which stays visible under the sticky header of the layout: `#pub-forum-block` carries `height: calc(100vh - var(--app-header-height, 64px))`, and since a rule cannot ask a neighbour for its size, `syncAppHeaderHeight()` measures `.app-header` into that variable when the page is initialised, on every resize and again on `load` — the header is 64px on a desktop window, where its search field and avatar hold it, and 70px below `lg`, where the layout's 46px brand mark stands beside them (which is also the fallback the rule keeps for a script that never ran). Only the box of topics grows: `#pub-forum-block > .scroll350` takes `flex: 1 1 0` with `min-height: 0`, the card being a flex column already, so the header row of the block keeps its own height and the box fills what is left instead of stretching the card over every topic it holds — the three record blocks, which share that same `.scroll350` rule, are no longer kept at 350px but at `height: 50vh` of the card — half the visible window, the list taking the rest of the card by the same two flex rules. See «Блок «Форум»» and «Высота блоков записей» in [README.md](README.md). Beside the «Опубликовать» button of a topic, two more buttons load the whole discussion into the form: they post to `forum-thread`, which answers every post the table holds for that topic (`ForumRepository::topicThread` — no page, no filter, published posts included, `login_required = FALSE` kept) in the order the block currently shows them, while the topic itself is read off the attributes of its own publish button; «Тред целиком» joins the texts into one field and the links of the whole discussion into the album of the first part, «Тред по частям» gives each entity a part of its own with that entity's links in that part's album field, cutting every text with `splitIntoParts` so no part can exceed the limit `saveParts` checks (see «Тред топика в форму» in [README.md](README.md)). A switch in the header of a block posts to `publication-sort`, which stores the reading order of that list in the session and answers with the block the switch belongs to redrawn from its first page in the new order — the forum block has two such switches, one for its topics (`ForumRepository::latestTopicsWithPosts` topic order) and one for the posts of each topic; the session state — the forum filters and the reversed lists alike — is mirrored into the address bar (`SiteController::publicationsUrl`, `?postsOldest=1` and friends), and a page opened on an address that disagrees with the session is redirected onto it (see «Сортировка списков» in [README.md](README.md)). Beside those two switches the forum header carries a paired button group — «Сначала короткий текст» / «Сначала длинный текст» (two `input.btn-check` in one `btn-group`, `pubForumTextAsc` / `pubForumTextDesc`) — which stands the topic list up by the length of its own text: pressing one releases the other, and pressing the already pressed button once more drops the sort and the list returns to the order of its dates. A press posts the state the pair now shows (`asc`, `desc` or nothing) to `forum-text-order-save`, which keeps it in the session under `forumTextOrder` and answers the forum block redrawn from the first page of the new order with its `totals` and the address of that state; `textOrderState()` reads the pair after the browser has released the neighbour, so a refused request puts both buttons back where the page stood and shows a flash. The order reaches the bar as `?forumTextOrder=asc|desc` through the same `publicationsUrl()` mirror and the same redirect, and `normalizeForumTextOrder()` reads anything else as no sort at all. Only topics are ordered — the posts of a discussion keep their date order, since a thread sorted by length would no longer read as a thread — and `t.id` keeps the secondary key of the `ORDER BY` turned the same way, so the pages the block scrolls through cannot overlap. The length itself is stored rather than computed: `topic.text_length` is written by `ForumRepository::saveTopic()` as `mb_strlen()` of the same `content_text` it stores and backfilled by `m261001_000001_add_text_length_to_topic`, because counting the text of every topic before `LIMIT` discards most of them costs about 1.2 s over the current 59k topics where ordering a stored integer stays under 0.2 s. Addresses are flat: `UrlManager` maps each of these routes onto its own path without `index.php?r=` (see «Адреса страниц» in [README.md](README.md)). After a scheduled post becomes due the background `publish-due` command sends it to Telegram.

## Testing

Codeception suites live in `app/tests`; the installed PHPUnit requires PHP >= 8.4, and `Unit`, `Functional` and `Acceptance` run against the test configuration in `app/config/test.php`, which binds `PublicationRepositoryInterface` to the real repository, so repository tests talk to a PostgreSQL test database.

- `Unit/shared/Publications/Infrastructure/PublicationRepositoryTest` — rows written by `createDraft`/`createPost`, the sort order of the three lists, what `findDueForPublishing` selects, that an entity list, a record's buttons and a heading survive a write and an update and come back with the record they belong to — one keyboard and one heading per part of a long publication — and moving records back out of `publications_deleted`
- `Unit/shared/Publications/Infrastructure/PublicationRepositoryPagingTest` — the paging the three record blocks scroll through: a page of ten read in order leaves nothing out and nothing twice, an offset counts rows rather than pages, the page after an exact multiple is empty, `0` hands out the whole list at once, the oldest-first pages mirror the newest order, rows written in the same moment keep the `id` tiebreaker, drafts page over `updated_at` and deleted records over theirs, and each `count*()` is the number of rows its pages hand out
- `Unit/shared/Publications/Infrastructure/CachePublicationForumLinkStoreTest` — remember/find/move/forget of the temporary forum link
- `Unit/shared/Publications/Service/PublicationsServiceEmptyTextTest` — the rule that a part is kept by its own album: an empty text with pictures reaches the repository, an empty text without them is refused, a heading over an empty text does not save the part, and in a split publication every part is measured against the album of its own field rather than against the album of another
- `Unit/shared/Telegram/Dto/MessageEntitiesTest` — reading a stored list in every shape the jsonb column brings it, UTF-16 counting, what `slice()` keeps of a caption and what it hands to the continuation, what `underHeading()` puts over a message and how far it moves the spans it stands behind, and every case `assertFitsText()` refuses
- `Unit/shared/Telegram/Dto/LinkButtonTest` — reading a stored pair in every shape the jsonb column brings it, the byte limit of a label, the character and scheme limits of an address, and the half-filled pair `assertValid()` refuses
- `Unit/shared/Telegram/Dto/LinkButtonsTest` — the rows of the form paired positionally into a keyboard, trimmed, with their empty rows dropped, a half-filled row kept so that validation can refuse it, what `fromStored()` makes of every shape the jsonb column has ever held (a list, one legacy object, `{}`, `[]`, nothing, broken JSON), the empty keyboard, the rows the keyboard is packed into — their shape for one to ten buttons, no row left empty and no button lost, the wide row last — and what `assertValid()` refuses — a button of the list and the limit of the list itself
- `Unit/shared/Telegram/Service/ChannelServicePublishPhotosTest` — album grouping, caption truncation and the continuation message, the keyboard travelling with the album that carries the caption, and the album that goes out with no caption at all when the text is empty — with the low-level Telegram client mocked
- `Unit/shared/Telegram/Infrastructure/PublishedDescriptionRepositoryTest` — channel description persistence

Automated coverage is partial: `publishDue()` has unit tests, but `saveParts` beyond the text-or-album rule, `saveFromForm`, `deleteDue()`, `editDue()` and `clean-temp` have no dedicated service-level tests, and no Codeception test drives the publications page. The infinite loading of the three record blocks is covered on both of its halves: `PublicationRepositoryPagingTest` on the `LIMIT`/`OFFSET` reads, and `pubjs/paging.js` on the scroll client (its thresholds, its append, the offset re-derived from the rows on screen, the latch after a refused page, and the block that stops asking when it has reached its `total`) — see «Бесконечная прогрузка списков» in [README.md](README.md). The corner time of the preview is held the same way, on the client half only: `pubjs/previewtime.js` (29 checks) slices the card builder and `previewTimeOf()` out of the nowdoc verbatim, walks the settings and the sender's constants through the same chains the page uses, and drives the built cards over the vendored `moment.min.js`; its red half is 25 mutants (`previewtime-mutants.js`), six of which break the view itself rather than the extracted JS. The geometry — where the corner actually lands — is not something a string check can answer, so a `file://` probe lays the same built cards out in headless Chrome on the real stylesheets and reads their boxes. The frame of a part block is held the same way and by nothing else: `partframe/` lifts the `registerCss` heredoc verbatim out of the view, lays two boxes in the real `#publicationTextParts` container chain — one holding a single block, one holding a split pair — and asks the laid-out page for every block's border, padding, radius, cursor, the box of the fields standing inside it and the border of the album frame nested in it, so a frame standing on the lone block of a monolithic publication is as much a failure as a frame missing from a part, and a row that spills sideways is measured against the padding box of whatever holds it (the frame when there is one, the card when there is not). What has been checked against the runtime this project really uses is described below; remaining gaps are listed at the end.

That runtime is the Docker Compose file at the repository root — `app` on PHP 8.4, `nginx`, `postgres`, and separate `parser` and `telegram` cron containers. All 21 migrations in `app/migrations`, through `m261001_000001_add_text_length_to_topic`, are applied in `yii_dev`; the 19 migrations configured for the test database are applied in `yii_test`. The publications columns `formatting` and `button` are `jsonb`, and `title` is `text` in both databases.

Both databases are reached through `DB_DSN`, and `app/config/test_db.php` falls back to `yii_test` only when that variable is empty — while the `app` container exports the address of the development one. A suite therefore has to be started with the name of the database spelled out:

```
docker compose exec -T -u appuser \
  -e DB_DSN="pgsql:host=postgres;port=5432;dbname=yii_test" \
  app php vendor/bin/codecept run Unit
```

Started any other way, `PublicationRepositoryTest` — whose `_before()` truncates `publications_post`, `publications_draft` and `publications_deleted` — would empty the data being worked on.

Run that way on 2026-10-06, `Unit` is green: 180 tests, 700 assertions. It is the first time an entity list, a keyboard of several link buttons and a heading have gone through a real PostgreSQL write and read instead of a harness — what `createDrafts()` and `createPosts()` put into the three new columns of each part of a long publication, and what each list hands back with the row the value belongs to. The parts of one draft share a single `updated_at`, which is what `allDrafts()` orders by, so their relative order is the database's to choose and the assertion matches each heading against the text of its own row rather than against a position.

`Functional` is not green in the current image. A run on 2026-10-06 produced 10 tests, 4 errors and 3 failures: the four `ContactFormCest` tests error because the app image carries neither GD nor Imagick, which the captcha widget of `/contact` requires; three `LoginFormCest` checks still look for `Logout (admin)`, while `/` renders `dashboard.php`, whose user menu says «Выйти» and names nobody. The other three login scenarios passed. These failures do not exercise publications.

What the browser has been made to do is a click through `/publications`: a publication of two parts with a heading in each of the two fields, a real POST of `publicationPartTitle[]`, the draft it wrote reopened by a double-click on its row, and the composed «Заголовок. Часть N» line watched in the preview and in the counters of the form.

Still unverified is the live Telegram channel: what Telegram accepts of an overlapping entity list, of a keyboard standing under an album, and of a heading that has taken the «Часть N» line out of the text. Nothing has been sent during these checks. The `telegram` service owns `telegram/publish-due`, `telegram/delete-due`, `telegram/edit-due` and `telegram/clean-temp`; the separate `parser` service runs forum scans. The settings are also not covered by Codeception tests: clamping on read, refusal on write, the floor derived from the cron schedule, and both settings pages rest on the service implementation and manual checks.
